# 6. 이미지 생성 프롬프트 점검 및 교정 지침

## 목적

이 문서는 실사 모델 제작 프로젝트의 이미지 생성 작업에서 요구사항 확인서와 최종 영어 프롬프트를 사용자에게 공개하기 직전에 수행하는 공통 사전 점검의 정본이다.

프롬프트가 자연스럽거나 그럴듯한지만 평가하지 않는다. 작업 계약, 참고 자료, 스타일 계약과 고정 영어 블록이 실제 문안에 정확히 반영되었는지를 `통과` 또는 `실패`로 판정하고, 실패한 문안은 승인 요청 전에 바로잡는다.

## 적용 시점과 하드 게이트

1. 필요한 자료와 실제 이미지 픽셀을 확인한다.
2. `2. 요구사항 확인서 작성 규칙.md`의 15개 섹션 고정 양식으로 요구사항 확인서 초안을 작성하고 최종 영어 프롬프트 초안을 작성한다.
3. 이 지침의 점검을 수행한다.
4. 실패 항목이 있으면 자동 교정하고 처음부터 다시 점검한다.
5. 모든 필수 항목이 통과한 뒤에만 요구사항 확인서와 최종 영어 프롬프트를 공개하고 생성을 승인받는다.

점검 결과가 `실패`이거나 확인할 수 없는 필수 항목이 남아 있으면 프롬프트를 확정하지 않는다. 해당 상태에서 `생성`, `진행`, `승인`, `이대로 생성`, `다음`을 요청하거나 이미지 생성 도구를 호출하지 않는다.

이미 실패한 문안을 공개한 뒤 사용자가 생성을 승인했더라도 그 승인을 사용하지 않는다. 문안을 교정하여 다시 공개하고 새 승인을 받는다.

## 점검 전 기준 분류

먼저 스타일 적용 방식을 다음 중 하나로 확정한다.

### A. 제공 이미지 스타일 보존

- 별도 스타일 변경 지시가 없고 입력 이미지의 스타일 자체를 이어야 하는 작업에 적용한다.
- 제공 이미지의 디자인, 스타일, 재질 표현과 마감을 기준으로 사용한다.
- 별도의 정식 스타일 블록과 공통 마감 블록을 자동 삽입하지 않는다.

### B. 프로젝트 승인 스타일 적용

- 프로젝트 내부에 승인된 스타일 계약이나 고정 영어 스타일 블록이 존재하고, 사용자가 그 적용을 원하거나 프로젝트 지침상 적용이 필요한 경우에 사용한다.
- 선택 스타일의 정식 앵커가 있다면 실제 픽셀을 확인한다.
- 선택 스타일의 고정 영어 스타일 블록과 공통 마감 블록을 원문 그대로 삽입한다.

### C. 사용자 지정 스타일 또는 기능성 예외

- 사용자가 다른 스타일을 명시했거나, 상품 설계 보드·기술 레이아웃·제품 단품 정본처럼 기능 계약이 스타일보다 우선하는 경우에 적용한다.
- 적용하거나 제외한 스타일·마감 규칙과 그 근거를 고정 요구사항 확인서의 `6. 시각 스타일`과 필요한 경우 `11. 참고 이미지 역할`에 적는다.
- 프로젝트 승인 스타일을 선택하지 않았다면 그 스타일 블록을 임의로 혼합하지 않는다.

스타일 적용 방식이 둘 이상으로 충돌하면 임의로 혼합하지 않는다. 현재 대화와 참고 자료만으로 기준을 확정할 수 없으면 사용자에게 한 가지 결정만 질문한다.

## 필수 점검표

각 항목은 증거를 확인한 경우에만 `통과`로 판정한다.

### P00. 요구사항 확인서 출력 형식

- 사용자 공개 요구사항 확인서가 `2. 요구사항 확인서 작성 규칙.md`의 **렌더링 Markdown 고정 양식**을 따른다.
- 요구사항 확인서를 플레인 텍스트나 코드 블록으로 감싸지 않았다.
- 문서 제목과 15개 대분류가 지정된 Markdown 제목 계층으로 표시되어 있다.
- 모든 필드명이 `**굵게**` 표시되어 있다.
- 단일 값은 `- **필드명:** 값` 형식으로 한 줄에 기록되어 있다.
- 한 필드에 값이 둘 이상이면 해당 필드 아래 중첩 번호 목록을 사용하며, 쉼표 나열로 평탄화하지 않았다.
- 이미지별 역할처럼 하위 속성이 있는 항목은 상위 항목 아래 중첩 불릿 목록을 사용하고 하위 필드명도 굵게 표시되어 있다.
- `8. 반드시 유지할 요소`, `9. 변경 가능한 요소`, `10. 반드시 제외할 요소`는 복수 항목일 때 번호 목록으로 표시되어 있다.
- `15. 최종 해석 > 우선순위`가 복수이면 중첩 번호 목록으로 표시되어 있다.
- 해당하지 않는 필드도 삭제하지 않고 `해당 없음`, `없음`, `미지정` 중 적절한 값을 유지한다.

P00이 실패하면 내용 점검으로 넘어가기 전에 요구사항 확인서의 Markdown 구조부터 자동 교정하고 다시 점검한다.

### P01. 작업군과 산출물 계약

- 선택된 작업군이 사용자 목적과 일치한다.
- 생성 수량, 캔버스 비율, 파일 형식, 투명 배경, 레이아웃과 필수 패널이 작업 계약과 일치한다.
- 요구사항 확인서와 영어 프롬프트가 같은 산출물을 가리킨다.
- 상품 작업이면 상품 생성 프롬프트 템플릿-v01.md의 MODE TEMPLATE가 하나만 선택되어 있으며 OUTPUT CONTRACT가 현재 산출물과 일치한다.
- DESIGN LAYOUT 또는 PRODUCT DESIGN이면 DESIGN LAYOUT v1의 정보 위계와 필수 패널이 들어 있다.
- PRODUCT MASTER이면 CURRENT_VIEW가 하나만 지정되어 있고 CATEGORY_VIEWSET의 다른 시점과 한 이미지에 섞이지 않는다.

### P02. 대상과 가변 요구사항

- 대상 수, 성별 표현, 연령 인상, 체형, 핵심 외형, 헤어, 메이크업, 의상, 제품 구조, 행동과 감정이 사용자 지시와 일치한다.
- 사용자가 맡긴 자동 보정 요소는 실제로 고정한 해석 또는 `모델 재량으로 미고정`임을 `14. 미확정 사항`에 기록한다. 모델 재량 항목을 사용자 확정 사항처럼 표현하지 않는다.
- 포즈, 카메라, 배경이 미지정이면 모델 재량으로 둘 수 있으며, 자유 결정 영역과 기능상 필수 제한을 구분한다.
- 상품 작업의 핵심 슬롯은 CONFIRMED / DERIVED / UNSET 중 하나로 판정되어 있으며 UNSET 날짜·가격·치수·사이즈·상품 코드·출시 상태·버전을 임의 값으로 바꾸지 않았다.

### P03. 참고 자료와 디자인 기준

- 사용자 제공 이미지, 프로젝트 공식 이미지, 모델 정체성 앵커, 상품 기준 이미지, 설계 자료와 설정 자료의 사용 여부가 기록되어 있다.
- 디자인 기준 이미지가 있으면 어떤 이미지를 우선하는지 명확하다.
- 제공 이미지의 스타일을 보존할지 프로젝트 승인 스타일이나 사용자 지정 스타일로 변경할지 명확하다.
- 기준 이미지가 충돌하거나 대상 동일성이 불명확하면 임의로 선택하지 않는다.
- 상품 작업이면 MODEL, PRODUCT DESIGN, PRODUCT MASTER, FITTING MASTER, 외부 소재·구조 참고가 각각 어떤 역할인지 기록되어 있고 참조의 권한을 넘어 디자인·정체성·브랜드 요소를 복제하지 않는다.

### P04. 스타일 앵커 및 핵심 레퍼런스 실제 확인

프로젝트 승인 스타일 적용 방식 B에서만 필수다. 그 외 방식에서도 핵심 참고 이미지는 실제 픽셀 확인을 권장한다.

- 선택 스타일의 활성 앵커 또는 핵심 스타일 기준 자료를 확인했다.
- 요구사항 확인서 `5. 화면 구성`의 구도, 카메라 거리와 프레이밍이 실제 산출물의 주 프레이밍과 일치한다.
- 실제 불러온 핵심 스타일 앵커와 레퍼런스의 전체 파일명이 요구사항 확인서 `2. 입력 자료` 또는 `11. 참고 이미지 역할`에 기록되어 있다.
- 제외한 핵심 참고 자료가 있으면 전체 파일명과 제외 사유가 요구사항 확인서 `2. 입력 자료` 또는 `11. 참고 이미지 역할`에 기록되어 있다. 참조 예산 한도로 제외한 자료를 `해당 없음`으로 처리하지 않는다.
- 파일명, 메타데이터, 과거 기억이 아니라 실제 이미지 픽셀을 확인했다.
- 사용자 제공 또는 프로젝트 공식 디자인 기준 이미지가 있으면 참조 우선순위를 명확히 기록했다.
- 스타일 앵커에서는 스타일, 마감, 재질 표현만 참조하며 인물 정체성, 의상 내용, 팔레트, 포즈, 카메라와 구도를 무단 복제하지 않는다.

### P05. 고정 영어 스타일 블록

프로젝트 승인 스타일 적용 방식 B에서만 필수다.

- 선택 스타일 계약의 코드 블록 전체가 최종 영어 프롬프트에 한 번만 들어 있다.
- 문장, 단어, 구두점과 순서를 요약, 번역 또는 변형하지 않았다.
- `photorealistic style`, `editorial fashion style` 같은 일반적인 한두 문장은 고정 영어 스타일 블록을 대체하지 못한다.
- 가변 프롬프트가 고정 블록과 다른 얼굴 구조, 재질 표현, 선 처리, 질감 방향을 요구하지 않는다.

### P06. 공통 고정 영어 마감 블록

프로젝트 승인 스타일 적용 방식 B에서만 필수다.

- 공통 마감 규칙의 코드 블록 전체가 최종 영어 프롬프트에 한 번만 들어 있다.
- 문장, 단어, 구두점과 순서를 요약, 확장 또는 변형하지 않았다.
- 고정 영어 스타일 블록 바로 뒤에 배치되어 있다.
- 가변 프롬프트는 공통 마감 블록과 충돌하는 표현을 요구하지 않는다.

### P07. 스타일과 가변 내용의 분리

- 가변 프롬프트는 대상, 디자인, 상품 구조, 행동, 포즈, 카메라, 배경과 출력 규격만 담당한다.
- 모델의 매력, 상품의 고급감, 무드의 세련됨을 특정 문화권 도상이나 과장된 장식으로 자동 치환하지 않는다.
- 스타일 앵커의 콘텐츠나 구도를 긍정 조건으로 복제하지 않는다.
- 같은 스타일을 서로 다른 표현으로 중복 지시하여 고정 블록의 영향력을 흐리지 않는다.

### P08. 인체, 제품 구조와 구도 안정성

- 단일 대상 계약에서 추가 인물, 불필요한 분할 화면, 콜라주와 인셋을 요구하지 않는다.
- 머리, 손, 발, 의상 핵심 부위, 제품 구조가 계약과 맞게 보존된다.
- 손가락, 그립, 제품 착용 방식, 가방 스트랩, 신발 착화, 의상 장력과 바닥 접촉이 물리적으로 읽힌다.
- 전신 실루엣과 주요 상품 또는 소품이 서로 가리지 않도록 한다.
- 상품 설계 이미지와 제품 단품 정본에서는 구조, 봉제, 절개, 여밈, 포켓, 하드웨어, 라벨 위치가 물리적으로 성립해야 한다.
- 러칭, 강한 드레이프 고정점, 두꺼운 플리츠 결합부, 랩 고정점처럼 장력과 원단 겹침이 집중되는 구조선에 긴 지퍼·여밈을 무리하게 중첩하지 않는다. 충돌하면 더 안정적인 구조선으로 여밈을 이동한다.
- FRONT / BACK / LEFT SIDE / RIGHT SIDE 등 복수 뷰가 있는 상품 설계에서는 넥라인, 절개선, 드레이프 시작·고정점, 러칭 집중점, 랩 오버랩, 슬릿 높이, 여밈 위치, 안감·페이싱 경계가 논리적으로 이어져야 한다.
- 한 뷰에 존재하는 핵심 구조선이 인접 뷰에서 이유 없이 사라지거나 다른 구조로 바뀌면 P08 실패로 판정한다.
- PRODUCT MASTER 전환이 예정된 PRODUCT DESIGN은 카테고리에 필요한 핵심 치수 또는 상대적 위치 규칙이 확정되어 있어야 한다. 테스트용 설계 보드의 빈 치수 슬롯은 허용하지만 정본 승격 전에는 잠근다.
- 상품 작업은 상품 생성 프롬프트 템플릿-v01.md의 STRUCTURE LOCK을 빠짐없이 포함하며 카테고리별 VIEWSET과 SIDE 단일화 조건이 현재 상품 구조에 맞는다.
- 디테일 확대 이미지는 본체 스케치에 실제로 존재하는 구조만 확대하며, 확대도에서 새로운 봉제·하드웨어·절개를 임의 추가하지 않는다.

### P09. 금지 조건과 내부 충돌

- 사용자 금지 요소, 작업군별 금지 조건과 선택 스타일의 금지 조건이 반영되어 있다.
- 긍정 조건과 금지 조건이 서로 충돌하지 않는다.
- 사실성, 상품성, 모델 정체성, 배경 처리, 텍스트 포함 여부 등에서 상충 지시가 없다.
- 실존 인물 복제, 특정 브랜드 로고 복제, 비현실적 의복 구조, 과잉 장식, 과도한 AI 아티팩트 유도 표현이 없는지 확인한다.
- 상품 작업은 미확정 날짜·가격·치수·사이즈·상품 코드·출시 상태·버전을 표시하지 않으며 DESIGN LAYOUT 또는 PRODUCT DESIGN의 미확정 필드는 빈칸 또는 TBD로만 처리한다.
- 가짜 브랜드명, 읽을 수 없는 패키지 문구, 워터마크, 장식용 의사 텍스트가 없다.

### P10. 공개본 일치와 승인 가능 상태

- 사용자에게 공개한 요구사항 확인서와 최종 영어 프롬프트가 실제 점검을 통과한 최종본과 동일하다.
- `15. 최종 해석 > 작업 가능 여부`가 `가능`, `확인 필요`, `불가` 중 하나로 명확하다.
- 승인 요청은 `작업 가능 여부`가 `가능 — P00~P10 통과 / 자동 교정: ...`일 때만 붙인다.
- `확인 필요` 또는 `불가` 상태에서는 생성 승인 요청을 붙이지 않는다.

## 판정 규칙

각 항목의 판정은 아래 셋 중 하나만 사용한다.

- `통과`
- `실패`
- `확인 필요`

`확인 필요`는 사용자 결정이 없거나, 증거가 부족하거나, 자료 충돌을 해소할 수 없을 때 사용한다. 추측으로 `통과` 처리하지 않는다.

## 자동 교정 규칙

점검 중 실패 항목이 발견되면 아래 순서로 자동 교정한다.

1. 실패한 항목과 원인을 식별한다.
2. 현재 작업의 정본 지침과 산출물 계약을 다시 확인한다.
3. 사용자 요구를 보존하면서 충돌하는 문장을 제거한다.
4. 누락된 보존 조건, 금지 조건, 출력 조건, 참고 자료 정보를 보강한다.
5. 필요한 경우 스타일 블록, 공통 마감 블록, 참고 이미지 역할 기술을 다시 삽입한다.
6. 요구사항 확인서와 최종 영어 프롬프트를 함께 갱신한다.
7. P00부터 P10까지 처음부터 다시 검사한다.

자동 교정 과정에서도 새로운 창작 결정을 임의로 확정하지 않는다. 사용자 확인이 필요한 사항은 `14. 미확정 사항`과 `15. 최종 해석 > 작업 가능 여부`에 `확인 필요`로 남긴다.

## 생성 직전 최종 점검

사용자가 승인한 뒤 실제 생성 직전에 아래를 마지막으로 확인한다.

1. 공개본과 실행본이 완전히 같은가.
2. 승인 이후 새로 바뀐 요구사항이 없는가.
3. 승인 상태가 이미 소모되지 않았는가.
4. 핵심 참고 자료 접근 가능 상태가 유지되는가.

하나라도 만족하지 않으면 도구를 호출하지 않고 새 확인서와 새 승인 절차로 되돌린다.
