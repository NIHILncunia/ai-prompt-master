# 이미지 생성 공통 승인 절차

## 공통 폴더 운영 진입점과 동기화

이 폴더의 `PROJECT AGENTS.md`, `1. 이미지 생성 공통 승인 절차.md`, `2. 요구사항 확인서 작성 규칙.md`, `6. 이미지 생성 프롬프트 점검 및 교정 지침.md`는 함께 공통 이미지 정책의 운영 진입점으로 취급한다.

이미지 생성 계열 작업을 시작할 때에는 프로젝트 루트 지침, 이 승인 절차, 해당 기능 또는 작업군의 로컬 지침, 현재 작업과 직접 관련된 모델 정체성 정본과 레퍼런스 자료를 확인한 뒤 요구사항 확인서와 최종 영어 프롬프트 초안을 조립하고, 6번 점검 지침을 적용한다. 상품 설계·상품 단품·피팅·화보 파생 작업은 추가로 패션·뷰티-시장성-상품생성-지침-v02.md와 상품 생성 프롬프트 템플릿-v01.md를 읽는다.

승인 상태 정의, 첫 응답 절차, 재승인 조건, 공통 확인 양식 또는 파일 작업 정책을 바꾸면 프로젝트 루트 지침과 이 폴더의 관련 운영 문서도 함께 점검한다. 기능별 스타일·출력 형식·구도 규칙은 각 기능 문서가 소유하며 이 공통 문서에 과도하게 복제하지 않는다.

## 문서 목적

이 문서는 실사 모델 제작 프로젝트의 모든 이미지 생성 계열 요청에 적용되는 공통 승인 절차다.

모델 앵커, 뷰티 포트레이트, 패션 룩북, 상품 설계 이미지, 상품 단품 정본, 전신 착용샷, 화보, 라이프스타일 이미지, SNS용 비주얼, 광고 컷, 이미지 수정, 이미지 재구성, 참고 이미지 기반 재생성 요청은 모두 이 절차를 먼저 따른다.

## 최우선 이미지 생성 하드 게이트

이미지 생성 계열 요청에서는 이미지 생성·수정 도구 호출보다 이 확인 절차가 항상 먼저다.

- 첫 응답에서는 절대로 이미지 생성·수정 도구를 호출하지 않는다.
- 사용자가 `생성`, `진행`, `다음`, `1번 실행`, `생성해줘`, `그려줘`, `만들어줘`, `바로 생성`, `create`, `generate`, `draw`, `render`라고 말해도, 승인 절차가 완료되기 전에는 그 말 자체를 도구 호출 승인으로 해석하지 않는다.
- 승인 상태는 어시스턴트가 같은 대화 흐름에서 공통 점검을 통과한 요구사항 확인서와 최종 영어 프롬프트를 먼저 공개한 뒤, 사용자가 그 해석을 보고 명시적으로 승인했을 때만 성립한다.
- 승인 상태가 성립하기 전의 `생성` 계열 표현은 전부 `요구사항 확인 절차를 시작하라`는 뜻으로 처리한다.
- `확인 없이 생성`, `확인 필요 없음`, `사전 확인 생략`, `바로 생성`, `즉시 만들어` 같은 표현도 이 하드 게이트를 우회하지 못한다.
- 프롬프트만 요청한 경우에는 이미지를 생성하지 않는다.


## 승인 키워드 공개 규칙

요구사항 확인서와 최종 영어 프롬프트를 공개하여 이미지 생성 승인을 받을 때에는, 사용자가 어떤 말로 생성 실행을 승인할 수 있는지 반드시 함께 고지한다.

- 고지는 확인서·최종 프롬프트 뒤, `SESSION PROGRESS` 앞에 배치한다.
- 기본 고지 문구는 `생성 실행 키워드: 생성, 진행, 승인, 이대로 생성, 좋다, 확정, 다음, go, generate it`이다.
- 사용자가 가장 간단히 사용할 키워드는 `생성`임을 명시한다.
- 이미지 생성이 실제로 실행된 결과 보고에는 사용자가 입력한 승인 키워드와 해당 승인 상태가 소모되었음을 기록한다.

## 승인 상태 정의

승인 상태는 아래 네 조건이 모두 충족될 때만 성립한다.

1. 어시스턴트가 요청 유형과 작업군을 판별했다.
2. 요구사항 확인서와 최종 영어 프롬프트 초안이 `6. 이미지 생성 프롬프트 점검 및 교정 지침.md`의 필수 항목을 모두 통과했다.
3. 어시스턴트가 통과한 한국어 요구사항 확인서와 최종 영어 프롬프트를 사용자에게 공개했다.
4. 사용자가 그 확인서를 본 뒤 `생성`, `진행`, `승인`, `이대로 생성`, `좋다`, `확정`, `다음`, `go`, `generate it`처럼 명시적으로 승인했다.

위 네 조건 중 하나라도 충족되지 않으면 이미지 생성·수정 도구를 호출하지 않는다.

### `다음` 명령의 단계별 해석

- 요구사항 확인서와 최종 영어 프롬프트가 공개되기 전의 `다음`은 준비·해석·자료 확인 등 현재 절차의 다음 단계 진행으로 처리하며, 이미지 생성 승인으로 해석하지 않는다.
- 요구사항 확인서와 최종 영어 프롬프트를 공개하고 생성 여부를 묻는 상태에서 사용자가 `다음`이라고 응답하면, `생성`·`진행`·`승인`과 동일한 명시적 승인으로 해석하여 직전 확인서의 생성 작업을 즉시 실행한다.
- 이미지 생성이 완료된 뒤 입력된 `다음`은 다음 산출물·프레이밍·변형·시안으로 넘어가라는 요청으로 해석한다. 이 경우 소모된 승인 상태를 재사용하지 않고 새 요구사항 확인서와 최종 영어 프롬프트를 공개한 뒤 다시 승인받는다.
- 사용자가 `프롬프트만`, `생성 전에 검토` 등 실제 생성을 제외한 범위를 명시한 상태에서는 `다음`만으로 이미지 생성을 시작하지 않는다. 실제 생성으로 전환하려면 사용자가 생성 의사를 별도로 명시해야 한다.

## 첫 응답 고정 처리

이미지 생성 계열 요청을 받으면 첫 응답은 아래 순서를 따른다.

1. 요청 유형을 판별한다.
2. 필요한 프로젝트 지침과 작업군 기준을 확인한다.
3. 제공 이미지의 스타일을 보존할지, 사용자가 명시한 스타일로 변경할지 판정한다.
4. 스타일·정체성·상품·레이아웃 등 핵심 레퍼런스의 실제 이미지 픽셀을 확인한다.
5. 사용자의 요구사항을 해석한다.
6. 상품 작업이면 상품 생성 프롬프트 템플릿-v01.md에서 MODE TEMPLATE를 하나 선택하고, 슬롯값·VIEWSET·고정 계약 블록을 조립한다.
7. `2. 요구사항 확인서 작성 규칙.md`의 15개 섹션 고정 양식을 그대로 사용하여 요구사항 확인서를 작성하고, 그 다음 최종 영어 프롬프트 초안을 작성한다.
8. `6. 이미지 생성 프롬프트 점검 및 교정 지침.md`의 P00~P10을 검사하고 실패 항목을 자동 교정한다.
9. 전 항목을 통과한 요구사항 확인서와 최종 영어 프롬프트를 함께 공개한다.
10. 마지막에 `위 해석과 최종 프롬프트로 생성할까요?`라고 확인한다.

이 첫 응답에서는 이미지를 생성하지 않는다.

## 요구사항 확인서 고정 양식

사용자에게 공개하는 요구사항 확인서는 `2. 요구사항 확인서 작성 규칙.md`에 정의된 **`[이미지 생성 요구사항 확인서]` 15개 섹션 고정 양식**을 그대로 사용한다.

- 번호·섹션 제목·필드명·순서뿐 아니라 **Markdown 계층 구조와 강조 규칙도 변경하지 않는다.**
- 요구사항 확인서는 플레인 텍스트나 코드 블록으로 출력하지 않고 **실제 Markdown이 렌더링되는 형태**로 공개한다.
- 15개 대분류는 `###` 제목으로 표시하고, 각 필드명은 반드시 `**굵게**` 표시한다.
- 단일 값은 `- **필드명:** 값` 한 줄로 작성한다.
- 한 필드에 값이 둘 이상이면 필드 아래 **중첩 번호 목록**으로 분리하고, 쉼표 나열로 평탄화하지 않는다.
- 이미지별 역할처럼 하위 속성이 있는 항목은 상위 항목 아래 **중첩 불릿 목록**으로 작성하고 하위 필드명도 굵게 표시한다.
- 기능에 필요하지 않은 필드도 삭제하지 않고 `해당 없음` 또는 `없음`으로 유지한다.
- 작업군별 추가 정보는 가장 가까운 기존 필드의 값 안에 기록하며 새 섹션이나 새 필드를 만들지 않는다.
- 요구사항 확인서 뒤에는 아래 형식으로 최종 영어 프롬프트를 별도 공개한다.

````md
## 최종 영어 프롬프트
```text
...
```

위 내용으로 진행하려면 `생성`, `진행`, `승인`, `이대로 생성`, `다음`처럼 명시적으로 승인해 주세요.
````

P00~P10 점검 결과와 자동 교정 내역은 별도 공개 필드를 추가하지 않고, 고정 양식의 `15. 최종 해석 > 작업 가능 여부`에 `가능 — P00~P10 통과 / 자동 교정: ...` 형식으로 통합한다.

도구 참조 한도 때문에 일부 참고 이미지를 제외한 경우에는 해당 파일명과 제외 사유를 `2. 입력 자료` 또는 `11. 참고 이미지 역할`의 기존 필드 안에 기록한다. 제외된 자료를 `해당 없음`으로 표시하지 않는다.

### 스타일 프롬프트 조립 규칙

- 제공 이미지 스타일 보존이 선택되면 해당 이미지의 스타일, 재질 표현과 마감을 기준으로 기술하며 별도의 정식 스타일 블록을 자동 삽입하지 않는다.
- 사용자가 특정 스타일이나 프로젝트 승인 스타일을 지정하면, 해당 스타일 계약이 존재할 경우 그 고정 영어 스타일 블록과 공통 마감 규칙을 문장 변경 없이 삽입한다.
- 기능별 가변 프롬프트는 대상, 디자인, 의상, 상품 구조, 행동, 포즈, 카메라, 배경, 출력 규격만 담당한다.
- 상품 작업은 자유 자연어 문안이 아니라 상품 생성 프롬프트 템플릿-v01.md의 선택된 MODE TEMPLATE에 슬롯값을 채워 조립한다. LAYOUT CONTRACT, VIEWSET CONTRACT, STRUCTURE LOCK, BRAND LOCK, TEXT / METADATA POLICY, QUALITY, NEGATIVE / CONSTRAINT 블록은 원문 그대로 한 번씩만 넣는다.
- 상품의 날짜·가격·치수·사이즈·상품 코드·출시 상태·버전이 미확정이면 임의로 값을 만들지 않는다. DESIGN LAYOUT과 PRODUCT DESIGN에서는 빈칸 또는 TBD, PRODUCT MASTER 이후 단계에서는 미표시로 처리한다.
- 스타일 앵커의 인물 정체성, 의상 내용, 팔레트, 포즈, 카메라, 배경과 구성을 최종 프롬프트의 긍정 조건으로 복제하지 않는다.
- 조립한 문안은 공개하기 전에 `6. 이미지 생성 프롬프트 점검 및 교정 지침.md`의 전체 점검을 통과해야 한다.

## 작업군별 산출물 계약 하드 게이트

하나의 승인 상태는 하나의 생성 작업만 승인한다.

생성 작업의 출력 수, 캔버스 구성, 단일 뷰 또는 다중 뷰 여부는 선택된 작업군의 마스터 규칙이 정의한 산출물 계약을 따른다.

- 공통 승인 절차는 모든 작업을 단일 인물·단일 뷰로 제한하지 않는다.
- 상품 설계 보드, 다각도 상품 단품 정본, 모델 앵커 세트처럼 작업 정의상 복수 패널 또는 복수 파일이 필요한 산출물은 해당 작업군 계약 안에서 허용한다.
- DESIGN LAYOUT과 PRODUCT DESIGN은 승인된 레이아웃 안의 복수 패널을 허용한다. PRODUCT MASTER는 한 이미지에 한 상품·한 시점만 허용하며 CATEGORY_VIEWSET의 각 시점은 별도 파일·별도 승인 단위다.
- 서로 다른 성격의 산출물을 묶어 한 번에 생성하려면 그 조합 자체가 하나의 산출물 계약으로 정의되어 있어야 한다.
- 같은 대화에서 여러 장이 필요해도 승인 단위와 산출물 계약은 항상 함께 움직인다.

## 재승인 조건

다음 중 하나라도 발생하면 기존 승인 상태를 폐기하고 새 요구사항 확인서와 최종 영어 프롬프트를 다시 공개한 뒤 재승인받는다.

1. 대상이 바뀐다.
2. 작업 유형이 바뀐다.
3. 생성 수량이 바뀐다.
4. 화면 비율, 투명 배경, 레이아웃, 필수 패널, 전신/반신 같은 산출물 계약이 바뀐다.
5. 디자인 기준 이미지, 상품 기준 이미지, 정체성 앵커, 참고 이미지가 바뀐다.
6. 스타일 보존 / 스타일 변경 / 프로젝트 승인 스타일 적용 여부가 바뀐다.
7. 핵심 의상, 메이크업, 헤어, 소품, 포즈, 카메라, 배경, 조명이 실질적으로 바뀐다.
8. 수정 작업에서 유지 영역과 변경 영역이 바뀐다.
9. 요구사항 확인서나 최종 영어 프롬프트가 점검 실패로 교정되었다.
10. 이전 승인 상태를 이미 한 번 사용했다.

## 생성 직전 최종 확인

사용자가 명시적으로 승인한 직후에도 즉시 도구를 호출하지 말고 아래를 다시 확인한다.

1. 요구사항 확인서 `15. 최종 해석 > 작업 가능 여부`가 `가능 — P00~P10 통과 ...`인지 확인한다.
2. 실제 실행할 프롬프트가 사용자에게 공개되어 승인받은 버전과 동일한지 확인한다.
3. 승인 이후 새로 바뀐 대상, 스타일, 참고 자료, 산출물 계약이 없는지 확인한다.
4. 승인 상태가 이미 다른 생성 작업에 사용되지 않았는지 확인한다.

위 네 항목 중 하나라도 어긋나면 도구를 호출하지 않고 재승인 절차로 되돌린다.

## 승인 상태의 1회성

하나의 승인 상태는 하나의 생성 작업을 실행하는 순간 즉시 소모된다.

- 생성이 끝난 뒤 `다음`, `이 버전 수정`, `이제 화보`, `같은 옷으로 다른 컷`, `비율만 바꿔서 다시`, `이번엔 다른 모델에게 입혀`처럼 이어지는 요청은 모두 새 생성 작업이다.
- 새 생성 작업은 새 요구사항 확인서와 새 최종 영어 프롬프트 공개, 새 승인 절차를 다시 거친다.

## 생성 완료 후 자가검수

이미지를 생성한 뒤에는 아래 항목을 점검한다.

1. 대상, 정체성, 상품 또는 구조가 승인된 요구사항과 일치하는가.
2. 수량, 화면 비율, 구도, 프레이밍, 캔버스와 레이아웃이 계약과 일치하는가.
3. 참고 자료에서 반드시 유지하기로 한 요소가 실제로 유지되었는가.
4. 제외하기로 한 요소가 들어가지 않았는가.
5. 손, 발, 얼굴, 의상, 제품 구조, 텍스트, 배경 등에서 치명적 시각 오류가 없는가.
6. 작업군 고유 규칙이 있다면 충족되었는가.

자가검수 판정은 아래 셋 중 하나로만 내린다.

- `사용 권고`: 승인된 목적에 충분히 부합한다.
- `재생성 권고`: 핵심 오류가 있어 새 확인서와 새 승인 뒤 재생성이 바람직하다.
- `확인 보류`: 일부 모호한 지점이 있어 사용자 판단이 필요하다.

문제가 있어도 자동으로 재생성하지 않는다. 필요한 경우 실패 원인과 수정 방향을 요약한 뒤 새 요구사항 확인서와 새 최종 영어 프롬프트를 다시 공개한다.
