# 8. 마스터 프롬프트 생성 규칙 설계

## 1. 단계 목적

이 문서는 창작 이미지 마스터 프롬프트 생성 웹앱의 핵심 출력물인 `마스터 프롬프트`를 어떻게 생성할지 정의한다.

이 웹앱은 이미지 생성 모델에 직접 넣을 최종 영문 프롬프트를 바로 생성하는 도구가 아니다.

웹앱은 사용자가 선택한 구조화 입력값을 바탕으로, GPT / Gemini / Grok 같은 채팅형 AI에게 전달할 상담형 마스터 프롬프트를 생성한다.

채팅형 AI는 이 마스터 프롬프트를 읽고, 필요하면 사용자에게 부족한 정보를 질문한 뒤, 최종 이미지 생성용 영어 프롬프트를 작성한다.

---

## 2. 마스터 프롬프트의 정의

마스터 프롬프트는 사용자의 선택값과 추가 입력을 바탕으로 채팅형 AI에게 전달되는 상위 지시문이다.

마스터 프롬프트는 다음 역할을 한다.

```text
- 사용자가 어떤 이미지를 만들려는지 해석하게 한다.
- 선택된 사용처에 맞는 최종 프롬프트 형식을 지시한다.
- 카테고리별 핵심 시각 정보를 정리해서 전달한다.
- 부족한 정보가 있으면 짧은 질문을 하게 한다.
- 정보가 충분하면 최종 영어 프롬프트 옵션을 만들게 한다.
- selected / auto / directInput / none 처리 규칙을 지키게 한다.
- 참조 이미지가 있을 경우 플레이스홀더와 사용 목적을 명확히 알려준다.
```

즉, 마스터 프롬프트는 최종 프롬프트 자체가 아니라, 최종 프롬프트를 만들기 위한 상담형 지시문이다.

---

## 3. 마스터 프롬프트와 최종 영문 프롬프트의 차이

두 개념은 반드시 분리해야 한다.

```text
마스터 프롬프트
- 웹앱이 생성한다.
- 채팅형 AI에게 전달한다.
- 한국어 상담 규칙과 영어 최종 프롬프트 생성 규칙을 함께 포함한다.
- 구조화 입력값, 카테고리 지식, 사용처별 출력 규칙을 담는다.

최종 영문 프롬프트
- 채팅형 AI가 생성한다.
- 실제 이미지 생성 모델이나 이미지 생성 서비스에 입력한다.
- 사용처에 따라 자연어형, 태그형, positive / negative 분리형 등으로 달라진다.
```

웹앱은 최종 영문 프롬프트를 직접 완성하려고 하지 않는다.

웹앱의 책임은 채팅형 AI가 정확한 상담과 최종 프롬프트 생성을 수행하도록 충분한 지시문을 만드는 것이다.

---

## 4. 전체 생성 흐름

마스터 프롬프트 생성 흐름은 다음 순서로 진행한다.

```text
1. 사용처 선택값을 확인한다.
2. 선택된 사용처에 맞는 출력 규칙을 결정한다.
3. 카테고리 선택값을 확인한다.
4. 공통 필드 16개를 정리한다.
5. 선택된 카테고리의 전용 필드만 활성화한다.
6. selected / auto / directInput / none 상태를 해석한다.
7. 포함 요청, 제외 요청, 추가 요청을 정리한다.
8. 참조 이미지 사용 가능 여부와 슬롯 검증 결과를 반영한다.
9. 카테고리 지식과 자동 고려 사항을 삽입한다.
10. 부족 정보 판단 규칙을 삽입한다.
11. 최종 출력 형식을 삽입한다.
12. 품질 규칙을 삽입한다.
```

이 과정을 거쳐 하나의 상담형 마스터 프롬프트가 만들어진다.

---

## 5. 마스터 프롬프트 기본 블록 구조

마스터 프롬프트는 다음 블록 순서를 기본으로 한다.

```text
1. Role Block
2. Core Behavior Block
3. Target Usage Output Rule Block
4. Mode Interpretation Block
5. Reference Image Rule Block
6. Structured User Input Block
7. Category Specification Block
8. Category Knowledge Block
9. Consultation Decision Rule Block
10. Final Output Format Block
11. Quality Rule Block
```

각 블록은 상황에 따라 일부 생략될 수 있다.

예를 들어 참조 이미지가 없는 경우 `Reference Image Rule Block`은 삽입하지 않거나 “참조 이미지 없음”으로 간단히 처리한다.

비채팅형 사용처에서는 참조 이미지 관련 블록을 아예 만들지 않는다.

---

## 6. Role Block

Role Block은 채팅형 AI에게 역할을 부여한다.

이 블록은 모든 마스터 프롬프트에 들어간다.

실제 마스터 프롬프트에는 영어로 작성한다.

```text
You are an active Korean image-prompt consultant and creative director.

Your job is not to blindly output a final image prompt immediately.
Your job is to understand the user's intended image from the structured inputs, detect any visually important missing information, ask concise follow-up questions only when needed, and then produce production-ready English image prompts for the selected target service.
```

역할은 단순 프롬프트 작성자가 아니라 상담형 이미지 프롬프트 디렉터로 잡는다.

이렇게 해야 사용자의 선택값이 약할 때 질문하고, 충분할 때만 최종 프롬프트를 작성하는 흐름이 안정된다.

---

## 7. Core Behavior Block

Core Behavior Block은 채팅형 AI가 반드시 따라야 하는 기본 행동 규칙이다.

이 블록도 모든 마스터 프롬프트에 들어간다.

```text
Core behavior:
- First understand the user's intended image from the structured inputs.
- Preserve every explicit user selection.
- Preserve every direct user input, especially proper nouns, worldbuilding terms, character names, place names, organization names, and custom terminology.
- Do not collapse multiple subjects, objects, or requested details into one vague phrase.
- If an input contains two or more entities, preserve every entity explicitly and clarify their visual relationship when needed.
- Treat fields marked as auto as permission to complete the design naturally based on the previous selections.
- Do not ask about every auto field.
- Ask follow-up questions only when missing information would materially change the final image.
- If the brief is already strong enough, produce final prompt options immediately.
- Consult the user in Korean.
- Write final image prompts in English unless the user explicitly asks otherwise.
```

여기서 가장 중요한 문장은 `Do not ask about every auto field`다.

5번에서 스킵은 auto로 통합되었으므로, auto 필드를 전부 질문하면 선택형 웹앱의 장점이 사라진다.

---

## 8. Target Usage Output Rule Block

Target Usage Output Rule Block은 7번 문서의 사용처별 출력 규칙을 삽입하는 영역이다.

사용처별로 하나의 블록만 선택해서 넣는다.

### 8.1 GPT / ChatGPT 이미지 생성

```text
Target service: GPT / ChatGPT image generation.

Write the final image prompts in clear natural English.
Use complete visual descriptions rather than thin keyword fragments.
Describe the subject, composition, lighting, mood, background, style, and any required exclusions naturally.
If reference image placeholders are provided, explain exactly how each reference image should be used.
Do not create tag-only prompts.
Do not include unnecessary model parameters.
```

### 8.2 Gemini / Imagen

```text
Target service: Gemini / Imagen.

Write the final image prompts in clear natural English.
Use descriptive visual sentences that explain the subject, environment, composition, lighting, colors, and mood.
Prioritize clarity and visual specificity.
If reference image placeholders are provided, connect each placeholder to its intended visual role.
Do not use tag-only formatting.
```

### 8.3 Grok

```text
Target service: Grok image generation.

Write the final image prompts in direct, clear English.
Put the main subject and image purpose first.
Then describe style, composition, background, lighting, mood, and important details.
If reference image placeholders are provided, clearly state what each reference image should preserve or influence.
```

### 8.4 Midjourney

```text
Target service: Midjourney.

Write the final prompt in English using a compact natural-language and visual-keyword hybrid style.
Place the core subject and strongest visual identity at the beginning.
Use concise comma-separated visual descriptors when helpful.
Include composition, lighting, mood, style, and environment.
If useful, place aspect ratio or style-related parameters at the end.
Do not include reference image placeholders.
Do not use Stable Diffusion-style tag dumping.
```

### 8.5 FLUX

```text
Target service: FLUX.

Write the final prompt in clear English natural language.
Use concrete visual descriptions with a strong subject, composition, material detail, lighting, mood, and style direction.
Avoid excessive tag lists.
Do not include reference image placeholders.
Keep the prompt model-agnostic enough to remain stable.
```

### 8.6 Z-Image-Turbo / ZIT

```text
Target service: Z-Image-Turbo / ZIT.

Write the final prompt in English using concise natural language supported by strong visual keywords.
Put the main subject and visual goal first.
Avoid overly long paragraphs.
Do not include reference image placeholders.
Keep the image direction clear, direct, and visually grounded.
```

### 8.7 모르겠음 / 범용

```text
Target service: unknown / general-purpose image generation.

Write a broadly compatible English image prompt.
Do not rely on model-specific syntax, parameters, or reference image placeholders.
Use natural-language visual description.
Include subject, style, composition, lighting, mood, background, and important constraints.
```

### 8.8 NovelAI / SDXL / SD 1.5 / Pony / Illustrious / NoobAI

```text
Target service: tag-based or Stable Diffusion-style image generation.

Write the final output in English.
Use a structured positive prompt and negative prompt when appropriate.
Place selected values, direct inputs, must-include details, subject identity, composition, visual style, lighting, mood, and background in the positive prompt.
Place none conditions and exclusion requests in the negative prompt.
Do not include reference image placeholders.
Prefer clear visual tags and concise keyword phrases over long prose.
Preserve user-defined proper nouns and unique terms when they matter.
```

### 8.9 기타 / 직접 입력

```text
Target service: user-defined or custom.

Follow the user's custom target-service description when provided.
If no detailed target-service rule is available, use a clear general-purpose English natural-language prompt.
Do not include reference image placeholders unless the target service is explicitly defined as a chat-style image generator that can use attached references.
```

## 9. Mode Interpretation Block

Mode Interpretation Block은 5번 문서의 selected / auto / directInput / none 규칙을 전달한다.

이 블록은 모든 마스터 프롬프트에 들어간다.

```text
Input mode interpretation:
- selected means the user explicitly selected this value. Preserve it and reflect it clearly.
- auto means skip / automatic / leave it to the AI. Complete it naturally based on category, usage target, main subject, output purpose, mood, and layout. Do not ask about every auto field.
- directInput means the user directly wrote this value. Preserve the meaning and keep proper nouns or custom terms intact.
- none means the element must not appear. Treat it as an explicit absence condition and, when needed, as a negative requirement.
```

이 블록에는 우선순위도 함께 넣는다.

```text
Conflict priority:
1. Exclusion requests
2. none
3. directInput
4. Include requests
5. selected
6. auto
```

이 우선순위는 선택값과 제외 조건이 충돌할 때 반드시 적용한다.

---

## 10. Structured User Input Block

Structured User Input Block은 웹앱에서 수집한 공통 필드 16개를 정리해 넣는 영역이다.

모든 필드를 무조건 길게 넣는 것이 아니라, 의미 있는 값만 정리한다.

다만 auto 필드는 별도로 누락시키기보다, 하단에 “자동 보완 대상”으로 요약할 수 있다.

기본 구조는 다음과 같다.

```text
[Structured User Input]

Usage target:
- {usageTarget}

Category:
- {category}

World context:
- {worldContext}

Main subject type:
- {mainSubjectType}

Output purpose:
- {outputPurpose}

Style direction:
- {styleDirection}

Mood:
- {mood}

Background setting:
- {backgroundSetting}

Layout / composition:
- {layout}

Text policy:
- {textPolicy}

Must include:
- {includeRequests}

Must avoid:
- {excludeRequests}

Additional user request:
- {additionalRequests}
```

`detailDesign`은 이 블록에 직접 넣지 않고, 다음의 Category Specification Block에 넣는다.

`referenceImages`도 별도 Reference Image Rule Block으로 분리한다.

---

## 11. 공통 필드 삽입 규칙

공통 필드 16개는 다음처럼 처리한다.

```text
category
- 반드시 삽입한다.
- 카테고리 지식과 전용 필드 분기 기준이 된다.

usageTarget
- 반드시 삽입한다.
- 사용처별 출력 지시 블록을 결정한다.

worldContext
- selected / directInput이면 명시한다.
- auto이면 장르와 세계관을 자연 보완하라고 지시한다.
- none은 허용하지 않는다.

mainSubjectType
- 반드시 삽입한다.
- auto일 경우에도 카테고리와 출력 목적을 기준으로 중심 대상을 보완하라고 지시한다.

outputPurpose
- 반드시 삽입한다.
- 레퍼런스 시트, 아이콘, 지도, 배틀맵, VFX 시트 등 결과물 형식에 직접 영향을 준다.

detailDesign
- 공통 블록에 넣지 않는다.
- 선택된 카테고리의 전용 스키마 블록으로 삽입한다.

styleDirection
- selected / directInput이면 명시한다.
- auto이면 사용처와 카테고리에 맞게 보완하도록 한다.

mood
- selected / directInput이면 명시한다.
- auto이면 중심 대상과 장르에 맞게 보완하도록 한다.

backgroundSetting
- 카테고리별 중심성이 다르므로 선택값을 그대로 반영한다.
- none이면 배경 없음 조건으로 처리한다.

layout
- outputPurpose와 함께 최종 프롬프트 구도를 결정한다.
- selected / directInput이면 반드시 반영한다.

referenceImages
- 사용처와 첨부 검증 조건을 통과한 경우에만 별도 블록으로 삽입한다.

textPolicy
- none이면 텍스트 없음 조건으로 처리한다.
- 로고, 지도, 시트형 결과물에서는 특히 중요하게 반영한다.

includeRequests
- 반드시 포함할 조건으로 삽입한다.

excludeRequests
- 가장 높은 우선순위의 제외 조건으로 삽입한다.

additionalRequests
- 사용자 자유 요청으로 삽입한다.
- 고유명사를 유지한다.

automationPolicy
- 별도 표시값이라기보다 selected / auto / directInput / none 처리 규칙으로 작동한다.
```

---

## 12. Category Specification Block

Category Specification Block은 4번 문서에서 확정한 11개 전용 스키마 중 하나만 삽입한다.

선택된 카테고리에 해당하는 전용 필드만 활성화한다.

```text
character_person
→ characterSpecification

monster_creature
→ creatureSpecification

landscape_background_place_world
→ placeSpecification

building_architecture_structure
→ architectureSpecification

scene_narrative_illustration
→ sceneSpecification

item_weapon_artifact_prop
→ itemSpecification

costume_equipment_design
→ costumeSpecification

mecha_vehicle_machine
→ machineSpecification

symbol_emblem_logo
→ symbolSpecification

map_battlemap
→ mapSpecification

concept_phenomenon_effect
→ effectSpecification
```

다른 카테고리의 전용 필드는 마스터 프롬프트에 넣지 않는다.

예를 들어 캐릭터 카테고리라면 `characterSpecification`만 넣고, `creatureSpecification`, `mapSpecification`, `effectSpecification` 등은 넣지 않는다.

---

## 13. 카테고리별 전용 필드 삽입 방식

전용 필드는 선택값이 있는 항목과 직접 입력값이 있는 항목을 중심으로 삽입한다.

auto 항목은 전부 나열하지 않고, 카테고리별 자동 보완 지시로 묶는다.

none 항목은 반드시 부정 조건으로 별도 반영한다.

### 13.1 캐릭터 / 인물

```text
[Character Specification]
- Character focus: {characterFocus}
- Number of characters: {numberOfCharacters}
- Role archetype: {roleArchetype}
- Age range: {ageRange}
- Body type: {bodyType}
- Face impression: {faceImpression}
- Expression: {expression}
- Gaze: {gaze}
- Pose: {pose}
- Hair: {hair}
- Eyes: {eyes}
- Skin: {skin}
- Distinctive features: {distinctiveFeatures}
- Non-human traits: {nonHumanTraits}
- Outfit summary: {outfitSummary}
- Equipment summary: {equipmentSummary}
- Reference sheet options: {referenceSheetOptions}
```

자동 보완 지시는 다음처럼 넣는다.

```text
Complete any auto character details naturally, focusing on a coherent silhouette, readable face, consistent outfit, and clear character identity.
```

### 13.2 몬스터 / 크리처

```text
[Creature Specification]
- Creature focus: {creatureFocus}
- Scale: {creatureScale}
- Body structure: {bodyStructure}
- Movement method: {movementMethod}
- Silhouette: {silhouette}
- Surface type: {surfaceType}
- Texture: {texture}
- Color pattern: {colorPattern}
- Attack method: {attackMethod}
- Special ability: {specialAbility}
- Intelligence level: {intelligenceLevel}
- Habitat: {habitat}
- Ecological role: {ecologicalRole}
```

자동 보완 지시는 다음처럼 넣는다.

```text
Complete any auto creature details naturally, prioritizing body structure, threat readability, scale, texture, and ecological logic.
```

### 13.3 풍경화 / 배경 / 장소 / 세계관

```text
[Place Specification]
- Place category: {placeCategory}
- Place type: {placeType}
- Spatial structure: {spatialStructure}
- Terrain elements: {terrainElements}
- Natural elements: {naturalElements}
- Artificial elements: {artificialElements}
- Landmark: {landmark}
- Worldbuilding feature: {worldbuildingFeature}
- Environmental condition: {environmentalCondition}
- Lighting condition: {lightingCondition}
- Weather: {weather}
- Time of day: {timeOfDay}
```

자동 보완 지시는 다음처럼 넣는다.

```text
Complete any auto place details naturally, focusing on spatial clarity, atmosphere, lighting, terrain, and worldbuilding identity.
```

### 13.4 건물 / 건축물 / 구조물

```text
[Architecture Specification]
- Architecture category: {architectureCategory}
- Architecture type: {architectureType}
- Culture style: {cultureStyle}
- Architectural style: {architecturalStyle}
- Scale: {scale}
- Silhouette: {silhouette}
- Structural form: {structuralForm}
- Main function: {mainFunction}
- Material: {material}
- Ornament: {ornament}
- Mechanical elements: {mechanicalElements}
- Magical elements: {magicalElements}
- Damage state: {damageState}
```

자동 보완 지시는 다음처럼 넣는다.


## 14. none 조건 삽입 규칙

none 조건은 반드시 별도 부정 조건으로 정리한다.

none은 auto와 다르므로, 채팅형 AI가 임의로 추가하지 못하도록 명시해야 한다.

```text
[Explicit Absence Conditions]
- No wings.
- No text inside the image.
- No detailed background.
- No grid.
- No frame.
```

사용처가 태그형 / Stable Diffusion 계열이면 none 조건은 negative prompt로 이동한다.

사용처가 자연어 계열이면 자연어 부정 조건으로 정리한다.

## 15. includeRequests / excludeRequests / additionalRequests 처리

세 필드는 최종 이미지 방향에 큰 영향을 준다.

따라서 마스터 프롬프트 안에서 별도 블록으로 분리한다.

```text
[Must Include]
- {includeRequests}

[Must Avoid]
- {excludeRequests}

[Additional User Notes]
- {additionalRequests}
```

처리 우선순위는 다음과 같다.

```text
- Must Avoid는 가장 강하다.
- none은 Must Avoid에 준하는 부정 조건이다.
- directInput은 selected보다 우선한다.
- Must Include는 selected보다 우선한다.
- auto는 앞선 모든 조건을 침범하지 않는 범위에서만 보완한다.
```

## 16. Reference Image Rule Block

참조 이미지 블록은 사용처와 첨부 검증 조건을 모두 통과한 경우에만 삽입한다.

참조 이미지가 없는 경우에는 블록을 만들지 않는다.

### 16.1 참조 이미지가 있는 경우

```text
[Reference Images]
- Character reference image 1: [캐릭터 참조 이미지 1]
  Use this image to preserve the character's face, hairstyle, silhouette, outfit direction, color identity, and visual personality.

- Background reference image 1: [배경 참조 이미지 1]
  Use this image to preserve the environment structure, atmosphere, lighting direction, color tone, and spatial mood.
```

### 16.2 참조 이미지가 없는 경우

참조 이미지 블록을 삽입하지 않는다.

```text
Do not mention reference images if no valid reference image slot exists.
```

### 16.3 참조 이미지가 허용되지 않는 사용처

Midjourney, NovelAI, FLUX, SDXL, SD 1.5, Pony, Illustrious / IL, NoobAI, ZIT, 범용, 기타 사용처에서는 참조 이미지 블록을 만들지 않는다.

## 17. Category Knowledge Block

Category Knowledge Block은 선택된 카테고리의 핵심 해석 규칙을 전달한다.

이 블록은 카테고리별로 다르게 삽입한다.

예시는 다음과 같다.

```text
[Category Knowledge]
This category is not only about choosing a subject type.
The assistant must first understand what should be visually emphasized: the subject itself, its design sheet function, its environment, its narrative moment, or its production use.

Automatically consider:
- subject identity
- output purpose
- composition
- crop
- camera distance
- lighting
- color harmony
- mood
- background complexity
- text-in-image intent
- category-specific visual clarity
```

카테고리별 자동 고려 사항은 2.1~2.11 문서의 핵심을 요약해서 삽입한다.

예를 들어 지도 카테고리라면 공간 구조와 라벨 / 아이콘 / 그리드 여부를 자동 고려해야 한다.

효과 카테고리라면 발광, 밀도, 움직임, 발생 지점, 에너지 속성을 자동 고려해야 한다.

## 18. Consultation Decision Rule Block

이 블록은 채팅형 AI가 질문할지, 바로 최종 프롬프트를 출력할지 판단하게 한다.

```text
Before writing final prompts, evaluate whether the current structured brief is strong enough.

Ask follow-up questions only if the missing information would materially change the image.

Do not ask about every auto field.
Auto means the assistant may complete the design naturally.

Ask 1 to 4 concise, high-impact follow-up questions in Korean when needed.

If the brief is already strong enough, do not over-question.
Produce final prompt options immediately.
```

질문해야 하는 상황은 다음과 같다.

```text
Ask questions when:
- the main subject identity is unclear
- there are multiple subjects but their relationship is unclear
- the output purpose and layout conflict
- selected and none conditions conflict
- include and exclude requests conflict
- a required reference image was selected but not provided
- the category-critical information is too weak to produce a coherent result
```

질문하지 말아야 하는 상황은 다음과 같다.

```text
Do not ask questions when:
- auto can reasonably complete the missing detail
- the selected fields already define the image direction
- directInput contains enough specific visual intent
- the missing information is minor and does not materially change the image
```

## 19. Follow-up 질문 출력 규칙

정보가 부족할 때는 최종 영어 프롬프트를 출력하지 않는다.

질문은 한국어로 작성한다.

질문 수는 1~4개만 허용한다.

```text
부족한 정보가 있습니다. 아래 항목만 확인하면 바로 최종 프롬프트를 만들 수 있습니다.

1. 캐릭터의 구체적인 외형이나 종족을 정해둘까요, 아니면 밝고 친근한 마스코트형으로 자동 보완할까요?
2. 표정 / 포즈 시트에서 필요한 표정 개수나 포즈 개수가 있을까요?
3. 이미지 안에 텍스트는 넣지 않는 방향이 맞을까요?
```

질문은 반드시 시각 결과에 영향을 주는 것만 묻는다.

단순 취향 확인이나 사소한 선택지는 auto로 처리한다.

## 21. 최종 프롬프트 품질 규칙

Quality Rule Block은 모든 마스터 프롬프트에 들어간다.

```text
Quality rules:
- Keep the final prompt intentional, visual, and production-ready.
- Preserve every explicit user selection.
- Do not merge multiple subjects or requested objects into vague wording.
- Use concrete visual descriptions.
- Avoid vague adjectives unless they are supported by visible details.
- Avoid text inside the generated image unless the user clearly wants it.
- If text is requested, mention that exact text rendering may require post-editing.
- Do not imitate a living artist's exact style.
- Describe visual qualities instead of naming living artists.
- Keep the final prompt aligned with the selected target service.
- Do not mention unavailable reference images.
- Do not contradict none or exclusion conditions.
```

## 26. 구현 관점의 생성 규칙

실제 구현에서는 다음 순서로 마스터 프롬프트 문자열을 생성한다.

```text
1. baseRoleBlock을 삽입한다.
2. coreBehaviorBlock을 삽입한다.
3. usageTarget을 기준으로 targetServiceOutputRuleBlock을 선택한다.
4. modeInterpretationBlock을 삽입한다.
5. commonFieldBlock을 만든다.
6. category 값을 기준으로 categorySpecificationBlock을 만든다.
7. referenceImages가 사용 가능하고 유효하면 referenceImageBlock을 만든다.
8. category 값을 기준으로 categoryKnowledgeBlock을 만든다.
9. consultationDecisionRuleBlock을 삽입한다.
10. outputFormatBlock을 삽입한다.
11. qualityRuleBlock을 삽입한다.
```

삽입하지 않아야 하는 경우도 명확히 둔다.

```text
- 사용처가 비채팅형이면 referenceImageBlock을 만들지 않는다.
- 참조 이미지가 선택되지 않았으면 referenceImageBlock을 만들지 않는다.
- 선택되지 않은 카테고리의 전용 스키마는 만들지 않는다.
- 값이 none인 항목은 일반 입력값이 아니라 부정 조건으로 이동한다.
- auto 항목은 전부 질문 목록으로 바꾸지 않는다.
```

## 27. 8번 단계 결론

8번 단계의 결론은 다음과 같다.

```text
마스터 프롬프트는 구조화 입력값을 단순 나열하는 문서가 아니다.
```

```text
마스터 프롬프트는 채팅형 AI에게 상담 방식, 보완 방식, 질문 기준, 사용처별 최종 프롬프트 형식, 카테고리별 시각화 기준을 지시하는 상위 생성 지시문이다.
```

```text
웹앱은 공통 필드, 카테고리별 전용 필드, mode 처리 규칙, 참조 이미지 규칙, 사용처별 출력 규칙을 조립해 하나의 마스터 프롬프트를 만든다.
```

가장 중요한 원칙은 다음이다.

```text
auto는 질문 대상이 아니라 자연 보완 대상이다.
none은 부정 조건이다.
directInput은 사용자 의도 보존 대상이다.
selected는 명시 반영 대상이다.
참조 이미지는 허용된 사용처에서만 플레이스홀더로 삽입한다.
사용처별 출력 규칙은 최종 영어 프롬프트의 형식을 결정한다.
```
