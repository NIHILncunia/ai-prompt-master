# 5. 스킵 / 자동 / 직접 입력 처리 규칙 통합

## 1. 분석 목적

이번 문서는 창작 이미지 마스터 프롬프트 생성 웹앱에서 반복적으로 사용되는 입력 처리 방식을 통합하기 위한 기준 문서다.

2.1부터 2.11까지의 모든 카테고리에는 선택지, 자동 처리, 직접 입력, 없음 처리 같은 입력 방식이 반복적으로 등장한다.

이 규칙을 통일하지 않으면 같은 `스킵`이라도 어떤 화면에서는 무시로 처리되고, 어떤 화면에서는 자동 보완으로 처리되는 문제가 생길 수 있다.

따라서 본 문서에서는 전체 웹앱에서 사용할 입력 처리 방식을 하나의 기준으로 정리한다.

---

## 2. 핵심 결론

이 프로젝트에서 `스킵`은 별도의 독립 모드로 보지 않는다.

```text
스킵 = 자동 / 맡기기
```

사용자가 어떤 세부 항목을 스킵한다는 것은 해당 항목을 완전히 무시한다는 뜻이 아니다.

이 프로젝트에서는 스킵을 **채팅형 AI가 앞선 선택값과 전체 맥락을 보고 자연스럽게 보완하도록 맡기는 것**으로 처리한다.

따라서 내부 데이터 구조에는 `skip` mode를 만들지 않는다.

UI에서 `스킵`이라는 표현을 보여주더라도 내부 저장값은 `auto`로 저장한다.

---

## 3. 최종 처리 모드

최종 처리 모드는 다음 4개로 통일한다.

```text
1. selected
2. auto
3. directInput
4. none
```

화면 표시명과 내부 저장값은 다음처럼 대응한다.

```text
selected
→ 선택

auto
→ 스킵 / 자동 / 맡기기

directInput
→ 직접 입력

none
→ 없음
```

즉, 사용자에게는 `스킵`, `자동`, `맡기기`를 상황에 따라 다르게 보여줄 수 있지만, 내부적으로는 모두 `auto`로 처리한다.

---

## 4. selected

### 의미

`selected`는 사용자가 웹앱이 제공하는 선택지 중 하나 또는 여러 개를 직접 고른 상태다.

예시는 다음과 같다.

```text
장르 / 세계관: 다크 판타지
캐릭터 나이대: 청년
몬스터 크기: 거대
아이템 유형: 검
지도 유형: 배틀맵
효과 유형: 검은 안개
```

### 처리 규칙

```text
- 선택된 값은 마스터 프롬프트에 명시적으로 반영한다.
- 선택된 값은 auto보다 우선한다.
- 선택된 값이 directInput, none, 제외 요청과 충돌하면 더 높은 우선순위의 지시를 따른다.
```

### 예시

```text
입력:
카테고리: 캐릭터 / 인물
나이대: 청년
체형: 날렵한 체형
분위기: 차가운 인상

처리:
최종 마스터 프롬프트에는 청년, 날렵한 체형, 차가운 인상이 명시되어야 한다.
```

---

## 5. auto

### 의미

`auto`는 사용자가 해당 항목을 직접 지정하지 않고, 채팅형 AI가 전체 맥락에 맞춰 보완하도록 맡기는 상태다.

이 프로젝트에서는 다음 표현을 모두 `auto`로 처리한다.

```text
- 스킵
- 자동
- 자동 / 맡기기
- 맡기기
```

`auto`는 단순한 빈값이 아니다.

해당 항목을 앞선 입력값에 맞춰 자연스럽게 완성하도록 허용하는 값이다.

### 처리 규칙

```text
- auto 항목은 채팅형 AI가 카테고리, 장르, 중심 대상, 사용 목적, 분위기, 레이아웃을 기준으로 적절히 보완한다.
- auto 보완은 selected, directInput, none, 포함 요청, 제외 요청을 침범하면 안 된다.
- auto 보완은 카테고리 정체성을 유지해야 한다.
- UI에서 스킵을 눌러도 내부 mode는 auto로 저장한다.
```

### 예시

```text
입력:
날개: 스킵

저장:
mode: auto

처리:
캐릭터 콘셉트상 날개가 필요하면 AI가 넣을 수 있고, 필요 없으면 넣지 않는다.
```

```text
입력:
색상: 자동 / 맡기기

저장:
mode: auto

처리:
장르, 대상, 분위기에 어울리는 색상을 AI가 보완한다.
```

---

## 6. directInput

### 의미

`directInput`은 사용자가 자유 입력한 내용을 직접 반영하는 상태다.

직접 입력은 일반 선택값보다 우선한다.

### 처리 규칙

```text
- 사용자가 입력한 의미를 최대한 보존한다.
- 고유명사, 세계관 용어, 캐릭터명, 지명, 조직명, 기술명, 마법명은 임의로 바꾸지 않는다.
- 한국어 직접 입력은 최종 영문 프롬프트 생성 단계에서 의미를 영어로 옮기되, 고유명사는 유지한다.
- selected와 충돌하면 directInput을 우선한다.
- 제외 요청과 충돌하면 제외 요청을 우선한다.
```

### 예시

```text
입력:
룩스테라의 앙그라의 안개처럼 검고 침식성이 있는 안개

처리:
`룩스테라`, `앙그라의 안개`라는 고유명사는 유지한다.
검고 침식성이 있는 안개라는 의미를 최종 프롬프트에 반영한다.
```

---

## 7. none

### 의미

`none`은 해당 요소가 존재하지 않는다고 명시하는 상태다.

`none`은 `auto`와 완전히 다르다.

```text
auto
- 사용자가 직접 정하지 않는다.
- AI가 필요 여부를 판단한다.
- 들어갈 수도 있고, 들어가지 않을 수도 있다.

none
- 해당 요소가 없어야 한다.
- AI가 임의로 추가하면 안 된다.
- 필요하면 제외 조건으로 변환한다.
```

### 처리 규칙

```text
- none은 마스터 프롬프트에 명시적으로 반영한다.
- none은 필요에 따라 제외 요청으로 변환할 수 있다.
- none은 auto보다 우선한다.
- none이 설정된 요소는 채팅형 AI가 임의로 추가하면 안 된다.
```

### 예시

```text
날개: auto
→ 날개 여부를 AI가 캐릭터 콘셉트에 맞게 판단한다.

날개: none
→ 날개가 없어야 한다.

배경: auto
→ 적절한 배경을 AI가 보완한다.

배경: none
→ 배경 없는 이미지로 처리한다.

텍스트: auto
→ 카테고리와 결과물 유형에 따라 AI가 텍스트 여부를 판단한다.

텍스트: none
→ 글자나 라벨을 넣지 않는다.
```

---

## 8. 가장 중요한 구분

이 규칙에서 가장 중요한 구분은 다음이다.

```text
스킵 = auto
없음 = none
```

스킵은 자동 보완이고, 없음은 명시적 부정 조건이다.

```text
날개: 스킵
→ mode: auto
→ 날개가 필요하면 AI가 넣고, 필요 없으면 넣지 않는다.

날개: 없음
→ mode: none
→ 날개가 없어야 한다.
```

```text
텍스트: 스킵
→ mode: auto
→ 카테고리와 결과물 유형에 따라 AI가 판단한다.

텍스트: 없음
→ mode: none
→ 글자나 라벨을 넣지 않는다.
```

---

## 9. 처리 우선순위

마스터 프롬프트 생성 시 처리 우선순위는 다음과 같이 둔다.

```text
1. 제외 요청
2. none
3. directInput
4. 포함 요청
5. selected
6. auto
```

### 우선순위 해석

```text
제외 요청
- 사용자가 명시적으로 빼라고 한 조건이다.
- 가장 높은 우선순위를 가진다.

none
- 특정 요소가 없어야 한다는 명시 조건이다.
- auto 보완보다 우선한다.

directInput
- 사용자가 직접 입력한 세부 의도다.
- selected보다 우선한다.

포함 요청
- 반드시 포함해야 하는 조건이다.
- 일반 selected보다 우선한다.

selected
- 사용자가 선택지에서 고른 구조화된 조건이다.

auto
- 앞선 모든 조건을 침범하지 않는 범위에서 AI가 보완한다.
```

### 충돌 예시

```text
선택:
날개 있음

없음:
날개 없음

처리:
none이 우선하므로 날개 없음으로 처리한다.
```

```text
선택:
신성한 후광

직접 입력:
빛은 금색이 아니라 창백한 청백색

처리:
후광의 성격은 유지하되 색상은 직접 입력을 우선한다.
```

```text
선택:
텍스트 포함 로고

제외 요청:
글자 없음

처리:
제외 요청이 우선하므로 글자 없는 상징형 로고로 재해석한다.
```

## 10. 내부 데이터 구조

선택값은 다음처럼 저장한다.

```json
{
  "mode": "selected",
  "value": "다크 판타지"
}
```

자동 / 스킵 / 맡기기는 다음처럼 저장한다.

```json
{
  "mode": "auto",
  "value": null
}
```

직접 입력은 다음처럼 저장한다.

```json
{
  "mode": "directInput",
  "value": "룩스테라의 앙그라의 안개처럼 검고 침식성이 있는 안개"
}
```

없음은 다음처럼 저장한다.

```json
{
  "mode": "none",
  "value": null
}
```

다중 선택은 다음처럼 저장할 수 있다.

```json
{
  "mode": "selected",
  "values": ["룬 문양", "금속 장식", "보석 장식"]
}
```

중요한 점은 다음이다.

```text
skip mode는 만들지 않는다.
스킵은 auto로 저장한다.
```

## 11. UI 처리 기준

UI에서는 사용자 편의를 위해 다음 표현을 제공할 수 있다.

```text
- 선택
- 스킵
- 자동 / 맡기기
- 직접 입력
- 없음
```

하지만 내부적으로는 다음처럼 변환한다.

```text
선택
→ selected

스킵
→ auto

자동 / 맡기기
→ auto

직접 입력
→ directInput

없음
→ none
```

즉, UI 표현은 사용자 편의를 위한 것이고, 데이터 저장 구조는 단순하게 유지한다.

---

## 12. 필드별 권장 처리

필수 상위 필드는 `none`을 허용하지 않는다.

```text
none을 허용하지 않는 필드:
- 사용처
- 카테고리
- 중심 대상 유형
- 결과물 유형
```

세부 선택 필드는 `auto`를 기본값으로 둘 수 있다.

```text
auto 기본값이 적절한 필드:
- 세부 외형
- 색상
- 장식
- 분위기
- 조명
- 세부 배경
- 효과 세부값
```

부재 자체가 중요한 필드는 `none`을 제공한다.

```text
none이 필요한 필드:
- 날개
- 뿔
- 꼬리
- 문신
- 배경
- 텍스트
- 라벨
- 아이콘
- 프레임
- 격자
- 무기
- 손상
- 오염
```

## 13. 카테고리별 적용 예시

## 2.1 캐릭터 / 인물

```text
날개: 스킵
→ mode: auto
→ 캐릭터 콘셉트에 따라 AI가 판단한다.

날개: 없음
→ mode: none
→ 날개 없음으로 명시한다.
```

## 2.2 몬스터 / 크리처

```text
표피: 스킵
→ mode: auto
→ 크리처 콘셉트에 맞는 표피를 AI가 보완한다.

촉수: 없음
→ mode: none
→ 촉수를 넣지 않는다.
```

## 2.3 풍경화 / 배경 / 장소 / 세계관

```text
날씨: 스킵
→ mode: auto
→ 장소와 분위기에 맞는 날씨를 AI가 보완한다.

인공 구조물: 없음
→ mode: none
→ 자연 경관 중심으로 처리한다.
```

## 2.6 아이템 / 무기 / 유물 / 소품

```text
마법 효과: 스킵
→ mode: auto
→ 아이템 성격에 맞으면 은은한 효과를 보완할 수 있다.

마법 효과: 없음
→ mode: none
→ 발광, 오라, 마법 입자 없음으로 처리한다.
```

## 2.9 상징 / 문장 / 엠블럼 / 로고

```text
텍스트: 없음
→ mode: none
→ 글자 없는 상징으로 처리한다.

장식 수준: 스킵
→ mode: auto
→ 대표 대상의 위상에 맞춰 장식 수준을 보완한다.
```

## 2.10 지도 / 맵 / 배틀맵

```text
라벨: 없음
→ mode: none
→ 지도에 글자 없음으로 처리한다.

격자: 스킵
→ mode: auto
→ 배틀맵이면 격자 사용 여부를 AI가 판단한다.
```

## 2.11 개념 / 현상 / 효과

```text
발광: 스킵
→ mode: auto
→ 효과 속성에 맞춰 발광 정도를 AI가 보완한다.

배경: 없음
→ mode: none
→ 효과 단독 소재처럼 처리한다.
```

## 14. 마스터 프롬프트 생성 시 처리 방식

마스터 프롬프트를 생성할 때 mode별 처리는 다음과 같다.

```text
selected
- 선택값을 명시 조건으로 반영한다.

auto
- 채팅형 AI가 앞선 입력값을 바탕으로 자연스럽게 보완하도록 지시한다.

directInput
- 사용자 입력을 우선 반영한다.
- 고유명사는 유지한다.

none
- 해당 요소가 없음을 명시한다.
- 필요하면 제외 조건으로 변환한다.
```

예시는 다음과 같다.

```text
field: wings
mode: auto
→ 캐릭터 콘셉트에 어울릴 경우 날개 여부를 AI가 결정하도록 한다.

field: wings
mode: none
→ 캐릭터에게 날개가 없어야 한다고 명시한다.

field: wings
mode: directInput
value: 검은 깃털이 듬성듬성 빠진 타락천사형 날개
→ 해당 표현을 직접 반영한다.
```

## 15. 오류 방지 규칙

다음 상황은 UI 또는 생성 로직에서 방지하는 것이 좋다.

```text
카테고리: none
→ 허용하지 않는다.

사용처: none
→ 허용하지 않는다.

사용처: auto
→ 가능하면 허용하지 않는다.
→ 대신 모르겠음 / 범용을 제공한다.

중심 대상 유형: none
→ 허용하지 않는다.

스킵 mode 저장
→ 허용하지 않는다.
→ 반드시 auto로 변환한다.

동일 필드에 selected와 none 동시 적용
→ 허용하지 않는다.

색상: none
→ 일반적으로 허용하지 않는다.
→ 대신 auto 또는 directInput을 사용한다.

텍스트: none
→ 허용한다.
→ 기본값으로 권장할 수 있다.
```

## 16. 최종 결론

5번 단계의 최종 결론은 다음과 같다.

```text
내부 mode는 4개만 사용한다.

selected
auto
directInput
none
```

```text
스킵은 auto로 처리한다.
자동 / 맡기기도 auto로 처리한다.
skip mode는 만들지 않는다.
```

```text
auto는 AI 보완 허용이다.
none은 명시적 부정 조건이다.
directInput은 사용자 의도 우선이다.
selected는 구조화된 명시 조건이다.
```

가장 짧게 정리하면 다음 한 문장이다.

```text
스킵은 별도 상태가 아니라 auto로 처리하고, 없음만 none으로 분리한다.
```
