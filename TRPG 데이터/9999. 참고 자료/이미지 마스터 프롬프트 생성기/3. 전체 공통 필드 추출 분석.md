# 3. 전체 공통 필드 추출 분석

## 1. 분석 목적

이번 단계의 목적은 2.1부터 2.11까지의 개별 카테고리 설계를 하나의 웹앱 입력 구조로 묶기 위해, 모든 카테고리에서 반복되는 공통 필드를 추출하는 것이다.

이 단계에서는 아직 JSON 구조를 확정하지 않는다.  
먼저 모든 카테고리가 공유할 수 있는 상위 입력 체계를 정리하고, 이후 4번 단계에서 카테고리별 전용 필드를 분리한다.

---

## 2. 전체 카테고리에서 반복되는 기본 흐름

기존 2.1~2.11 문서를 보면 대부분 다음 흐름을 공유한다.

```text
1. 카테고리
2. 장르 / 세계관 또는 양식
3. 중심 대상 / 유형 / 결과물 방향
4. 상세 설계
5. 배경 / 분위기 / 조명 / 연출
6. 레이아웃 / 예상 결과물
```

다만 카테고리에 따라 2번의 명칭이 달라진다.

```text
캐릭터 / 몬스터 / 장소 / 장면 / 아이템 / 효과
→ 장르 / 세계관

건물 / 구조물
→ 문화권 / 양식 / 세계관

의상 / 장비
→ 의복 세계 / 착용 실루엣

메카 / 탈것 / 기계
→ 세계관 / 기술 양식

지도 / 맵 / 배틀맵
→ 지도 용도 / 범위
```

따라서 웹앱의 내부 공통 필드명은 `genreContext` 또는 `worldContext`처럼 넓게 잡고, 화면 표시명만 카테고리에 따라 바꾸는 방식이 적절하다.

---

## 3. 공통 필드 1차 추출

전체 카테고리에 공통으로 둘 수 있는 필드는 다음과 같다.

```text
공통 필드

1. category
2. usageTarget
3. worldContext
4. mainSubjectType
5. outputPurpose
6. detailDesign
7. styleDirection
8. mood
9. backgroundSetting
10. layout
11. referenceImages
12. textPolicy
13. includeRequests
14. excludeRequests
15. additionalRequests
16. automationPolicy
```

이 중 `category`, `usageTarget`, `mainSubjectType`, `outputPurpose`는 마스터 프롬프트 생성의 뼈대가 된다.

`detailDesign`, `styleDirection`, `mood`, `backgroundSetting`, `layout`은 이미지의 실제 내용을 구성한다.

`referenceImages`, `textPolicy`, `includeRequests`, `excludeRequests`, `additionalRequests`, `automationPolicy`는 모든 카테고리에서 공통 처리 규칙으로 묶는 것이 좋다.

---

## 4. category

`category`는 사용자가 2.1~2.11 중 어떤 창작 이미지 카테고리를 선택했는지 저장하는 필드다.

```text
category

- character_person
- monster_creature
- landscape_background_place_world
- building_architecture_structure
- scene_narrative_illustration
- item_weapon_artifact_prop
- costume_equipment_design
- mecha_vehicle_machine
- symbol_emblem_logo
- map_battlemap
- concept_phenomenon_effect
```

화면 표시명은 한글 그대로 유지한다.

```text
2.1 캐릭터 / 인물
2.2 몬스터 / 크리처
2.3 풍경화 / 배경 / 장소 / 세계관
2.4 건물 / 건축물 / 구조물
2.5 장면 / 서사 일러스트
2.6 아이템 / 무기 / 유물 / 소품
2.7 의상 / 장비 디자인
2.8 메카 / 탈것 / 기계
2.9 상징 / 문장 / 엠블럼 / 로고
2.10 지도 / 맵 / 배틀맵
2.11 개념 / 현상 / 효과
```

이 필드는 모든 후속 필드의 조건 분기 기준이 된다.

---

## 5. usageTarget

`usageTarget`은 1단계에서 선택한 사용처를 저장하는 필드다.

```text
usageTarget

- GPT / ChatGPT 이미지 생성
- Gemini / Imagen
- Grok
- Midjourney
- NovelAI
- FLUX
- SDXL
- SD 1.5
- Pony
- Illustrious / IL
- NoobAI
- Z-Image-Turbo / ZIT
- 모르겠음 / 범용
- 기타 / 직접 입력
```

이 필드는 이미지 내용 자체보다 **프롬프트 출력 양식**에 영향을 준다.

따라서 카테고리 내부 필드로 넣기보다는 전체 최상위 필드로 두는 것이 맞다.

---

## 6. worldContext

`worldContext`는 장르, 세계관, 문화권, 기술 양식, 미학권을 통합하는 공통 필드다.

기존 문서에서는 카테고리마다 다음처럼 다르게 표현된다.

```text
캐릭터
- 장르 / 세계관

몬스터
- 장르 / 세계관

장소
- 장르 / 세계관

건물
- 문화권 / 양식 / 세계관

의상
- 의복 세계 / 착용 실루엣

메카
- 세계관 / 기술 양식

효과
- 장르 / 세계관
```

내부 공통 필드는 `worldContext`로 통합하고, 하위에 카테고리별 표시명을 붙이는 것이 좋다.

```text
worldContext

- genre
- subGenre
- cultureStyle
- technologyStyle
- aestheticDirection
- directInput
- auto
```

예를 들어 메카 카테고리에서는 `technologyStyle`이 중요하고, 건축 카테고리에서는 `cultureStyle`이 중요하다.

---

## 7. mainSubjectType

`mainSubjectType`은 해당 이미지에서 무엇을 만들 것인지 정하는 필드다.

이 필드는 모든 카테고리에 존재하지만, 카테고리별 의미가 다르다.

```text
캐릭터
- 중심 인물 유형

몬스터
- 크리처 유형

장소
- 장소 유형

건물
- 중심 대상 유형

장면
- 장면 유형 / 핵심 사건

아이템
- 아이템 유형

의상
- 의상 부위 / 계열

메카
- 대상 유형 / 운용 방식

상징
- 대표 대상 / 결과물 유형

지도
- 지도 유형 / 범위

효과
- 현상 유형
```

따라서 내부 구조는 다음처럼 잡는 것이 안정적이다.

```text
mainSubjectType

- primaryType
- secondaryType
- detailType
- directInput
- auto
```

예를 들어 2.11에서는 다음처럼 들어간다.

```text
primaryType: 원소 현상
secondaryType: 번개
detailType: 방사형 전격 파동
```

2.10에서는 다음처럼 들어간다.

```text
primaryType: 배틀맵
secondaryType: 던전 내부
detailType: 보스전용 원형 광장
```

---

## 8. outputPurpose

`outputPurpose`는 최종 이미지가 어떤 형식으로 쓰일지를 정하는 필드다.

아이템, 의상, 메카, 상징, 지도, 효과 문서에서 특히 중요하게 등장한다.

```text
outputPurpose

- 컨셉아트
- 설정화
- 전신 디자인
- 레퍼런스 시트
- 아이콘
- 인벤토리 아이콘
- 카드형 이미지
- 로고 / 엠블럼
- 지도 이미지
- 배틀맵
- VFX 디자인 시트
- 장면 일러스트
- 배경 일러스트
- 직접 입력
- 자동 / 맡기기
```

이 필드는 `layout`과 연결된다.

예를 들어 `아이콘`을 선택하면 정사각 구도와 단순 배경이 우선된다.

`레퍼런스 시트`를 선택하면 다중 뷰, 정면/후면, 디자인 정보 배치가 필요하다.

---

## 9. detailDesign

`detailDesign`은 카테고리별 상세 설계값을 담는 공통 컨테이너다.

다만 이 필드의 내부 구조는 카테고리마다 완전히 다르다.

```text
detailDesign

캐릭터
- 외형, 나이대, 체형, 피부, 머리, 눈, 특징 요소

몬스터
- 크기, 신체 구조, 표피, 공격 방식, 생태

장소
- 공간 구조, 자연 요소, 인공 요소, 랜드마크

건물
- 규모, 양식, 재질, 기능, 구조

장면
- 등장 주체, 행동, 관계, 감정선, 사건

아이템
- 형태, 재질, 기능, 장식, 희귀도

의상
- 부위, 실루엣, 소재, 색상, 장식, 기능

메카
- 구조, 동력, 이동 방식, 조종 방식, 무장

상징
- 대표 대상, 모티프, 구성 요소, 텍스트 여부

지도
- 범위, 지형, 연결 구조, 시점, 정보 표현

효과
- 형태, 움직임, 발광, 밀도, 속성, 주변 영향
```

즉 `detailDesign`은 공통 필드이지만, 내부는 카테고리별 스키마로 분기해야 한다.

---

## 10. styleDirection

`styleDirection`은 이미지의 화풍, 렌더링 방향, 시각적 표현법을 정하는 필드다.

모든 카테고리에 적용 가능하다.

```text
styleDirection

- 반실사풍
- 실사풍
- 회화풍
- 애니메이션풍
- 셀셰이딩
- 게임 일러스트풍
- 컨셉아트풍
- 카드 일러스트풍
- 아이콘풍
- 로고 디자인풍
- 지도 일러스트풍
- VFX 디자인풍
- 직접 입력
- 자동 / 맡기기
```

다만 사용처에 따라 이 필드의 표현 방식은 달라져야 한다.

예를 들어 Midjourney는 스타일 키워드 중심으로, SDXL이나 Pony 계열은 태그형 표현으로 변환될 수 있다.

---

## 11. mood

`mood`는 분위기, 감정, 긴장감, 위협감, 신성함, 장엄함 같은 인상 계열을 담는다.

문서마다 이름은 다르다.

```text
캐릭터
- 분위기

몬스터
- 분위기 / 위협감

장소
- 분위기 / 조명 / 환경 조건

건물
- 분위기 / 조명 / 환경 조건

장면
- 감정선 / 긴장감 / 분위기

효과
- 속성 / 영향 / 분위기
```

통합 필드는 `mood`로 잡되, 하위에 다음 값을 둘 수 있다.

```text
mood

- emotionalTone
- tensionLevel
- threatLevel
- sacredness
- darkness
- beauty
- mystery
- scaleImpression
- directInput
- auto
```

특히 2.5 장면과 2.11 효과는 감정적 인상이 중요하므로 `mood`의 비중이 높다.

---

## 12. backgroundSetting

`backgroundSetting`은 배경 유무, 장소, 무대, 환경 조건을 담는다.

모든 카테고리에 필요하지만 중심성은 다르다.

```text
중심 필드로 중요한 카테고리
- 2.3 풍경화 / 배경 / 장소 / 세계관
- 2.5 장면 / 서사 일러스트
- 2.10 지도 / 맵 / 배틀맵

보조 필드로 쓰이는 카테고리
- 2.1 캐릭터 / 인물
- 2.2 몬스터 / 크리처
- 2.4 건물 / 구조물
- 2.6 아이템
- 2.7 의상
- 2.8 메카
- 2.9 상징
- 2.11 효과
```

통합 구조는 다음이 적절하다.

```text
backgroundSetting

- none
- simpleBackground
- transparentLikeBackground
- naturalBackground
- indoorBackground
- urbanBackground
- battlefieldBackground
- abstractBackground
- referencedBackground
- directInput
- auto
```

아이콘, 로고, 효과 소재는 배경 없음이나 단색 배경을 우선한다.

장면, 장소, 지도는 배경이 사실상 핵심 설계값이다.

---

## 13. layout

`layout`은 최종 이미지의 구도와 결과물 형식을 정한다.

이 필드는 모든 카테고리에 필요하다.

```text
layout

- 정면 구도
- 측면 구도
- 3/4 구도
- 전신 구도
- 흉상 구도
- 클로즈업
- 와이드샷
- 탑뷰
- 아이소메트릭
- 중앙 단일 오브젝트
- 정사각 아이콘
- 가로형 컨셉아트
- 세로형 일러스트
- 레퍼런스 시트
- 턴어라운드
- 지도형 레이아웃
- 디자인 시트
- 직접 입력
- 자동 / 맡기기
```

2.10 지도는 탑뷰와 정보 표현이 중요하다.

2.7 의상은 마네킹 착용, 전신, 부위별 표현이 중요하다.

2.11 효과는 단일 효과, 아이콘형, VFX 시트형 레이아웃이 중요하다.

---

## 14. referenceImages

`referenceImages`는 참조 이미지 사용 규칙을 통합하는 필드다.

참조 이미지는 모든 카테고리에서 쓸 수 있지만, 해석 방식이 달라야 한다.

```text
referenceImages

- characterReference
- creatureReference
- backgroundReference
- structureReference
- itemReference
- costumeReference
- machineReference
- symbolReference
- mapReference
- effectReference
- styleReference
```

중요한 규칙은 다음과 같다.

```text
참조 이미지는 카테고리 중심 대상을 보조해야 한다.

캐릭터 카테고리에서 참조 이미지는 캐릭터 외형을 유지하는 데 쓴다.

장면 카테고리에서는 여러 캐릭터 레퍼런스와 배경 레퍼런스를 조합할 수 있어야 한다.

효과 카테고리에서는 참조 이미지의 대상 자체가 아니라 효과, 색상, 밀도, 움직임을 참고한다.

지도 카테고리에서는 참조 이미지의 지형 구조나 공간 구성을 우선 유지한다.
```

이 필드는 이후 별도 통합 규칙 문서에서 더 자세히 다뤄야 한다.

---

## 15. textPolicy

`textPolicy`는 텍스트, 라벨, 글자 표현 여부를 정하는 필드다.

특히 2.9 상징 / 로고, 2.10 지도, 2.11 효과 아이콘에서 중요하다.

```text
textPolicy

- 텍스트 없음
- 라벨 없음
- 간단한 라벨
- 제목 텍스트 포함
- 후편집 전제 텍스트 자리만 표시
- 지도 라벨 포함
- 아이콘 라벨 포함
- 직접 입력
- 자동 / 맡기기
```

기본값은 `텍스트 없음`이 적절하다.

이미지 생성 모델은 정확한 문자를 안정적으로 생성하지 못하므로, 텍스트는 후편집 전제로 다루는 것이 안전하다.

---

## 16. includeRequests

`includeRequests`는 사용자가 반드시 포함하고 싶은 요소를 담는 공통 필드다.

```text
includeRequests

- 반드시 포함할 대상
- 반드시 포함할 색상
- 반드시 포함할 분위기
- 반드시 포함할 구도
- 반드시 포함할 장식
- 반드시 포함할 세계관 요소
- 반드시 포함할 고유명사
```

이 필드는 모든 카테고리보다 우선순위가 높다.

단, 카테고리 정체성을 깨뜨리는 요청은 마스터 프롬프트 생성 단계에서 보조 요소로 재해석해야 한다.

---

## 17. excludeRequests

`excludeRequests`는 사용자가 제외하고 싶은 요소를 담는 공통 필드다.

```text
excludeRequests

- 제외할 대상
- 제외할 색상
- 제외할 장르 요소
- 제외할 스타일
- 제외할 배경
- 제외할 구도
- 제외할 텍스트
- 제외할 장식
```

예를 들어 지도 카테고리에서 `텍스트 없음`, `아이콘 없음`은 매우 중요한 제외 요청이다.

캐릭터 카테고리에서는 `현대 요소 없음`, `과도한 노출 없음`, `카툰풍 제외` 같은 조건이 들어갈 수 있다.

---

## 18. additionalRequests

`additionalRequests`는 기존 선택지로 표현하기 어려운 자유 입력 요청을 담는다.

```text
additionalRequests

- 추가 설명
- 세계관 고유 설정
- 캐릭터 고유명사
- 조직명
- 지역명
- 금지 조건
- 후편집 전제
- 특수한 이미지 사용 목적
```

이 필드는 사용자가 직접 입력한 내용을 최대한 보존해야 한다.

특히 창작 세계관 용어는 자동 번역하거나 일반화하지 않는 편이 좋다.

---

## 19. automationPolicy

`automationPolicy`는 스킵, 자동, 직접 입력의 처리 방식을 통합한다.

```text
automationPolicy

- skip
- auto
- directInput
- none
```

처리 기준은 다음과 같다.

```text
스킵
- 해당 필드를 마스터 프롬프트에 명시하지 않는다.

자동 / 맡기기
- 선택된 카테고리, 장르, 중심 대상에 맞춰 채팅형 AI가 보완한다.

직접 입력
- 사용자의 입력값을 가장 높은 우선순위로 반영한다.

없음
- 해당 요소가 존재하지 않음을 명시한다.
```

중요한 점은 `스킵`과 `없음`을 분리해야 한다는 것이다.

예를 들어 캐릭터의 날개 항목에서 `스킵`은 언급하지 않는 것이고, `없음`은 날개가 없다고 명시하는 것이다.

## 20. 공통 필드 우선순위

마스터 프롬프트 생성 시 필드 우선순위는 다음처럼 잡는 것이 좋다.

```text
1. usageTarget
2. category
3. mainSubjectType
4. outputPurpose
5. worldContext
6. detailDesign
7. styleDirection
8. mood
9. backgroundSetting
10. layout
11. referenceImages
12. textPolicy
13. includeRequests
14. excludeRequests
15. additionalRequests
16. automationPolicy
```

하지만 실제 충돌 해결 우선순위는 조금 다르다.

```text
충돌 해결 우선순위

1. 사용자가 직접 입력한 고유 요청
2. 제외 요청
3. 포함 요청
4. 카테고리 정체성
5. 사용처별 프롬프트 규칙
6. 세부 선택지
7. 자동 보완
```

예를 들어 사용자가 `텍스트 없음`을 제외 요청으로 넣었다면, 2.9 로고 카테고리라도 정확한 글자 생성을 강제하지 않아야 한다.

## 21. 공통 필드와 전용 필드의 경계

이번 3번 단계에서 확정할 것은 “공통 필드명”이다.

카테고리별 실제 세부 선택지는 4번 단계에서 전용 필드로 분리해야 한다.

```text
공통 필드로 둘 것
- category
- usageTarget
- worldContext
- mainSubjectType
- outputPurpose
- detailDesign
- styleDirection
- mood
- backgroundSetting
- layout
- referenceImages
- textPolicy
- includeRequests
- excludeRequests
- additionalRequests
- automationPolicy

카테고리별 전용 필드로 둘 것
- characterAppearance
- creatureAnatomy
- placeStructure
- architectureStructure
- sceneComposition
- itemSpecification
- costumeSpecification
- machineSpecification
- symbolSpecification
- mapSpecification
- effectSpecification
```

`detailDesign`은 공통 컨테이너이고, 그 내부에서 위 전용 필드로 갈라지는 구조가 적절하다.
