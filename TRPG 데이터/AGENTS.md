# TRPG 데이터 작업 지침

## 최우선 실행·저장·진행 정책

이 섹션은 전역 지침과 하위 기능 문서에 남아 있는 이전 파일 정책, `다음` 해석, 로컬·ZIP 제공 규칙과 충돌할 때 최우선으로 적용한다.

### 최신 정본과 프로젝트 에이전트 기준일

- 웹 GPT의 프로젝트 최상위 진입점은 Google Drive `TRPG 데이터` 루트의 프로젝트 에이전트다. 프로젝트 자체에 업로드된 별도 프로젝트 소스는 사용하지 않는다.
- 프로젝트 에이전트 파일명은 `PROJECT AGENTS YYYY MMDD.md` 형식을 사용한다. 예: `PROJECT AGENTS 2026 0911.md`.
- 작업을 시작할 때 `TRPG 데이터` 루트에서 위 형식과 정확히 일치하는 파일을 확인하고, 파일명의 `YYYY MMDD`를 `YYYY-MM-DD` 기준일로 해석한다. 여러 후보가 있으면 가장 최근의 유효한 날짜를 가진 파일을 최신 정본으로 선택한다.
- 날짜가 없는 `PROJECT AGENTS.md`, 오래된 로컬 사본, 캐시된 파일명·ID는 최신 정본을 대체하지 않는다. 날짜형 프로젝트 에이전트를 찾을 수 없거나 파일명 날짜를 유효하게 판정할 수 없으면 임의로 추정하지 않고 차단 사유를 보고한다.
- 프로젝트 에이전트를 읽은 직후, 기능 라우팅·분석·생성·수정 등 실질 작업을 시작하기 전에 `프로젝트 에이전트 기준일: YYYY-MM-DD (PROJECT AGENTS YYYY MMDD.md)` 형식으로 현재 적용 중인 지침의 시점을 명시한다.
- 프로젝트 에이전트를 갱신하는 날에는 같은 Drive 정본 파일의 이름을 해당 날짜로 갱신하고, 문서 내부의 정본 기준일도 같은 날짜로 맞춘다.
- 실행 규칙과 자료 구조는 이 최신 프로젝트 에이전트와 Google Drive의 현재 정본을 기준으로 한다.
- 캐시된 경로나 ID가 실제 Drive 구조와 다르면 실제 폴더·파일 조회 결과를 우선하고, 현재 구조에 맞춰 라우팅한다.

### 데이터 생성·수정의 즉시 Drive 반영

- 이미지, 토큰, 레퍼런스 시트, 풍경, 배틀맵, 지도, 아이콘, 세션 문서, 설정 문서, 룰북 인덱스, Highlight Card, 스탯블록, 아이템, 특성, 능력, 클래스, 인물 데이터와 같이 **지속 보관할 데이터**를 새로 생성하거나 수정하면, 생성·수정 직후 해당 정본 경로에 Drive 직접 생성·업로드·갱신을 먼저 시도한다. 이후 검수·확정으로 내용이 바뀌면 같은 정본 파일을 다시 갱신한다.
- 기존 정본 파일을 갱신하는 경우에는 원본 파일명과 Drive 파일 ID를 유지하는 교체 업로드를 우선한다. 신규 정본이면 기능별 기본 경로에 새 파일을 만든다.
- 실제 Drive 쓰기 결과를 확인하기 전에는 반영 완료라고 보고하지 않는다.

### 비데이터 결과의 업로드

- 준비 안내, 채팅 답변, 조회 결과, 검토 의견, 선택지, 작업 중간 설명처럼 지속 보관 데이터가 아닌 결과는 자동 업로드하지 않는다.
- 마스터가 업로드·저장·반영·교체를 요청하면, 해당 결과도 Drive 직접 업로드를 먼저 시도한다.

### Drive 업로드 실패 시 대체 산출물

- Drive 직접 생성·업로드·갱신이 도구 또는 권한 문제로 실패하면, 같은 상대 경로와 원본 파일명을 보존한 ZIP을 제공한다.
- ZIP은 Drive 직접 반영의 대체 수단이며 기본 산출물이 아니다.
- Drive 반영이 실패했을 때에는 실패 사실과 ZIP 제공 사실을 구분해 보고한다.

### `다음`의 전역 의미

- 마스터의 `다음`은 언제나 **직전에 제시된 현재 단계의 결과·판단·초안을 확정하고, 다음 정의된 프로세스로 즉시 진행하라**는 뜻이다.
- 확인서, 최종 프롬프트, 설계 골격, 장면 목록, 데이터 초안, 검수 결과처럼 확정 가능한 결과가 제시된 직후의 `다음`에는 추가 확인 질문을 하지 않는다.
- 이미지 확인서와 최종 영어 프롬프트가 제시된 뒤의 `다음`은 해당 생성 배치 승인으로 처리한다. 생성·검수 뒤의 `다음`은 생성 결과를 채택하고 다음 산출물 또는 다음 처리 단계로 진행한다.
- 아직 확정 대상으로 제시된 결과가 없는 상태에서의 `다음`도 현재 절차를 가능한 다음 필수 단계로 진행한다. 다만 대상명·파일 경로처럼 현재 자료만으로 안전하게 판정할 수 없는 필수 정보는 임의로 발명하지 않고, 확인 가능한 범위까지 진행한 뒤 정확한 차단 지점만 표시한다.
- 하위 문서의 `다음` 해석이 이 정책과 다르면 이 정책을 우선한다.

### 기능·점검 시작 전 안내와 승인

- 아직 진행 상태가 없는 새 기능 또는 점검 요청은 먼저 **라우팅과 절차 안내만** 수행한다. 첫 응답에는 선택된 기능·점검 범위, 목적과 대표 산출물, 주요 단계, 필요한 입력·선행 자료, 연결 기능을 요약하고 `시작할까요?`를 명시한다. 이 단계에서 생성·수정·업로드·검증 재현·교정을 시작하지 않는다.
- 이 규칙은 `준비`, `프로세스 점검`, 새로운 생성·분석·제작·정비 요청처럼 새 흐름을 여는 표현에 적용한다. 이미 진행 중인 흐름에서 직전 결과가 공개된 뒤의 `생성`, `수정`, `업로드`, `다음`에는 같은 시작 안내를 반복하지 않는다.
- `프로세스 점검.`처럼 대상 없이 요청하면 전역 라우팅·정본·Drive 저장·`다음`, 이미지 생성 모듈 내부 8개 기능, 로그 분석, 룰북, 설정, FVTT, 창작 지원, 세션 제작, 집필 데이터 체크, 복합 파이프라인의 전체 점검 흐름을 빠짐없이 나열한 뒤 전체 P0 점검 시작 여부를 묻는다.
- `프로세스 점검 <기능명·흐름명·UC ID>`처럼 대상을 지정하면 해당 흐름과 필요한 선행·후속 흐름을 안내한 뒤 그 범위의 점검 시작 여부를 묻는다.
- 시작 안내 뒤의 `시작`, `진행`, `다음`은 제시된 기본 범위 또는 선택 범위를 확정하고 점검·기능 절차를 시작하라는 승인이다. 이 승인 뒤에는 같은 시작 질문을 반복하지 않는다.


## 파일 형식 최우선 규칙

- 프로젝트에서 신규 생성·수정·갱신하는 모든 문서 파일은 Markdown 형식인 `.md`로 관리한다.
- Google Docs, Google Sheets, Google Slides 등 Google Workspace 네이티브 문서를 직접 생성하지 않는다.
- 표 형식의 데이터도 별도 스프레드시트를 만들지 않고 가능한 범위에서 Markdown 표 또는 Markdown 문서 내부 구조로 작성한다.
- Google Drive에 직접 반영할 때에는 로컬 `.md` 파일을 업로드하거나 기존 `.md` 파일의 원본 ID를 유지하여 갱신한다.
- 기존 네이티브 문서를 교체해야 할 때에는 동일 내용을 `.md`로 작성·검증한 뒤 혼동 방지를 위해 네이티브 문서를 제거한다.
- 사용자의 일회성 요청이 있더라도 프로젝트 산출물의 기본 형식은 `.md`를 유지하며, 다른 형식이 반드시 필요한 경우에만 별도 산출물로 취급한다.


## 문서 역할

이 문서는 `TRPG 데이터` 루트의 최상위 작업 진입점이다.

이 문서는 프로젝트 전체에서 공통으로 적용되는 작업 분류, 정본 경계, Google Drive 운용, 파일 산출물 정책, Superpowers 운용, 전역 갱신 범위를 정의한다. 기능별 세부 실행 규칙은 여기에서 복제하지 않으며 `TRPG 데이터/1. 프롬프트/AGENTS.md`와 각 기능 폴더의 `AGENTS.md`, `0. ... 마스터 프롬프트.md`를 따라 내려간다.

## 최우선 원칙

- 사용자의 현재 대화에서 가장 최근에 명시한 지시를 최우선으로 따른다.
- Google Drive를 웹 GPT의 영구 작업·저장 정본으로 사용한다. 사용자의 요청 또는 프로젝트 기능 규칙이 직접 반영을 요구하면 Google Drive에서 생성·업로드·갱신·교체한다. GitHub 쓰기는 사용자가 명시적으로 요청한 범위에서만 수행한다.
- 웹 GPT의 프로젝트 지침·프롬프트·데이터 정본은 Google Drive만 사용한다. 프로젝트 자체 업로드 소스를 진입점이나 보조 정본으로 가정하지 않는다.
- 웹 GPT에서 프로젝트 지침·프롬프트·데이터의 영구 변경을 요청받으면 **항상 Google Drive의 대응 정본을 수정한다.** `지침 수정`, `반영`, `저장`, `업로드`, `교체` 요청의 기본 쓰기 대상은 Google Drive다.
- 런타임 로컬 파일은 Drive 파일을 편집·변환·검증하기 위한 임시 작업본으로만 사용할 수 있으며, 로컬 사본 수정만으로 반영 완료라고 보고하지 않는다.
- 로컬 파일 또는 ZIP은 사용자가 별도로 요청했거나 Drive 직접 반영이 도구상 불가능한 경우의 대체 산출물로 사용한다.
- 기존 파일을 수정하여 제공할 때에는 사용자가 파일명 변경을 요청하지 않는 한 원본 파일명을 그대로 유지한다.
- 여러 파일을 제공할 때에는 실제 적용 경로를 보존한 ZIP을 기본으로 한다.
- ZIP 안에 다시 ZIP을 넣지 않는다. 단계별 패키지가 필요하면 내부 파일을 풀어 최종 적용 구조로 합쳐 제공한다.
- 사용자가 지정한 저장 위치와 목적을 임의로 변경하지 않는다.

## 작업 아카이브

- 완료되어 재적용할 필요가 없는 패치 ZIP·백업 ZIP·정비 산출물 ZIP은 `TRPG 데이터/작업 정비/정비 아카이브/`에 보관한다.
- 보관 전에는 적용 대상의 경로·파일 수·필요한 경우 SHA-256을 확인한다. 적용 완료가 확인되지 않은 패치는 아카이브로 이동하지 않는다.
- 아카이브는 보존용이며 활성 지침·실행·자동 추출·자동 재적용의 입력으로 사용하지 않는다.
- 보관 파일은 원본 파일명을 유지한다. 같은 이름의 파일이 이미 있으면 기존 파일을 덮어쓰지 않고, 유입 파일에 `yyyy-MM-dd-HHmm_` 접두를 붙여 구분한다.
- 아카이브 파일의 삭제·교체·재적용은 마스터의 명시적 지시가 있을 때만 수행한다.

## 작업 진입

요청을 받으면 먼저 작업 유형을 분류한다.

1. 이미지 생성 계열
2. 세션 운영·제작·로그 분석
3. 룰북·시스템 데이터 조회
4. 설정 조회·정비·문서 작업
5. Foundry VTT 관련 작업
6. 창작 지원 데이터 제작
7. 프로젝트 구조·지침·프롬프트 체계 정비
8. 기타 파일·데이터 작업

Codex에서는 TRPG 세션 운영, 룰북 데이터, 설정, 로그, 이미지 생성 준비, Foundry VTT 요청에 필요한 동기화된 로컬 Markdown을 직접 읽는다. Google Drive 커넥터와 `구글 드라이브에 접근을 시도합니다.` 문구를 사용하지 않는다.

그 뒤 요청 유형을 현재 라우팅 캐시로 판정하고, 캐시된 폴더 ID로 관련 기능 폴더를 직접 연다. 기능 번호와 폴더명은 개편될 수 있으므로 과거 기억만으로 새 경로를 추정하지 않되, 정상 작업마다 프롬프트 루트나 Drive 전체를 다시 검색하지 않는다.

## 엔터티 자산과 미분류

- 자산 정본은 `5. 신격`, `6. NPC`, `7. PC`, `8. 국가`, `9. 단체`, `10. 몬스터`, `11. 맵`, `12. 종족`, `13. 지역`, `14. 용종`, `15. 장소`, `18. 아이템`의 대상 폴더에 둔다.

- NPC·PC·몬스터·신격의 신규 정본 설정화와 초상화는 9:16, 토큰은 1:1을 사용한다. 지역·장소·아이템·기타 설정화는 16:9, 아이템 아이콘은 1:1을 사용한다. 국가·단체·종족은 1:1 엠블럼과 16:9 배너를 추가 자산으로 사용한다.

- 동일 대상의 서로 다른 시안은 `시안/`에 모두 보존하며 덮어쓰지 않는다. 완성형 VTT 토큰과 캐릭터 레퍼런스의 기능 고정 캔버스는 이 일반 비율 규칙의 예외다.

## 이미지 생성 계열 하드 게이트

다음은 이미지 생성 계열로 취급한다.

- 이미지 생성·수정
- 반실사 포트레이트

- 세션 하이라이트 이미지
- 풍경

- 월드 지도

이미지 생성 계열 요청은 즉시 `image_gen`을 호출하지 않는다.

1. `TRPG 데이터/1. 프롬프트/1. 이미지 생성 모듈` 확인
2. `1. 이미지 생성 모듈/공통/1. 이미지 생성 공통 승인 절차.md` 확인
3. `1. 이미지 생성 모듈/공통/6. 이미지 생성 프롬프트 점검 및 교정 지침.md` 확인
4. 해당 내부 기능의 마스터·실행 문서 확인
5. 필요한 설정·종족·레퍼런스 탐색
6. 한국어 요구사항 확인서와 최종 영어 프롬프트 초안 작성
7. 프롬프트 점검·자동 교정 후 통과본 공개
8. 사용자 승인 후 실행 문안 재확인과 생성

요구사항 확인서와 최종 영어 프롬프트가 공개된 직후 사용자가 `다음`이라고 응답하면 명시적 생성 승인으로 해석한다. 확인 절차 완료 전의 `다음`은 현재 절차의 다음 단계 진행으로만 처리하며, 생성 완료 후의 `다음`은 새 산출물 요청으로 보고 다시 확인 절차를 거친다.

사용자가 `프롬프트만`, `컨셉만`, `생성 전에 검토`라고 명시하면 실제 이미지를 생성하지 않는다.

별도 화풍 지정이 없는 새 포트레이트의 기본 스타일은 **일러스트 중심의 붓터치 반실사**다. 다만 사용자가 `애니 페인팅`을 명시하면 이 기본값을 사용하지 않고 정식 스타일 `애니 페인팅`을 적용한다.

정식 스타일은 스타일별 활성 앵커 구성이 서로 다를 수 있으며, 붓터치 반실사는 핵심 얼굴·나이 표현·전신·마감 4장, 애니 페인팅은 현재 핵심 얼굴·중립 전신·마감 3장을 사용한다. 실제 조합과 참조 예산 축소는 이미지 모듈의 정식 스타일 호출 규칙을 따른다.

정식 스타일은 선택 스타일의 고정 영어 그림체 블록과 공통 고정 영어 마감 블록을 결합한다. 구 `photorealistic 3D CGI`, `AAA CGI` 스타일 잠금은 현행 기준이 아니다.

캐릭터 레퍼런스 V1·V2와 세션 하이라이트는 제공 이미지가 있으면 별도 스타일 변경 지시가 없는 한 그 이미지의 그림체와 마감을 그대로 따른다. 정식 스타일 변경이 명시된 경우에만 제공 이미지를 디자인 기준, 정식 앵커를 스타일 전용 기준으로 분리한다. 스타일 앵커의 인물·의상·팔레트·포즈·카메라·배경·구성은 참조하지 않는다.

반실사 포트레이트의 기본 흐름은 다음과 같다.

`전신 9:16 → 전신 확정 → 확정 전신 기반 흉상 9:16 또는 완성형 VTT 토큰 1:1`

흉상은 독립 재설계가 아니라 확정 전신의 동일 인물·동일 디자인을 확대하여 계승한다.

## 이미지 생성 결과 저장

- **인물·NPC·PC·몬스터 이미지 작업의 기본 종료 지점은 생성이 아니라 Google Drive 저장이다.** 마스터가 저장 제외나 로컬 산출물만을 명시하지 않는 한, 생성·수정 → 검수/확정 → 최초 업로드 또는 교체 업로드까지 이어서 수행해야 완료로 본다.
- 인물 계열의 표준 이미지 세트는 `<액터>.webp` 전신, `<액터> 초상화.webp`, `<액터> 토큰.webp`의 **3종 세트**다. 마스터가 특정 산출물만 요청하거나 일부를 제외한 경우에만 범위를 축소한다. 각 이미지 생성 호출의 승인 상태는 기존 공통 승인 절차대로 서로 독립적으로 사용한다.
- 저장 분류는 설정상 역할을 우선한다. NPC는 `TRPG 데이터/6. NPC/<대상>/`, PC는 `TRPG 데이터/7. PC/<대상>/`, 몬스터는 `TRPG 데이터/10. 몬스터/<유형>/<대상>/`, 용종은 `TRPG 데이터/14. 용종/<유형>/<대상>/`에 저장한다. 외형만으로 NPC·몬스터 분류를 바꾸지 않는다.
- 신규 정본이 없으면 최초 업로드한다. 같은 액터의 기존 정본이 있으면 **기존 Drive 파일 ID를 유지한 교체 업로드**를 기본으로 한다. 이미지 작업 안에서 마스터가 결과를 `픽스`, `확정`, `사용`, 다음 파생 산출물 진행 등으로 채택한 경우 저장·교체를 위해 별도의 `업로드하자` 지시를 다시 요구하지 않는다.
- NPC/PC/몬스터 분류가 자료만으로 판정되지 않을 때에만 저장 위치를 확인하며, 외형만으로 임의 분류하지 않는다.
- 인물 외 자산도 대상이 확정되면 국가·단체·종족·지역·장소·아이템의 대상 폴더에 직접 저장한다. 대상이 미확정일 때만 `TRPG 데이터/16. 미분류/이미지 생성 결과/`를 사용한다.
- `TRPG 데이터/10. 몬스터/`의 최상위 분류는 `01. 기괴체 / 02. 야수 / 03. 천상체 / 04. 구조체 / 05. 천룡종 / 06. 정령 / 07. 요정 / 08. 악마 / 09. 거인 / 10. 인간형 / 11. 괴물류 / 12. 점액류 / 13. 식물 / 14. 언데드 / 15. 용종 / 16. 곤충류 / 커스텀`으로 고정한다.
- `10. 인간형`은 적성 인간형 전용이며 비적성 인간형은 `TRPG 데이터/6. NPC/`를 사용한다.
- `16. 곤충류`는 이미지 관리상 절지동물형 전체를 포함하며, 유형 미확정 대상은 `커스텀`에 둔다.
- 상세 몬스터 분류와 계층은 `TRPG 데이터/10. 몬스터/몬스터 이미지 분류 및 저장 지침.md`를 따른다.

## 설정 자료 운용

설정 요청에서는 `프로젝트 위그드라실`을 정본 진입점으로 사용한다.

- 룩스테라: `프로젝트 위그드라실/룩스테라`
- 엘드로스: `프로젝트 위그드라실/엘드로스`
- 공통 설정: `프로젝트 위그드라실/위그드라실`

현재 Drive 구조와 기억이 충돌하면 현재 Drive 구조를 우선한다.

설정 문서를 신규 작성·수정할 때에는 해당 시리즈의 `AGENTS.md`, 문서 작성 지침, 템플릿, 설정 정비 지침을 필요한 범위까지 확인한다.

## 룰북 자료 우선순위

- 룰북·규칙·스탯블록·주문·아이템 데이터 요청은 Google Drive의 `TRPG 데이터/0. 룰북` 자료를 반드시 검색해 확인한다. Codex CLI에서는 Git 로컬 작업 폴더의 해당 자료를 직접 검색한다.
- 먼저 `1. 프롬프트/4. 룰북 관련 요청 프롬프트/9999. D&D 룰북 소유 리스트.md`를 확인한 뒤, 요청 대상에 맞는 기본 룰북을 직접 훑는다. 기본 룰북은 `D&D 5e 2024 Player’s Handbook`, `D&D 5e 2024 Dungeon Master’s Guide`, `D&D 5e 2025 Monster Manual`이다.
- 몬스터·스탯블록은 `Monster Manual`, 플레이어 규칙·주문·장비는 `Player’s Handbook`, 판정·보상·운영 규칙은 `Dungeon Master’s Guide`를 우선 확인한다. 요청 범위가 둘 이상에 걸치거나 불명확하면 세 기본 룰북을 이 순서대로 확인한다.
- 로컬 룰북 자료가 존재하는 요청에는 웹검색, 검색 엔진, 외부 웹사이트, Google Drive 커넥터를 사용하지 않는다. 로컬 자료만으로 확인할 수 없으면 추정하거나 웹에서 보완하지 않고 확인 불가로 보고한다.

## Superpowers 운용

프로젝트의 구조 변경, 기능 추가·통합·재번호, 대규모 문서 정비, 실행 계획이 필요한 작업에는 적용 가능한 Superpowers 스킬을 우선 사용한다.

Superpowers 문서는 다음 체계에서 관리한다.

```text
TRPG 데이터/docs/superpowers/
├─ SUPERPOWERS WORK REGISTRY.md
├─ SUPERPOWERS DOCUMENT OPERATIONS.md
├─ specs/
├─ plans/
└─ reports/
```

공식 작업 상태는 `SUPERPOWERS WORK REGISTRY.md`를 정본으로 삼는다.

설계·실행 계획·검증 보고서 등 Superpowers 운영 문서는 프로젝트 규칙상 Drive 직접 관리 대상이다. 다만 현재 도구 또는 보안 정책상 직접 반영이 차단되면 적용되었다고 간주하지 않고, 동일 파일명과 경로를 보존한 로컬 산출물 또는 ZIP으로 제공한다. 실제 존재를 확인한 문서만 레지스트리에 기록한다.

모든 실질 작업은 사용자 요청 여부와 무관하게 Superpowers 적용 여부와 작업 문서 생성 필요성을 자동 판정한다. 판정 결과 문서화가 필요한 작업만 Superpowers 문서를 자동 작성한다. 장기·다단계 작업은 시작 즉시 레지스트리에 등록하고, 상태 변화마다 갱신하며, 완료 시 검증/완료 보고서와 레지스트리 완료 처리를 자동 수행한다.

작업 폴더 내부의 장기 작업은 `TRPG 데이터/작업 정비`에도 동시에 등록한다. `작업 정비`는 분석·진행·확정·미결·재개 지점을 추적하며, `docs/superpowers`는 설계·계획·검증·완료 이력을 추적한다. 상세 규칙은 `TRPG 데이터/작업 정비/작업 정비 운영 지침.md`를 따른다.

## 전역 지침 동기화

전역 라우팅·기능 번호·고정 루트·파일 정책·승인 절차·SESSION PROGRESS가 바뀌면 최소 다음 문서를 함께 점검한다.

- `TRPG 데이터/AGENTS.md`
- `TRPG 데이터/1. 프롬프트/AGENTS.md`
- `TRPG 데이터/1. 프롬프트/00. TRPG 세션 매니저 프로젝트 기본 지침.md`
- `TRPG 데이터/1. 프롬프트/0. TRPG 데이터 프롬프트 통합 마스터 프롬프트.md`

기능 자체가 변경되면 해당 기능 폴더의 다음 문서도 함께 점검한다.

- `AGENTS.md`
- `README.md`
- `0. ... 마스터 프롬프트.md`
- 영향을 받는 실행 문서·라이브러리·템플릿

## SESSION PROGRESS

프로젝트 내 작업의 현재 위치와 다음 진행 지점은 `TRPG 데이터/SESSION PROGRESS 운영 지침.md`를 따른다.

- 모든 응답의 본문 뒤 최하단에 `SESSION PROGRESS`를 표시한다. 단순 질의와 잡담도 대기형을 사용한다.
- `SESSION PROGRESS` 전체는 항상 코드블럭 안의 플레인 텍스트로 표시하고, 그 뒤에는 본문이나 새 제안을 덧붙이지 않는다.
- 활성형은 `작업`, `현재`, `단계`, `완료`, `미결`, `다음`을 사용하며, 일시 중단형·완료형·대기형은 정본 지침의 필드를 따른다.
- 모든 SESSION PROGRESS 필드의 값이 복수이면 쉼표 대신 순차 목록을 사용한다. `완료`에는 실제 완료 또는 사용자 확정 사항만 기록한다.
- `미결`에는 이전 단계에서 판단·검증·합의되지 않았거나 충돌·장애로 해결되지 않은 채 현재 단계로 넘어온 사항만 기록한다. 현재 단계의 검토·판단·예정 작업은 `현재`와 `다음`으로 표현하며, 미결이 없으면 `미결: 없음`으로 표기한다.
- 미완료 작업을 두고 주제가 바뀌면 중단 지점과 재개 지점을 보존하고, 진행 중이거나 재개할 작업이 없으면 대기형으로 축약한다.
- 이미지 승인 절차와 SESSION PROGRESS는 별개다. 이미지 생성 뒤 자가검수 통과 여부와 관계없이 결과 응답에는 SESSION PROGRESS를 표시한다.
- 사용자가 SESSION PROGRESS의 표시 생략을 명시하면 그 지시를 우선한다.

## 세션 설계·로그 분석·하이라이트 연동 데이터 모델

세션 제작·플레이 종료 로그·하이라이트의 장기 연동은 다음 데이터 모델을 사용한다.

- `8. 세션 제작`은 플레이 전 의도와 자산의 정본이다.
  - 설계 장면에는 번호·제목과 별도로 영구 `scene_uuid`를 부여한다.
  - 설계 맵에는 번호·제목과 별도로 영구 `map_uuid`를 부여한다.
  - `scene_uuid`와 `map_uuid`는 소문자 표준 UUID 값이며, 번호 변경·이름 변경에도 유지하는 내부 식별자다.
- `3. 로그 분석`은 원본 로그를 먼저 실제 플레이 흐름대로 분할해 `P01`, `P02` 형식의 실제 플레이 장면을 만들고, 그 뒤 세션 설계가 있으면 `scene_uuid` 장면과 `map_uuid` 맵에 대응한다.
  - 설계 대응 상태는 `matched / merged / split / skipped / unplanned / uncertain`을 사용한다.
  - 설계 맵 상태는 `confirmed / none / unavailable / unmapped / uncertain`을 사용한다.
  - 분석 문서에는 기본 세션 하이라이트 `H01`, `H02`를 포함하며 각 `Hxx`는 `Pxx`를 참조한다.
- `2. 로그 하이라이트 추출`은 두 모드를 가진다.
  - 독립 추출: 분석본이 필요 없거나 사용자가 하이라이트만 요구하면 원본 로그에서 직접 Highlight Card를 만든다.
  - 분석 연계 정밀화: 3번 분석본의 `Hxx → Pxx → scene_uuid → map_uuid` 연결을 따라 필요한 원본 로그 범위만 재검증해 완전한 Highlight Card로 확장한다.
- `1. 이미지 생성 모듈 내부 4. 세션 하이라이트 이미지 생성`은 Highlight Card를 소비한다. 설계 장면 ID, 설계 맵 ID, 실제 FVTT Scene ID를 서로 다른 값으로 취급한다.
- 세션 설계가 없더라도 3번은 `Pxx`와 `Hxx`를 산출한다. 이 경우 설계 대응과 설계 맵은 `unavailable`로 기록한다.
- 동일 데이터는 중복 복제하지 않는다. 기본 참조 흐름은 `Hxx → Pxx → scene_uuid → map_uuid`다.

## 플레이 완료 세션 설계 보존

플레이가 끝난 세션 설계는 역사적 `의도` 기록으로 취급한다. 8번 세션 제작의 `status: played`는 개별 장면이 실제 진행되었다는 뜻이 아니라 세션이 이미 플레이되어 설계가 동결되었다는 뜻이다. 실제로 어떤 설계 장면이 진행·통합·분할·생략되었는지는 3번 로그 분석이 기록한다.

## 공용 맵 카탈로그

- 모든 맵 문서·풍경·전술맵의 물리 정본은 `11. 맵` 공용 카탈로그다.
- 환경 폴더 아래에 문서와 자산을 함께 두며, 세션 폴더는 개별 맵 문서나 이미지 사본을 소유하지 않는다.
- `map_uuid`는 영구 참조값이고 `map_code`와 파일명은 변경할 수 있다. 세션·로그·하이라이트는 `map_uuid`만 참조한다.
- 공용 맵 이름에는 특정 지역명을 넣지 않으며, 공간 구조·논리 그리드·자산은 공용 맵 문서가, 장면별 사건·토큰·배치는 세션 장면 문서가 소유한다.
