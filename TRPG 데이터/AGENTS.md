# TRPG 데이터 작업 지침

## 파일 형식 최우선 규칙

- 프로젝트에서 신규 생성·수정·갱신하는 모든 문서 파일은 Markdown 형식인 `.md`로 관리한다.
- Google Docs, Google Sheets, Google Slides 등 Google Workspace 네이티브 문서를 직접 생성하지 않는다.
- 표 형식의 데이터도 별도 스프레드시트를 만들지 않고 가능한 범위에서 Markdown 표 또는 Markdown 문서 내부 구조로 작성한다.
- Google Drive에 직접 반영할 때에는 로컬 `.md` 파일을 업로드하거나 기존 `.md` 파일의 원본 ID를 유지하여 갱신한다.
- 기존 네이티브 문서를 교체해야 할 때에는 동일 내용을 `.md`로 작성·검증한 뒤 혼동 방지를 위해 네이티브 문서를 제거한다.
- 사용자의 일회성 요청이 있더라도 프로젝트 산출물의 기본 형식은 `.md`를 유지하며, 다른 형식이 반드시 필요한 경우에만 별도 산출물로 취급한다.


## 문서 역할

이 문서는 `TRPG 데이터` 루트의 최상위 작업 진입점이다.

이 문서는 프로젝트 전체에서 공통으로 적용되는 작업 분류, 정본 경계, Google Drive 운용, 파일 산출물 정책, Superpowers 운용, 전역 갱신 범위를 정의한다. 기능별 세부 실행 규칙은 여기에서 복제하지 않으며 `TRPG 데이터/1. 프롬프트/AGENTS.md`와 각 기능 폴더의 `AGENTS.md`, `0. ... 마스터 프롬프트.md`를 따라 내려간다.

## 최우선 원칙

- 사용자의 현재 대화에서 가장 최근에 명시한 지시를 최우선으로 따른다.
- Google Drive와 GitHub에 파일을 직접 생성·업로드·덮어쓰기·삭제·푸시하지 않는다. 단, 사용자가 해당 작업을 명시적으로 직접 요청했거나 Superpowers 운영 문서처럼 프로젝트 규칙상 Drive 직접 관리 대상으로 정의된 경우에는 해당 범위에서 수행할 수 있다.
- 일반 파일 산출물은 사용자가 직접 적용할 수 있도록 로컬 파일 또는 ZIP으로 제공한다.
- 기존 파일을 수정하여 제공할 때에는 사용자가 파일명 변경을 요청하지 않는 한 원본 파일명을 그대로 유지한다.
- 여러 파일을 제공할 때에는 실제 적용 경로를 보존한 ZIP을 기본으로 한다.
- ZIP 안에 다시 ZIP을 넣지 않는다. 단계별 패키지가 필요하면 내부 파일을 풀어 최종 적용 구조로 합쳐 제공한다.
- 사용자가 지정한 저장 위치와 목적을 임의로 변경하지 않는다.

## 작업 아카이브

- 완료되어 재적용할 필요가 없는 패치 ZIP·백업 ZIP·정비 산출물 ZIP은 `TRPG 데이터/작업 정비/정비 아카이브/`에 보관한다.
- 보관 전에는 적용 대상의 경로·파일 수·필요한 경우 SHA-256을 확인한다. 적용 완료가 확인되지 않은 패치는 아카이브로 이동하지 않는다.
- 아카이브는 보존용이며 활성 지침·실행·자동 추출·자동 재적용의 입력으로 사용하지 않는다.
- 보관 파일은 원본 파일명을 유지한다. 같은 이름의 파일이 이미 있으면 기존 파일을 덮어쓰지 않고, 유입 파일에 `yyyy-MM-dd-HHmm_` 접두를 붙여 구분한다.
- 아카이브 파일의 삭제·교체·재적용은 마스터의 명시적 지시가 있을 때만 수행한다.

## 작업 진입

요청을 받으면 먼저 작업 유형을 분류한다.

1. 이미지 생성 계열
2. 세션 운영·제작·로그 분석
3. 룰북·시스템 데이터 조회
4. 설정 조회·정비·문서 작업
5. Foundry VTT 관련 작업
6. 창작 지원 데이터 제작
7. 프로젝트 구조·지침·프롬프트 체계 정비
8. 기타 파일·데이터 작업

Codex에서는 TRPG 세션 운영, 룰북 데이터, 설정, 로그, 이미지 생성 준비, Foundry VTT 요청에 필요한 동기화된 로컬 Markdown을 직접 읽는다. Google Drive 커넥터와 `구글 드라이브에 접근을 시도합니다.` 문구를 사용하지 않는다.

그 뒤 요청 유형을 현재 라우팅 캐시로 판정하고, 캐시된 폴더 ID로 관련 기능 폴더를 직접 연다. 기능 번호와 폴더명은 개편될 수 있으므로 과거 기억만으로 새 경로를 추정하지 않되, 정상 작업마다 프롬프트 루트나 Drive 전체를 다시 검색하지 않는다.

## 컨셉 이미지와 설정화

- 설정화는 세션 진행과 직접 연관된 중요한 아이템·유물·장치·구조물 등의 디자인과 시각 설정을 확정하기 위한 이미지다.
- 모든 설정화는 가로형 16:9 또는 세로형 9:16 중 하나로 제작한다. 정사각형과 임의 비율은 설정화 산출물로 사용하지 않는다.
- 가로로 긴 무기·장치처럼 대상의 실루엣이 좌우로 펼쳐지는 경우에는 16:9를 우선하고, 세로형 대상이나 인물 중심 설정화는 9:16을 우선한다.
- 설정화의 최종 저장 루트는 `TRPG 데이터/16. 컨셉 이미지/`이며 Google Drive 폴더 ID는 `1ebjSGyH75RCgwV9W0pLqJoOzV5j-QKk-`다.
- `16. 컨셉 이미지`는 프롬프트 기능 번호가 아니라 장기 보관용 산출물 폴더다. 생성 요청은 1번 이미지 생성 모듈에서 목적에 맞는 기존 기능과 공통 승인 절차로 처리한다.
- 하위 폴더는 캠페인·세션·대상·아이템과 시안 수를 기준으로 작업 시점에 판단하여 만든다. 고정된 깊이나 분류 체계를 강제하지 않는다.
- 같은 대상의 여러 디자인 시안은 구분 가능한 파일명으로 모두 보존하며 기존 파일을 덮어쓰지 않는다. 최종 선택과 불필요한 시안 삭제는 마스터가 결정한다.
- 완성형 VTT 토큰 1:1, 캐릭터 레퍼런스 V2 고정 캔버스 등 별도의 기능 고정 계약을 가진 산출물은 이 설정화 비율 규칙의 적용 대상이 아니다.

- 라우팅 체계 자체를 점검·정비하는 작업인 경우

### 준비 호출 규칙

- `준비`, `준비.` 요청에서는 프롬프트 루트 ID `1PDa8TO0BdKrPaNWTfImJTcYoYY3gpj8N`를 직접 열어 직계 하위 구조만 확인한 뒤 활성 1~8 기능을 안내한다. Drive 전체 검색은 사용하지 않는다.
- 각 기능은 번호·명칭뿐 아니라 처리 대상과 대표 산출물 또는 연결 관계를 설명한다.
- 이미지 생성 모듈은 내부 활성 기능 `1·2·3·4·5·6·7·8`을 줄바꿈 불릿으로 나열하고, 5번 `캐릭터 레퍼런스 V2 생성`을 함께 안내한다. 요구사항 확인서·최종 영어 프롬프트 초안, 프롬프트 점검·자동 교정, 통과본 공개, 마스터 승인 순서의 공통 절차도 함께 안내한다.
- 비이미지 기능에는 이미지 승인 절차를 표시하지 않으며, 필요한 선행·후속 기능 관계만 짧게 설명한다.
- `준비 ?번`, `준비. ?번`은 캐시된 해당 기능 폴더 ID로 바로 진입해 처리 프로세스만 안내하며 생성·수정·외부 실행을 시작하지 않는다.
- `포트레이트 준비`, `포트레이트 준비.`는 1번 이미지 생성 모듈 내부 1번 `반실사 포트레이트`의 직접 준비 호출로 해석한다. 해당 기능의 처리 프로세스만 안내하며 생성·수정·외부 실행을 시작하지 않는다.
- `애니 페인팅 포트 준비`, `애니 페인팅 포트레이트 준비` 계열은 같은 내부 1번으로 직접 라우팅하고 선택 스타일을 정식 명칭 `애니 페인팅`으로 바인딩한다.
- 이미지 요청에서 사용자가 `애니 페인팅`을 화풍 지시로 명시하면 준비 호출 문구 여부와 관계없이 `애니 페인팅`을 선택한다. `애니 페인팅으로 전환`, `애니 페인팅 스타일`, `애니 페인팅으로 재생성`, `애니 페인팅으로 리파인`도 같은 의미로 처리한다.
- `애니 페인팅` 또는 `붓터치 반실사` 정식 스타일을 적용할 때에는 이미지 모듈 마스터의 `정식 스타일 시각 앵커 하드 게이트`를 반드시 통과하며, 실제 앵커 픽셀을 확인하기 전에는 최종 영어 프롬프트를 확정하지 않는다.
- 요구사항 확인서와 최종 영어 프롬프트 초안은 `1. 이미지 생성 모듈/공통/6. 이미지 생성 프롬프트 점검 및 교정 지침.md`의 P01~P10을 통과해야 한다. 실패한 문안은 공개·승인·생성하지 않고 정본을 다시 읽어 자동 교정한 뒤 처음부터 재검사한다.

## 이미지 생성 계열 하드 게이트

다음은 이미지 생성 계열로 취급한다.

- 이미지 생성·수정
- 반실사 포트레이트
- 배틀맵
- 캐릭터 레퍼런스
- 세션 하이라이트 이미지
- 풍경
- 게임 아이콘
- 월드 지도

이미지 생성 계열 요청은 즉시 `image_gen`을 호출하지 않는다.

1. `TRPG 데이터/1. 프롬프트/1. 이미지 생성 모듈` 확인
2. `1. 이미지 생성 모듈/공통/1. 이미지 생성 공통 승인 절차.md` 확인
3. `1. 이미지 생성 모듈/공통/6. 이미지 생성 프롬프트 점검 및 교정 지침.md` 확인
4. 해당 내부 기능의 마스터·실행 문서 확인
5. 필요한 설정·종족·레퍼런스 탐색
6. 한국어 요구사항 확인서와 최종 영어 프롬프트 초안 작성
7. 프롬프트 점검·자동 교정 후 통과본 공개
8. 사용자 승인 후 실행 문안 재확인과 생성

요구사항 확인서와 최종 영어 프롬프트가 공개된 직후 사용자가 `다음`이라고 응답하면 명시적 생성 승인으로 해석한다. 확인 절차 완료 전의 `다음`은 현재 절차의 다음 단계 진행으로만 처리하며, 생성 완료 후의 `다음`은 새 산출물 요청으로 보고 다시 확인 절차를 거친다.

사용자가 `프롬프트만`, `컨셉만`, `생성 전에 검토`라고 명시하면 실제 이미지를 생성하지 않는다.

별도 화풍 지정이 없는 새 포트레이트의 기본 스타일은 **일러스트 중심의 붓터치 반실사**다. 다만 사용자가 `애니 페인팅`을 명시하면 이 기본값을 사용하지 않고 정식 스타일 `애니 페인팅`을 적용한다.

정식 스타일은 스타일별 활성 앵커 구성이 서로 다를 수 있으며, 붓터치 반실사는 핵심 얼굴·나이 표현·전신·마감 4장, 애니 페인팅은 현재 핵심 얼굴·중립 전신·마감 3장을 사용한다. 실제 조합과 참조 예산 축소는 이미지 모듈의 정식 스타일 호출 규칙을 따른다.

정식 스타일은 선택 스타일의 고정 영어 그림체 블록과 공통 고정 영어 마감 블록을 결합한다. 구 `photorealistic 3D CGI`, `AAA CGI` 스타일 잠금은 현행 기준이 아니다.

캐릭터 레퍼런스 V1·V2와 세션 하이라이트는 제공 이미지가 있으면 별도 스타일 변경 지시가 없는 한 그 이미지의 그림체와 마감을 그대로 따른다. 정식 스타일 변경이 명시된 경우에만 제공 이미지를 디자인 기준, 정식 앵커를 스타일 전용 기준으로 분리한다. 스타일 앵커의 인물·의상·팔레트·포즈·카메라·배경·구성은 참조하지 않는다.

반실사 포트레이트의 기본 흐름은 다음과 같다.

`전신 9:16 → 전신 확정 → 확정 전신 기반 흉상 9:16 또는 완성형 VTT 토큰 1:1`

흉상은 독립 재설계가 아니라 확정 전신의 동일 인물·동일 디자인을 확대하여 계승한다.

## 이미지 생성 결과 저장

- 이미지 생성 결과는 로컬 `TRPG 데이터/15. 이미지 생성 결과/`를 공통 저장 루트로 사용한다.
- 단, 설정화는 공통 결과 루트를 사용하지 않고 `TRPG 데이터/16. 컨셉 이미지/`에 저장하며 16:9 가로형 또는 9:16 세로형으로만 제작한다.
- 단, 이미지 생성 모듈 내부 3번 캐릭터 레퍼런스와 내부 5번의 인간형 V2 시트는 공통 저장 루트에 저장하지 않고 `TRPG 데이터/3. 캐릭터 레퍼런스 이미지/`에 저장한다.
- 내부 5번의 몬스터형 V2 시트와 장기 관리 대상으로 확정된 몬스터 이미지·토큰·초상화는 `TRPG 데이터/10. 몬스터 이미지/`에 저장한다.
- 저장 전 산출물 유형에 맞는 하위 폴더를 확인하고, 없으면 새로 만든다. 기본 분류 예시는 `캐릭터`, `배틀맵`, `아이콘`, `아이템`, `풍경`, `세션 하이라이트`, `지도`다.
- 각 이미지 기능은 실제 산출물의 목적에 맞는 하위 폴더에 저장하며, 예시에 없는 유형은 목적이 명확한 새 하위 폴더를 만들어 분류한다.
- 같은 이름의 결과 파일이 이미 있으면 덮어쓰지 않고, 구분 가능한 버전 파일명으로 저장한다.
- 이미지 결과 저장은 동기화된 로컬 작업 폴더에서 수행한다. Google Drive 커넥터를 통해 직접 생성·업로드·이동하지 않는다.
- `TRPG 데이터/10. 몬스터 이미지/`의 최상위 분류는 `01. 기괴체 / 02. 야수 / 03. 천상체 / 04. 구조체 / 05. 천룡종 / 06. 정령 / 07. 요정 / 08. 악마 / 09. 거인 / 10. 인간형 / 11. 괴물류 / 12. 점액류 / 13. 식물 / 14. 언데드 / 15. 용종 / 16. 곤충류 / 커스텀`으로 고정한다.
- `10. 인간형`은 적성 인간형 전용이며 비적성 인간형은 `TRPG 데이터/6. NPC 이미지/`를 사용한다.
- `16. 곤충류`는 이미지 관리상 절지동물형 전체를 포함하며, 유형 미확정 대상은 `커스텀`에 둔다.
- 상세 분류와 계층은 `TRPG 데이터/10. 몬스터 이미지/몬스터 이미지 분류 및 저장 지침.md`를 따른다.

## 룰북 자료 우선순위

- 룰북·규칙·스탯블록·주문·아이템 데이터 요청은 Google Drive의 `TRPG 데이터/0. 룰북` 자료를 반드시 검색해 확인한다. Codex CLI에서는 Git 로컬 작업 폴더의 해당 자료를 직접 검색한다.
- 먼저 `1. 프롬프트/4. 룰북 관련 요청 프롬프트/9999. D&D 룰북 소유 리스트.md`를 확인한 뒤, 요청 대상에 맞는 기본 룰북을 직접 훑는다. 기본 룰북은 `D&D 5e 2024 Player’s Handbook`, `D&D 5e 2024 Dungeon Master’s Guide`, `D&D 5e 2025 Monster Manual`이다.
- 몬스터·스탯블록은 `Monster Manual`, 플레이어 규칙·주문·장비는 `Player’s Handbook`, 판정·보상·운영 규칙은 `Dungeon Master’s Guide`를 우선 확인한다. 요청 범위가 둘 이상에 걸치거나 불명확하면 세 기본 룰북을 이 순서대로 확인한다.
- 로컬 룰북 자료가 존재하는 요청에는 웹검색, 검색 엔진, 외부 웹사이트, Google Drive 커넥터를 사용하지 않는다. 로컬 자료만으로 확인할 수 없으면 추정하거나 웹에서 보완하지 않고 확인 불가로 보고한다.

## Superpowers 운용

프로젝트의 구조 변경, 기능 추가·통합·재번호, 대규모 문서 정비, 실행 계획이 필요한 작업에는 적용 가능한 Superpowers 스킬을 우선 사용한다.

Superpowers 문서는 다음 체계에서 관리한다.

```text
TRPG 데이터/docs/superpowers/
├─ SUPERPOWERS WORK REGISTRY.md
├─ SUPERPOWERS DOCUMENT OPERATIONS.md
├─ specs/
├─ plans/
└─ reports/
```

공식 작업 상태는 `SUPERPOWERS WORK REGISTRY.md`를 정본으로 삼는다.

설계·실행 계획·검증 보고서 등 Superpowers 운영 문서는 프로젝트 규칙상 Drive 직접 관리 대상이다. 다만 현재 도구 또는 보안 정책상 직접 반영이 차단되면 적용되었다고 간주하지 않고, 동일 파일명과 경로를 보존한 로컬 산출물 또는 ZIP으로 제공한다. 실제 존재를 확인한 문서만 레지스트리에 기록한다.

모든 실질 작업은 사용자 요청 여부와 무관하게 Superpowers 적용 여부와 작업 문서 생성 필요성을 자동 판정한다. 판정 결과 문서화가 필요한 작업만 Superpowers 문서를 자동 작성한다. 장기·다단계 작업은 시작 즉시 레지스트리에 등록하고, 상태 변화마다 갱신하며, 완료 시 검증/완료 보고서와 레지스트리 완료 처리를 자동 수행한다.

작업 폴더 내부의 장기 작업은 `TRPG 데이터/작업 정비`에도 동시에 등록한다. `작업 정비`는 분석·진행·확정·미결·재개 지점을 추적하며, `docs/superpowers`는 설계·계획·검증·완료 이력을 추적한다. 상세 규칙은 `TRPG 데이터/작업 정비/작업 정비 운영 지침.md`를 따른다.

## 전역 지침 동기화

전역 라우팅·기능 번호·고정 루트·파일 정책·승인 절차·SESSION PROGRESS가 바뀌면 최소 다음 문서를 함께 점검한다.

- `TRPG 데이터/AGENTS.md`
- `TRPG 데이터/1. 프롬프트/AGENTS.md`
- `TRPG 데이터/1. 프롬프트/00. TRPG 세션 매니저 프로젝트 기본 지침.md`
- `TRPG 데이터/1. 프롬프트/0. TRPG 데이터 프롬프트 통합 마스터 프롬프트.md`

기능 자체가 변경되면 해당 기능 폴더의 다음 문서도 함께 점검한다.

- `AGENTS.md`
- `README.md`
- `0. ... 마스터 프롬프트.md`
- 영향을 받는 실행 문서·라이브러리·템플릿

## SESSION PROGRESS

프로젝트 내 작업의 현재 위치와 다음 진행 지점은 `TRPG 데이터/SESSION PROGRESS 운영 지침.md`를 따른다.

- 모든 응답의 본문 뒤 최하단에 `SESSION PROGRESS`를 표시한다. 단순 질의와 잡담도 대기형을 사용한다.
- `SESSION PROGRESS` 전체는 항상 코드블럭 안의 플레인 텍스트로 표시하고, 그 뒤에는 본문이나 새 제안을 덧붙이지 않는다.
- 활성형은 `작업`, `현재`, `단계`, `완료`, `미결`, `다음`을 사용하며, 일시 중단형·완료형·대기형은 정본 지침의 필드를 따른다.
- 모든 SESSION PROGRESS 필드의 값이 복수이면 쉼표 대신 순차 목록을 사용한다. `완료`에는 실제 완료 또는 사용자 확정 사항만 기록한다.
- `미결`에는 이전 단계에서 판단·검증·합의되지 않았거나 충돌·장애로 해결되지 않은 채 현재 단계로 넘어온 사항만 기록한다. 현재 단계의 검토·판단·예정 작업은 `현재`와 `다음`으로 표현하며, 미결이 없으면 `미결: 없음`으로 표기한다.
- 미완료 작업을 두고 주제가 바뀌면 중단 지점과 재개 지점을 보존하고, 진행 중이거나 재개할 작업이 없으면 대기형으로 축약한다.
- 이미지 승인 절차와 SESSION PROGRESS는 별개다. 이미지 생성 뒤 자가검수 통과 여부와 관계없이 결과 응답에는 SESSION PROGRESS를 표시한다.
- 사용자가 SESSION PROGRESS의 표시 생략을 명시하면 그 지시를 우선한다.

1. 현재 대화의 최신 사용자 지시
2. 프로젝트 최상위 지침
3. 프로젝트에 업로드된 목적별 공통 지침
4. Google Drive 프로젝트 기본 지침
5. 해당 기능 마스터 프롬프트
6. 기능별 실행 지침·라이브러리·템플릿
7. GitHub 및 기타 보조 자료
