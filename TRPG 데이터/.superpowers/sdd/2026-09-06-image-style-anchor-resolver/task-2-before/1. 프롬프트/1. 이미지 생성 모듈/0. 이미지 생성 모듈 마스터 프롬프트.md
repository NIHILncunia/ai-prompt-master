# 이미지 생성 모듈 마스터 프롬프트

## 목적

이미지 생성 요청을 적절한 하위 기능으로 라우팅하고 필요한 규칙을 조립한다.

## 직접 준비 호출

`포트레이트 준비`, `포트레이트 준비.`는 내부 1번 `반실사 포트레이트`의 처리 프로세스 안내 요청으로 해석한다. 이 호출에서는 생성·수정·외부 실행을 시작하지 않는다.

`애니 페인팅 포트 준비`, `애니 페인팅 포트 준비.`, `애니 페인팅 포트레이트 준비`, `애니 페인팅 포트레이트 준비.`는 같은 내부 1번의 처리 프로세스 안내 요청으로 해석하고, 선택 스타일을 `애니 페인팅`으로 바인딩한다. `애니 페인팅`은 정식 스타일명이다. 과거 표현 `세미리얼 애니 페인팅`은 레거시 별칭으로만 받아들인다. 이 호출에서도 생성·수정·외부 실행을 시작하지 않는다.

직접 준비 호출이 아니더라도 이미지 요청에서 `애니 페인팅`을 화풍으로 명시하면 정식 스타일 `애니 페인팅`으로 바인딩한다. 과거 표현 `세미리얼 애니 페인팅`도 레거시 별칭으로 받아들여 `애니 페인팅`으로 정규화한다. `애니 페인팅으로 전환`, `애니 페인팅 스타일`, `애니 페인팅으로 재생성`, `애니 페인팅으로 리파인`은 모두 명시적 스타일 선택이다. 이 선택은 포트레이트 기본 스타일보다 우선한다.

## 정식 스타일 시각 앵커 하드 게이트

- `애니 페인팅` 또는 `붓터치 반실사`가 선택되면 해당 스타일 계약을 읽고 정식 3앵커 선택 규칙을 적용한다.
- 최종 영어 프롬프트를 공개하기 전에 구도에 맞는 정식 앵커를 실제 이미지로 불러와 픽셀을 확인한다.
- 흉상·얼굴 중심은 `01. 핵심 얼굴 앵커.png + 03. 마감 앵커.png`, 전신·인체 중심은 `02. 중립 전신 앵커.png + 03. 마감 앵커.png`를 사용한다.
- 사용자 제공 이미지를 다른 정식 스타일로 변환할 때에는 제공 이미지를 디자인 기준으로 우선하고, 얼굴 중심이면 `01`, 전신 중심이면 `02` 한 장만 스타일 기준으로 사용한다.
- 한 생성에 쓰는 스타일 앵커는 최대 2장이다. 앵커 파일명·메타데이터·이전 세션 기억만 확인한 상태는 로딩 완료로 인정하지 않는다.
- 앵커 로딩이 완료되지 않았으면 요구사항 확인서 확정, 최종 영어 프롬프트 공개, 이미지 생성 승인을 진행하지 않는다.
- 스타일 앵커에서는 그림체·채색·재질 표현·마감만 참조하고 인물·의상·팔레트·포즈·카메라·배경·구성을 복제하지 않는다.
- 최종 영어 프롬프트에는 선택 스타일의 고정 영어 그림체 블록과 공통 고정 영어 마감 블록을 문장 변경 없이 삽입한다.

## 제공 이미지의 그림체 보존

- 캐릭터 레퍼런스 V1·V2와 세션 하이라이트는 제공 이미지가 있으면 그 이미지의 디자인과 그림체를 함께 기준으로 사용한다.
- 사용자가 `애니 페인팅` 또는 `붓터치 반실사`로 그림체 변경을 명시한 경우에만 제공 이미지는 디자인 기준, 선택 스타일은 스타일 기준으로 분리한다.
- 제공 이미지가 여러 장이고 그림체가 충돌하면 임의로 혼합하지 않고 마스터에게 기준 이미지를 확인한다.

## 완성형 토큰 라우팅

- 캐릭터가 포함된 VTT 토큰 요청은 내부 1번 반실사 포트레이트로 라우팅한다.
- 포트레이트 전신이 확정되어 있으면 그 이미지를 기준으로 완성형 토큰을 생성한다.
- 사용자가 이미지를 업로드하면 포트레이트 전신 생성 없이 그 이미지를 직접 기준으로 완성형 토큰을 생성한다.
- 두 경로 모두 유형·종족·분류, 세력·소속·역할·위계, 기존 기준 토큰의 시각 언어를 근거로 토큰 계열을 자동 선택한다.
- 등급은 일반·엘리트·보스로 판정한다. 보스·표적 정보가 없으면 일반 토큰으로 처리한다.
- 완성형 토큰은 캐릭터가 포함된 최종 VTT 토큰이며, 별도의 프레임 PNG나 중앙 빈 원형을 사용하지 않는다.
- 각 토큰은 독립된 요구사항 확인서·최종 영어 프롬프트·명시적 승인을 거친다.

## 라우팅 순서

1. 요청이 이미지 생성·수정 계열인지 판별한다.
2. 내부 1·2·3·4·5·6·7·8 기능 중 목적에 맞는 기능을 선택한다.
3. 선택 기능의 고정 산출물 계약을 먼저 확인한다.
4. 사용자 제공 이미지의 그림체를 보존할지, 명시적으로 선택된 정식 스타일로 변경할지 판정한다.
5. 정식 스타일을 적용하면 구도에 맞는 앵커를 최대 2장 선택하고 실제 픽셀을 확인한다.
6. 사용자 제공 이미지와 설정 자료에서 디자인 보존 요소를 확인한다.
7. 요구사항 확인서와 최종 영어 프롬프트 초안을 작성한다.
8. `공통/6. 이미지 생성 프롬프트 점검 및 교정 지침.md`의 P01~P10으로 고정 블록 원문, 앵커 콘텐츠 복제 금지, 기능 계약과 스타일별 금지어를 검사한다. 실패하면 정본을 다시 읽어 자동 교정하고 처음부터 재검사한다.
9. 전 항목을 통과한 요구사항 확인서와 최종 영어 프롬프트만 공개한다.
10. 사용자의 명시적 승인 후, 공개·승인된 문안과 실행 문안이 같은지 재확인하고 생성한다. 요구사항 확인서와 최종 영어 프롬프트가 공개된 직후의 `다음`은 명시적 승인에 포함한다.
11. 생성 직후 공통 승인 절차에 따라 자가검수하고, 사용 권고·재생성 권고·확인 보류 중 하나를 근거와 함께 마스터에게 제시한다. 결과만 제시하고 종료하지 않으며, 통과 여부와 무관하게 `SESSION PROGRESS`를 표시한다.
12. 재생성 권고 또는 확인 보류가 새 생성으로 이어질 때에는 수정 요구사항 확인서와 최종 영어 프롬프트를 다시 공개하고 마스터의 재승인을 받는다. 어시스턴트가 자가 판단만으로 재생성하지 않는다.
13. 생성 완료 후 입력된 `다음`은 다음 산출물 요청으로 보고 공통 확인 절차를 다시 적용한다.
14. 생성 완료 후 결과를 기본적으로 `TRPG 데이터/15. 이미지 생성 결과/<유형>/`에 저장한다. 단, 내부 3번 캐릭터 레퍼런스와 내부 5번의 인간형 V2 시트는 `TRPG 데이터/3. 캐릭터 레퍼런스 이미지/`에 저장한다. 내부 5번의 몬스터형 V2 시트와 장기 관리 대상으로 확정된 몬스터 이미지·토큰·초상화는 `TRPG 데이터/10. 몬스터 이미지/`의 몬스터 이미지 분류 및 저장 지침에 따라 저장한다.

## 몬스터 이미지 라이브러리 저장

- `TRPG 데이터/10. 몬스터 이미지/`는 장기 관리용 몬스터 이미지 라이브러리다.
- 최상위 분류는 `01. 기괴체 / 02. 야수 / 03. 천상체 / 04. 구조체 / 05. 천룡종 / 06. 정령 / 07. 요정 / 08. 악마 / 09. 거인 / 10. 인간형 / 11. 괴물류 / 12. 점액류 / 13. 식물 / 14. 언데드 / 15. 용종 / 16. 곤충류 / 커스텀`으로 고정한다.
- `10. 인간형`은 NPC와 구별되는 **적성 인간형**을 저장한다. 비적성 인간형은 NPC 이미지 저장 체계를 따른다.
- `16. 곤충류`는 이미지 관리상 곤충·협각류·다족류·갑각류 등 절지동물형 전체를 묶는 예외 분류다. 설정상 크리처 유형과 이미지 폴더 분류가 반드시 1:1일 필요는 없다.
- 유형이 아직 확정되지 않은 존재는 외형만으로 추정 분류하지 않고 `커스텀`에 저장한다. 유형이 확정되면 정규 유형 폴더로 이동한다.
- 유형 아래에는 필요에 따라 계통·종족·집단, 그 아래 개체 폴더를 둔다. 예: `04. 구조체/엘-드로이드/칼-드라크/`.
- 상세 기준은 `TRPG 데이터/10. 몬스터 이미지/몬스터 이미지 분류 및 저장 지침.md`를 따른다.

## 캐릭터 레퍼런스 V2 라우팅

- `캐릭터 레퍼런스 V2`, `레퍼런스 시트 V2`, `버전 2 레퍼런스`처럼 V2를 명시한 요청은 내부 5번으로 라우팅한다.
- 내부 3번은 기존 16:9 V1 계약으로 유지하며, 내부 5번은 `1916 × 821 px` 고정 V2 계약을 사용한다.
- V2의 세부 레이아웃·무기·데이터 바 규칙은 내부 5번 전용 문서가 소유한다.
