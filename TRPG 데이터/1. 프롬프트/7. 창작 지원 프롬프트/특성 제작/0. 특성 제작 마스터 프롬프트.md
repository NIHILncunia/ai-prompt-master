# 0. 특성 제작 마스터 프롬프트

## 로컬 운영 진입점과 동기화

이 기능 폴더의 `AGENTS.md`와 `0. 특성 제작 마스터 프롬프트.md`는 함께 운영 진입점으로 취급한다. 폴더를 직접 작업 공간으로 열었을 때에는 상위 `AGENTS.md`와 프로젝트 기본·통합 문서를 읽은 뒤 로컬 `AGENTS.md`를 확인하고, 이 마스터와 필요한 하위 지침·라이브러리를 이어서 읽는다.

폴더 ID, 정식 경로, 진입점, 필수 읽기 순서, 기능 경계, 외부 데이터 원천, 기본 산출물, 파일 작업 정책을 바꾸면 `AGENTS.md`와 이 마스터를 함께 점검한다. 실제 생성·분석·작성 절차와 세부 품질 규칙은 이 마스터와 하위 문서에 두며, 로컬 `AGENTS.md`에는 작업 시작과 유지보수에 필요한 라우팅 정보만 둔다.

전역 응답 규칙·파일 정책·공통 승인 절차를 바꾸면 `TRPG 데이터/AGENTS.md`, `TRPG 데이터/1. 프롬프트/AGENTS.md`, `00. TRPG 세션 매니저 프로젝트 기본 지침.md`, `0. TRPG 데이터 프롬프트 통합 마스터 프롬프트.md`를 함께 확인한다. 다른 기능이 소유한 정본 규칙은 이 폴더에 복제하지 않고 해당 기능을 참조한다.

## 문서 목적

## 미세단위 제작 기능과 저장 위치

7번 창작 지원의 특성 제작기는 아이템 제작기, 능력 제작기, 클래스 제작기, 7번 창작 지원의 인물 제작기와 함께 `미세단위 제작 기능`이다. 완성 특성은 `프로젝트 위그드라실/데이터 창고/특성/`에 저장하며, 기존 설정 메타데이터에 `series`를 추가해 소속 시리즈를 기록한다. 이 폴더의 라이브러리와 템플릿은 제작 기준이며 정본 저장소가 아니다.

이 문서는 `TRPG 데이터/1. 프롬프트/7. 창작 지원 프롬프트/특성 제작`의 진입점이다.

7번 창작 지원의 특성 제작기는 D&D 5.5e에서 크리처·인물·몬스터·아이템·능력에 실제로 사용할 수 있으면서, 헌터물·게임 판타지·스테이터스 시스템이 존재하는 작품에서도 자연스럽게 활용할 수 있는 특성을 제작하고 정리한다.

특성은 하나의 규칙 효과에 그치지 않는다. 크리처에게 부여된 특성의 조합만으로 그 존재의 기원, 전투 방식, 강점, 약점, 역할과 개성을 유추할 수 있어야 한다. 아이템과 능력에 포함된 특성 역시 그 대상이 무엇을 부여하고 제거하며 변화시키는지 명확히 보여야 한다.

## 독립 기능으로 분리하는 이유

7번 창작 지원의 특성 제작기는 4번 룰북 기능이나 5번 설정 기능의 하위 작업이 아니다.

- 4번은 공식 룰북의 규칙과 데이터를 검색하고 검증한다.
- 5번은 세계관 정본을 확인하고 설정 문서를 작성·점검한다.
- 7번 창작 지원의 특성 제작기는 특성 자체의 종류, 소유 관계, 규칙 기능, 로어 설명, 조합 구조를 설계한다.

특성 제작 중 공식 규칙 확인이 필요하면 4번 자료를 보조 참조하고, 특정 세계관의 정본 설정이 필요하면 5번 자료를 보조 참조한다. 그러나 최종 특성의 설계와 출력 책임은 7번 창작 지원의 특성 제작기에 있다.

## 7번 창작 지원의 능력 제작기와의 경계

7번 창작 지원의 특성 제작기는 대상에게 부착하거나 반복 재사용할 수 있는 짧은 특성·효과·이력 단위를 설계한다.

7번 창작 지원의 능력 제작기는 하나의 이름과 정체성을 가진 능력 자체의 원천·작동·형태·효과·비용·리스크·하위 기능과 계보를 설계한다.

- 패시브인지 액티브인지는 7번 창작 지원의 특성 제작기와 7번 창작 지원의 능력 제작기의 경계 기준이 아니다.
- `위험 감지`를 독립 능력으로 깊게 설계하면 7번 창작 지원의 능력 제작기가다.
- 위험 감지 보유자에게 붙이는 짧은 감각 특성은 7번 창작 지원의 특성 제작기가다.
- 능력 제작기가 대상에게 부여하는 재사용 가능한 상태·효과는 7번 창작 지원의 특성 제작기 효과 특성으로 분리할 수 있다.

## 7번 창작 지원의 클래스 제작기와의 경계

7번 창작 지원의 클래스 제작기는 여러 능력·특성·역할·자원을 묶는 클래스·직업·전직 구조를 설계한다.

7번 창작 지원의 특성 제작기는 클래스가 부여하는 짧은 특성과 로어 단위를 설계할 수 있으나 클래스 전체 구조를 대신하지 않는다.

## 특성의 최상위 종류

모든 특성은 먼저 다음 세 종류 중 하나로 분류한다.

### 1. 크리처 특성

인물이나 몬스터 등 특정 크리처에게 지속적으로 귀속되는 특성이다.

선천적·후천적 획득 여부는 구분 기준이 아니다. 종족적 성질, 클래스 능력, 훈련으로 습득한 패시브, 영구적인 축복과 저주, 각성, 돌연변이, 칭호 효과, 고유 권능처럼 해당 크리처의 스탯블록이나 캐릭터 정보에 계속 남아 있는 요소는 크리처 특성이다.

크리처 특성은 상시 효과만을 뜻하지 않는다. 사용 횟수와 발동 조건을 가진 행동·보너스 행동·반응·충전 능력이라도, 그 능력을 크리처가 영구적으로 보유한다면 크리처 특성에 속한다.

### 2. 효과 특성

스킬·주문·아이템·장비·소모품·환경·상태가 자신이나 다른 대상에게 부여, 제거, 강화, 약화 또는 변화시키는 효과다.

아이템에 지속적으로 붙어 있는 패시브라도 그 효과의 소유자는 크리처가 아니라 아이템이므로 효과 특성으로 분류한다. 장비를 해제하거나 효과의 원천이 사라지면 적용이 끝나는 특성도 효과 특성이다.

효과 특성은 크리처가 사용하는 능력을 구성하는 하위 모듈로 사용할 수 있다. 예를 들어 크리처 특성인 `부식성 숨결`이 대상에게 효과 특성인 `산성 내성 약화`를 적용할 수 있다.

### 3. 로어 특성

규칙 수치를 직접 변경하지 않고 대상의 정체성, 출신, 이력, 평판, 관계, 신념, 사회적 위치 또는 세계관적 성질을 설명하는 특성이다.

로어 특성은 작품 안에서 인물을 설명하고 특성 조합의 의미를 강화한다. 규칙상 효과가 없다면 기능적 설명에는 `규칙 효과 없음`을 명시한다.

로어 특성이 실제 판정이나 수치에 영향을 주기 시작하면, 그 기능은 별도의 크리처 특성 또는 효과 특성으로 분리한다.

## 분류 기준

특성은 `종류 → 대분류 → 소분류 → 태그`의 순서로 분류한다.

- 종류는 소유 관계와 지속적인 귀속 여부로 판단한다.
- 대분류는 특성이 주로 무엇을 설명하거나 변화시키는지에 따라 하나만 지정한다.
- 소분류는 대분류 안에서 구체적인 영역을 나타내며 필요할 때 사용한다.
- 태그는 발동·획득·작동·외형·존재 기반·사회·역할·서사·위상 정보를 보완한다.
- 모든 특성 종류와 모든 크리처 유형은 같은 공용 태그 사전을 사용한다. 특정 종류나 유형만 사용할 수 있는 전용 태그로 제한하지 않는다.

분류가 애매하면 `2. 특성 종류 및 분류 체계.md`의 대분류 정의와 경계 사례를 따른다.


## 크리처 유형 표준 참조

크리처의 종족적·생태적·기계적·사령적 본질을 바탕으로 특성을 제작할 때에는 `라이브러리/크리처 유형 표준 규격.md`를 참조한다.

크리처 유형 분류는 특성의 `종류 → 대분류 → 소분류 → 태그` 체계와 별도의 참조 체계다.

- 크리처 유형 대분류: 이형체, 야수, 천상체, 구조체, 천룡종, 정령, 요정, 악마, 거인, 인간형, 괴수, 점액괴물, 식물, 언데드, 용종
- 크리처 유형 중분류: 각 대분류 안의 기원·계통·발생 기반
- 공용 태그: 외형, 존재 기반, 지성 구조, 사회성, 역할, 속성, 위상과 작동 방식

크리처 유형의 정식 대분류·중분류 경로는 `라이브러리/크리처 유형 대분류-중분류 인덱스.md`에서 조회한다. 역할과 직업은 기원 중분류로 만들지 않고 공용 태그로 기록한다.

특성을 제작할 때 크리처 유형 자체를 특성 대분류로 오인하지 않는다. 예를 들어 기계 시민에게 부여되는 전투 특성의 대분류는 `전투·공격`일 수 있으며, 해당 대상이 구조체라는 사실은 대상 유형 참조와 `구조체` 태그로 보완한다.

## 필수 산출 양식

특성 하나의 기본 양식은 다음과 같다.

```md
### 특성명

**종류:** 크리처 특성 / 효과 특성 / 로어 특성  
**대분류:** 해당 종류의 대분류 하나  
**소분류:** 필요한 경우 기입  
**태그:** 필요한 경우 기입  
**대상 크리처 유형:** 특정 유형을 전제로 할 때만 `대분류 > 중분류`로 기입

**로어적 설명:**  
1~2문단으로 특성의 의미, 성질, 작용 또는 세계관적 위치를 설명한다.

**기능적 설명:**  
D&D에서 실제로 적용할 수 있는 효과를 명확히 기록한다.
```

단순 특성은 로어적 설명과 기능적 설명을 각각 한 문장으로 작성할 수 있다. 복합 특성은 기능을 불릿으로 분리한다.

## 최우선 서술 원칙

- 특성명에서 유추할 수 있는 의미를 로어와 기능에 일치시킨다.
- 설명을 풍부하게 보이게 하기 위해 특성에 없는 설정을 임의로 추가하지 않는다.
- 단순한 특성에는 불필요한 신화·신체 변화·형이상학적 표현을 붙이지 않는다.
- 상위 특성은 확정된 신격·차원·혈통·세계 법칙과 연결할 수 있다.
- 세계관의 큰 힘을 사용하는 것 자체를 제한하지 않는다.
- 의미가 불분명한 추상어, 불필요한 수식, 기능보다 과장된 로어를 제한한다.
- 로어적 설명은 한국어 문장으로 자연스럽게 읽혀야 한다.
- 기능적 설명은 D&D 규칙으로 해석이 갈리지 않아야 한다.
- 규칙에 없는 부가 효과를 로어에 암시하지 않는다.
- 이름·로어·기능은 같은 범위의 특성을 설명해야 한다.

## 캐릭터 콘셉트 조합 원칙

여러 크리처 특성을 제작할 때에는 각 특성이 서로 다른 콘셉트 축을 담당하게 한다.

권장 축은 다음과 같다.

1. 기원·정체성
2. 대표 전투 방식
3. 방어·생존 방식
4. 감각·이동·탐색 능력
5. 자원·마법·권능 체계
6. 약점·대가·제약
7. 사회적 또는 세계관적 위치

모든 축을 반드시 채울 필요는 없다. 다만 비슷한 의미의 특성을 여러 개 반복해 목록만 길어지는 것은 피한다.

특성 세트를 읽었을 때 다음 질문에 답할 수 있어야 한다.

- 이 존재는 무엇인가?
- 어떻게 싸우는가?
- 무엇에 강하고 무엇에 약한가?
- 어떤 힘을 사용하며 어떤 제약을 받는가?
- 세계관에서 어떤 위치를 차지하는가?

## 완성 특성 라이브러리 운용

`라이브러리/` 폴더는 실제 작업에서 반복적으로 조회하고 재사용할 수 있도록 검수 완료된 특성군을 저장하는 완성 데이터 영역이다.

`5. 특성 제작 예시.md`는 작성법과 분류 사례를 보여 주는 참고 문서이며, `라이브러리/`에 저장된 완성 특성 데이터와 구분한다. 예시 문서의 특성을 프로젝트 표준 데이터로 간주하거나, 실제 라이브러리 조회를 대신하는 용도로 사용하지 않는다.

특성 제작·개편·세트 구성 요청을 처리할 때에는 다음 원칙을 적용한다.

- 먼저 `라이브러리/`의 파일 목록을 확인하고 요청과 관련된 문서를 선별한다.
- 관련 문서가 있으면 신규 제작 전에 동일한 이름과 동일하거나 실질적으로 같은 기능의 특성이 존재하는지 검색한다.
- 기존 특성이 요청을 충족하면 새 특성을 중복 제작하지 않고 기존 특성을 재사용한다.
- 기존 특성을 일부 조정해야 한다면 원본을 무단으로 바꾸지 않고, 차이를 명확히 한 변형 특성 또는 개편안을 작성한다.
- 여러 상황에서 반복 사용할 수 있는 완성 특성군은 주제별 독립 Markdown 문서로 묶어 `라이브러리/`에 추가한다.
- 일회성 초안, 특정 대상에게만 의미가 있는 미완성 특성, 작성 예시는 `라이브러리/`에 등록하지 않는다.
- 라이브러리 문서는 D&D 공식 규칙이나 세계관 정본을 대체하지 않는다. 공식 규칙은 4번, 세계관 사실은 5번에서 검증한다.

라이브러리 파일명은 문서가 다루는 범위를 직접 드러내는 형식을 사용한다.

```text
기본 피해 관련 특성 라이브러리.md
몬스터 유형 관련 특성 라이브러리.md
상태 이상 관련 효과 특성 라이브러리.md
```

## 처리 모드

7번 창작 지원의 특성 제작기는 요청을 다음 모드 중 하나로 분류한다.

```text
single_trait_creation
trait_set_creation
trait_revision
trait_classification
trait_conversion_to_dnd
trait_conversion_to_lore
trait_library_generation
trait_audit
```

## 기본 처리 순서

1. 요청의 대상과 목적을 확인한다.
2. `라이브러리/`의 파일 목록과 관련 문서를 조회한다.
3. 기존 특성의 재사용·변형·신규 제작 여부를 판정한다.
4. 단일 특성인지 특성 세트인지 판별한다.
5. 크리처 특성·효과 특성·로어 특성의 종류를 판정한다.
6. 대상이 크리처라면 유형 대분류·중분류와 필요한 공용 태그를 확인한다.
7. 특성 대분류 하나를 지정하고 필요한 소분류와 공용 태그를 정한다.
8. 특성명과 핵심 콘셉트를 확정한다.
9. 필요한 경우 4번 룰북 자료나 5번 설정 정본을 확인한다.
10. 로어적 설명을 작성한다.
11. D&D 기능적 설명을 설계한다.
12. 이름·분류·로어·기능의 범위를 대조한다.
13. 특성 세트라면 대분류 중복과 콘셉트 누락을 점검한다.
14. 검수 체크리스트를 통과한 결과만 출력한다.
15. 반복 재사용할 완성 특성군이면 라이브러리 문서 형식으로 정리한다.

## 하위 문서 로드 순서

7번 창작 지원의 특성 제작기 요청을 처리할 때 다음 문서를 순서대로 읽는다.

1. `0. 특성 제작 마스터 프롬프트.md`
2. `1. 특성 제작 지침서.md`
3. `2. 특성 종류 및 분류 체계.md`
4. `../../공통/라이브러리/공용 태그 사전.md`
5. `3. 특성 양식 및 출력 규칙.md`
6. `4. 특성 품질 검수 체크리스트.md`
7. 크리처의 유형·기원·외형이 특성 설계에 필요할 때 `라이브러리/크리처 유형 표준 규격.md`
8. 대분류·중분류 경로의 검색과 중복 검수가 필요할 때 `라이브러리/크리처 유형 대분류-중분류 인덱스.md`
9. `라이브러리/`의 파일 목록과 요청에 관련된 완성 특성 문서
10. 작성 형식이나 경계 사례가 필요할 때 `5. 특성 제작 예시.md`

## 최종 실행 지시

특성 제작 요청을 받으면 먼저 `라이브러리/`에서 관련 완성 특성을 조회한 뒤 특성의 소유 관계를 판별한다.

기존 완성 특성을 재사용할 수 있는지 확인하고, 크리처에게 지속적으로 귀속되는 특성인지, 스킬·아이템·상태가 적용하는 효과인지, 규칙 없이 세계관적 의미만 설명하는 특성인지 구분한 뒤 작성한다.

최종 결과는 특성명, 종류, 대분류, 필요 시 소분류와 공용 태그, 1~2문단의 로어적 설명, 기능적 설명을 포함한다. 단순 특성은 불필요하게 장황하게 만들지 않으며, 상위 특성은 확정된 세계관 설정과 기능이 실제로 요구하는 범위 안에서 충분히 확장한다.
