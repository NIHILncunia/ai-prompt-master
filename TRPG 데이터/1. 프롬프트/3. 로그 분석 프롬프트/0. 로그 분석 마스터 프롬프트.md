# 0. 로그 분석 마스터 프롬프트

## 로컬 운영 진입점과 동기화

이 기능 폴더의 `AGENTS.md`와 `0. 로그 분석 마스터 프롬프트.md`는 함께 운영 진입점으로 취급한다. 폴더를 직접 작업 공간으로 열었을 때에는 상위 `AGENTS.md`와 프로젝트 기본·통합 문서를 읽은 뒤 로컬 `AGENTS.md`를 확인하고, 이 마스터와 필요한 하위 지침·라이브러리를 이어서 읽는다.

폴더 ID, 정식 경로, 진입점, 필수 읽기 순서, 기능 경계, 외부 데이터 원천, 기본 산출물, 파일 작업 정책을 바꾸면 `AGENTS.md`와 이 마스터를 함께 점검한다. 실제 생성·분석·작성 절차와 세부 품질 규칙은 이 마스터와 하위 문서에 두며, 로컬 `AGENTS.md`에는 작업 시작과 유지보수에 필요한 라우팅 정보만 둔다.

전역 응답 규칙·파일 정책·공통 승인 절차를 바꾸면 `TRPG 데이터/AGENTS.md`, `TRPG 데이터/1. 프롬프트/AGENTS.md`, `00. TRPG 세션 매니저 프로젝트 기본 지침.md`, `0. TRPG 데이터 프롬프트 통합 마스터 프롬프트.md`를 함께 확인한다. 다른 기능이 소유한 정본 규칙은 이 폴더에 복제하지 않고 해당 기능을 참조한다.

## 문서 목적

이 문서는 `TRPG 데이터/1. 프롬프트/3. 로그 분석 프롬프트` 폴더의 진입점이다.

사용자가 세션 로그 분석, 정보흐름분석, 기승전결 스토리 요약, 세션 연속성 정리, 장기 스토리 정리, 원본 로그 기반 분석본 작성을 요청하면 이 문서를 먼저 읽는다.

이 폴더는 `TRPG 데이터/2. 로그/원본`에 저장된 원본 로그를 분석하여 `TRPG 데이터/2. 로그/분석/<캠페인명>/<원본 최상위 폴더명>/`에 분석본을 작성하고, 필요한 경우 `TRPG 데이터/2. 로그/스토리 정리/<캠페인명>/<원본 최상위 폴더명>/`에 장기 스토리 정리 자료를 작성하기 위한 전용 프롬프트 모듈이다.

## 적용 조건

아래 요청은 모두 이 폴더의 지침으로 처리한다.

- 로그 분석
- 세션 분석
- 정보흐름분석 작성
- 기승전결 스토리 요약 작성
- 세션 연속성 프론트매터 작성
- 원본 로그를 분석본으로 변환
- 기존 분석본을 기준으로 다음 세션 분석
- 특정 세션의 업적, 밝혀진 진실, 미확정 사실 정리
- PC 관계 변화, 갈등, 떡밥, 인수인계 정보 정리
- 특정 스토리 전체 또는 여러 세션의 장기 스토리 정리
- 기존 `스토리 정리` 문서의 재작성·보완·윤문

세션 단위 분석에서는 실제 플레이 장면 `Pxx`와 기본 하이라이트 `Hxx`를 분석 문서 안에 함께 산출한다. 완전한 이미지 제작용 Highlight Card 정밀화 또는 하이라이트만 독립적으로 추출하는 요청은 `2. 로그 하이라이트 추출 프롬프트`가 담당한다.

## 기본 처리 순서

1. 사용자의 요청이 세션 단위 분석·요약인지 장기 스토리 정리인지 판별한다.
2. 이 문서를 읽은 뒤 `1. 로그 분석 지침서.md`와 `라이브러리/플레이어 및 PC 정보.md`를 확인한다. 정보흐름분석을 작성하는 경우 `템플릿/1. 정보흐름분석 템플릿.md`도 읽고 정본 구조로 사용한다.
3. 장기 스토리 정리 요청이면 `2. 스토리 정리 작성 지침.md`를 추가로 읽는다.
4. 원본 로그는 `TRPG 데이터/2. 로그/원본`에서 찾고, 원본 로그의 명시 표기 또는 마스터 지정으로 캠페인명을 확인한 뒤 최상위 폴더명으로 정규 스토리·외전과 진행자를 판별한다.
5. 세션 단위 분석은 같은 스토리명의 직전 분석 문서가 있으면 프론트매터 `continuity`를 연속성 기준으로 확인한다. 첫 세션처럼 직전 분석이 없으면 연속성 참조 없이 현재 원본 로그에서 시작한다. 직전 분석의 본문 길이·항목 수·서술 방식은 새 분석의 밀도 기준으로 사용하지 않는다.
6. 원본 로그를 정밀하게 읽고, 실제로 드러난 사건 관련 발언·진행자 묘사·현장 단서·PC 질문과 추론·선택·반응·관계 변화·상태 변화·후속 행동 압력을 추적한다. 분석 밀도는 이전 문서가 아니라 `1. 로그 분석 지침서.md`의 절대 기준으로 판정한다.
7. 장기 스토리 정리는 대상 스토리의 전체 세션 범위와 정보흐름분석 문서를 확인한 뒤, 중요한 사건·인과·선택을 원본 로그로 검증한다.
8. 원본 로그의 실제 내용만 확정 사실의 최종 근거로 사용한다. 등장인물의 진술·PC 추론·강한 정황·직접 확인을 구분하며, 로그에 공개되지 않은 숨은 설정·설계 정답·배후 의도는 분석 본체에 섞지 않는다.
9. 정보흐름분석 문서를 작성할 경우 최상단 YAML 프론트매터에 스토리 유형과 진행자 맥락을 포함하고, 세션 설계 존재 여부와 관계없이 원본 로그 기반 `Pxx`와 기본 `Hxx`를 작성한다. 세션 설계가 존재하면 Pxx에 `scene_uuid / map_uuid / 설계 대응 상태`를 추가하고 `설계본 대비 실제 진행 차이 Dxx`를 작성한다. 세션 설계가 없으면 `session_design.status: not_found`만 기록하고 설계 의존 필드와 Dxx 비교층을 생성하지 않는다. 설계 전용 정보는 비교층 밖의 실제 로그 분석에 섞지 않는다.
10. 초안 작성 후에는 `1. 로그 분석 지침서.md`의 **로그 기반 분석 밀도 최종 검수**를 수행하여, 원본에 드러난 정보 전환점·근거·확정도·인물 반응·후속 영향이 빠짐없이 추적되었고 로그 밖의 정보가 유입되지 않았는지 확인한다.
11. 생성 또는 수정 결과는 기본 파일 정책을 따르며, 사용자가 Drive 직접 반영을 명시한 경우 해당 요청 범위에서 직접 적용할 수 있다.

## 대상 데이터 구조

구글 드라이브 기준 경로는 아래를 따른다.

```text
TRPG 데이터/2. 로그/
├─ 원본/
├─ 분석/
│  └─ <캠페인명>/<원본 최상위 폴더명>/
└─ 스토리 정리/
   └─ <캠페인명>/<원본 최상위 폴더명>/
```

프롬프트 기준 경로는 아래를 따른다.

```text
TRPG 데이터/1. 프롬프트/
└─ 3. 로그 분석 프롬프트/
   ├─ 0. 로그 분석 마스터 프롬프트.md
   ├─ 1. 로그 분석 지침서.md
   ├─ 2. 스토리 정리 작성 지침.md
   ├─ 템플릿/
   │  └─ 1. 정보흐름분석 템플릿.md
   └─ 라이브러리/플레이어 및 PC 정보.md
```

## PC 정보 참조 규칙

로그 분석을 시작하기 전에 반드시 같은 폴더의 `라이브러리/플레이어 및 PC 정보.md`를 읽는다.

이 파일에 이름이 있는 발화자는 모두 PC로 취급한다.  
이 파일에 `/`로 병기된 이름이 있으면, 각 이름을 모두 독립된 PC급 발화자와 행동 주체로 취급한다.

이 파일에 없는 발화자는 NPC로 취급한다.  
단, 스토리 핸들러 역할의 NPC는 PC와 유사하게 추적할 수 있으나 분류는 NPC로 유지한다.

## 원본 스토리 분류와 진행자 맥락

원본 로그를 선택한 뒤에는 `1. 로그 분석 지침서.md`의 캠페인·원본 최상위 폴더명 판별 규칙을 적용한다. 정규 스토리는 니힐이 진행하며, 외전은 등록된 담당 정보 또는 원본 로그의 명시적 진행자 표기로 진행자를 확인한다. 같은 캠페인에서는 세션 번호와 관계없이 정규 스토리를 모든 외전보다 나중의 서사로 기록한다. 서로 다른 캠페인의 시간 순서는 비교하지 않는다. 이 정보는 발화자 분류와 분석·스토리 정리 문서의 프론트매터에만 사용하며, 원본 로그에 없는 서사 사실로 쓰지 않는다.

## 2. 로그 하이라이트 추출 프롬프트와의 관계

이 폴더는 2번의 완전한 Highlight Card 정밀화와 독립 추출 역할을 대체하지 않는다. 3번은 세션 분석의 일부로 기본 `Hxx` 선정까지만 담당한다.

`3. 로그 분석 프롬프트`는 원본 로그의 서사 정보, 인물 관계, 떡밥, 정보 흐름, 기승전결 요약, 실제 플레이 장면 `Pxx`, 기본 하이라이트 `Hxx`, 다음 세션 인수인계를 정리하는 장기 기록 분석 모듈이다. 세션 설계 대응과 `Dxx` 비교층은 설계본이 실제로 존재할 때만 추가한다.

`2. 로그 하이라이트 추출 프롬프트`는 하이라이트만 필요할 때 원본 로그에서 독립 추출하거나, 3번 분석본의 `Hxx/Pxx`를 따라 이미지 제작에 필요한 완전한 Highlight Card로 정밀화하는 모듈이다.

이미 작성된 3. 로그 분석 프롬프트의 분석본은 2. 로그 하이라이트 추출에서 장면 맥락, 등장 인물, 갈등 구조, 떡밥, 사건 흐름을 보강하는 참고 자료로 사용할 수 있다.

## 산출물 종류

이 폴더에서 다루는 기본 산출물은 아래와 같다.

- 정보흐름분석 문서
- 정보흐름분석 문서 안의 기승전결 스토리 요약 섹션
- 단독 기승전결 스토리 요약 문서
- 세션 단위 핵심 결과 데이터
- PC 관계 변화 및 갈등 정리
- 다음 세션 분석용 프론트매터 인수인계
- 여러 세션을 하나의 장기 서사로 재구성한 스토리 정리 문서

## 파일 제공 원칙

분석 결과나 수정 결과는 사용자가 내려받을 수 있는 파일로 제공한다.

에이전트는 사용자의 명시적 요청 없이 구글 드라이브에 파일을 자동 생성하거나, 기존 파일을 덮어쓰거나, 이름을 변경하지 않는다.

캠페인명은 상위 폴더로 식별한다. 원본 세션 로그와 세션 분석 문서 파일명은 모두 `세션 <번호>`로 시작하며, 파일명에 캠페인명을 반복하지 않는다. 그 밖의 파일명은 지침 또는 원본 로그명에 의해 정해진 이름을 그대로 사용한다.
`재수정`, `최종`, `수정본`, 날짜, 번호 같은 임의 접미사를 붙이지 않는다.

## 반드시 읽을 파일

세션 단위 로그 분석·요약 요청을 처리할 때에는 반드시 아래 파일을 읽고 따른다.

- `1. 로그 분석 지침서.md`
- `라이브러리/플레이어 및 PC 정보.md`

정보흐름분석 문서를 작성하는 요청에서는 아래 템플릿을 추가로 반드시 읽고 정본 구조로 사용한다.

- `템플릿/1. 정보흐름분석 템플릿.md`

장기 스토리 정리 요청에서는 위 파일에 더해 아래 파일을 반드시 읽는다.

- `2. 스토리 정리 작성 지침.md`

## 최종 실행 지시

사용자가 로그 분석, 정보흐름분석, 기승전결 요약, 세션 연속성 정리를 요청하면 `1. 로그 분석 지침서.md`와 `라이브러리/플레이어 및 PC 정보.md`를 읽고 그 규칙에 따라 작업한다. 정보흐름분석의 `Pxx`와 `Hxx`는 세션 설계가 없어도 작성하며, 설계 대응 필드와 `Dxx`는 설계본이 있을 때만 작성한다. 정보흐름분석 문서를 작성할 때에는 `템플릿/1. 정보흐름분석 템플릿.md`를 추가로 읽고 정본 구조를 따른다.

사용자가 여러 세션의 장기 스토리 정리 또는 기존 스토리 정리 문서의 재작성·보완을 요청하면 `2. 스토리 정리 작성 지침.md`를 추가로 읽고 그 문서의 산문·문단·품질 규칙을 우선 적용한다. `1. 로그 분석 지침서.md`의 비순차 목록 강제 규칙은 스토리 정리 문서에 적용하지 않는다.

원본 로그에 실제로 나온 정보만 확정 사실의 최종 근거로 삼고, 추정은 확정 사실처럼 작성하지 않는다.

정보흐름분석의 상세도는 기존 분석본과 비교해 결정하지 않는다. 첫 세션을 포함한 모든 세션은 동일한 절대 기준을 적용하며, 원본 로그에 실제로 드러난 서사 정보를 가능한 한 세밀하게 추적한다. `정보 흐름 지도`는 정보 전환마다 발화·발견 주체, 맥락, 수신·반응, 기존 이해의 변화, 확정도, 후속 영향을 기록하고, `서사 심층 분석`은 로그에 드러난 근거만으로 단서·인물·관계·사건 기능의 변화를 해석한다. 로그에 공개되지 않은 숨은 설정·설계 정답·인물의 미공개 속마음·배후 의도를 추측으로 채우지 않는다. 상세함은 분량이 아니라 **드러난 정보의 추적 정밀도**로 판정한다.

## 실제 플레이 장면·설계 대응·기본 하이라이트

## 실제 플레이 장면

세션 단위 정보흐름분석은 세션 설계의 존재 여부와 관계없이 원본 로그를 기준으로 실제 플레이 장면 `Pxx`와 기본 하이라이트 `Hxx`를 산출한다.

### 처리 순서

1. 원본 로그만 기준으로 실제 플레이 흐름을 먼저 분할한다. 세션 설계 장면을 정답지처럼 사용하여 로그를 강제로 자르지 않는다.
2. 실제 플레이 장면은 `P01`, `P02`, `P03` 형식으로 부여한다.
3. 장면 경계는 물리적 장소 변화 하나만으로 정하지 않고, 현재 목적·중심 갈등·비가역적 사건 상태·플레이 모드의 의미 있는 변화를 우선한다.
4. 세션 설계의 존재 여부를 확인한다. 설계가 없으면 프론트매터 `session_design.status`를 `not_found`로 기록하고 Pxx 분석을 계속한다.
5. 세션 설계가 있을 때만 Pxx를 설계 장면의 `scene_uuid`에 대응하고, 장면 파일의 직접 `사용 맵` 참조를 따라 `map_uuid`를 연결한다.
6. 세션 설계가 있을 때만 실제 플레이와 설계의 의미 있는 차이를 `Dxx`로 추적한다. 설계가 없으면 설계 비교층을 만들지 않는다.
7. `Pxx` 목록에서 이미지화 가치가 충분한 순간을 `H01`, `H02` 형식의 기본 세션 하이라이트로 선정한다. 이 단계는 설계 유무와 관계없이 수행한다.
8. `Hxx`는 항상 `Pxx`를 참조한다. 설계가 있으면 Pxx를 통해 `scene_uuid / map_uuid`를 추가 추적하고, 설계가 없으면 `Hxx → Pxx`에서 참조를 종료한다.

### Pxx 장면 경계

새 `Pxx`를 만드는 강한 조건은 다음과 같다.

- 플레이어의 현재 목적이 의미 있게 바뀐다.
- 중심 문제·갈등이 해결되거나 새로운 갈등이 시작된다.
- 협상 가능 상태에서 전투 상태로 바뀌는 것처럼 되돌리기 어려운 사건 상태 변화가 발생한다.
- 중요한 폭로 뒤 플레이어의 행동 방향이 바뀐다.
- 독립적인 전투·추격·도주·의식·잠입 등 새로운 플레이 국면이 시작된다.
- 장소·시간이 크게 이동하면서 이전 장면의 목적과 맥락도 함께 종료된다.
- 주요 참여자 변화가 장면의 중심 자체를 바꾼다.

단순 위치 이동, 같은 대화 안의 화제 변화, 짧은 판정, 전투 페이즈 변화, 같은 갈등 안의 접근법 변경만으로는 자동 분할하지 않는다. 하이라이트 컷을 만들기 위해 `Pxx`를 잘게 쪼개지 않는다.

### Pxx 필수 데이터

모든 Pxx는 다음 공통 데이터를 기록한다.

- 실제 전개
- 장면 시작
- 장면 종료
- 주요 장소
- 주요 참여자
- 핵심 사건

세션 설계가 있을 때만 다음 설계 의존 데이터를 추가한다.

- 세션 설계 대응
- 설계 맵
- 설계 대비 실제 변화

세션 설계가 없으면 설계 의존 필드를 빈 값이나 `없음`으로 남기지 않고 아예 생성하지 않는다. `scene_uuid`, `map_uuid`, `Dxx`, `진행되지 않은 설계 장면`, `설계 이월 요약`도 생성하지 않는다.

원본 로그에 타임스탬프가 있으면 장면 시작·종료에 시간 범위를 병기할 수 있다. 타임스탬프가 없거나 검색에 더 유용하면 대표 발화·사건을 경계 근거로 기록한다.

### 세션 설계 대응 상태

아래 상태는 세션 설계가 실제로 존재할 때만 사용한다.

- `matched`: 하나의 실제 장면과 하나의 설계 장면이 정상 대응한다.
- `merged`: 실제 플레이에서 둘 이상의 설계 장면이 하나의 `Pxx`로 합쳐졌다.
- `split`: 하나의 설계 장면이 실제 플레이에서 둘 이상의 `Pxx`로 갈라졌다.
- `skipped`: 설계에는 있으나 실제 플레이에서 진행되지 않았다. `Pxx`가 없으므로 별도 `진행되지 않은 설계 장면` 목록에 기록한다.
- `unplanned`: 세션 설계가 존재하지만 실제 플레이에서 해당 설계에 없던 장면이 새로 발생했다. 세션 설계 자체가 없을 때는 사용하지 않는다.
- `uncertain`: 세션 설계는 존재하지만 근거가 부족해 설계 장면 대응을 확정할 수 없다.

세션 설계 자체가 없으면 대응 상태를 부여하지 않는다.

### 설계 맵 상태

아래 상태 역시 세션 설계가 존재하고 설계 맵을 추적할 때만 사용한다.

- `confirmed`: 대응 장면의 직접 맵 참조를 따라 맵이 확정되었다.
- `none`: 해당 설계 장면이 의도적으로 맵을 사용하지 않는다.
- `unmapped`: 세션 설계는 있으나 해당 장면에 맵이 아직 할당되지 않았다.
- `uncertain`: 설계 장면 대응이 불확실하여 맵도 확정할 수 없다.

세션 설계 자체가 없으면 `설계 맵` 필드를 생성하지 않으며 `unavailable` 상태도 사용하지 않는다.

`설계 장면 UUID`, `설계 맵 UUID`, `FVTT Scene ID`는 서로 다른 값이다. 설계 장면·맵을 `scene_uuid` 하나에 혼합하지 않는다.

### 분석 문서 배치

- `기승전결 스토리 요약`은 기존 규칙대로 `정보 흐름 지도` 바로 위에 둔다.
- `## 실제 플레이 장면`은 세션 설계 유무와 관계없이 `정보 흐름 지도` 다음에 둔다.
- 세션 설계가 존재하면 각 Pxx에 설계 대응 필드를 추가하고 `## 설계본 대비 실제 진행 차이`를 `실제 플레이 장면` 다음, `서사 심층 분석` 앞에 둔다.
- 세션 설계가 없으면 `실제 플레이 장면` 다음에 바로 `서사 심층 분석`으로 이어간다.
- `## 세션 하이라이트`는 `PC 관계 변화` 등 기존 분석이 끝난 뒤, 문서 말미의 `세션 단위 핵심 결과 데이터` 바로 앞에 둔다.
- `세션 단위 핵심 결과 데이터`는 계속 문서의 최종 핵심 결과 섹션으로 유지한다.

### Hxx 기본 하이라이트

3번 로그 분석의 `Hxx`는 하이라이트의 기본 선정 결과이며 완전한 이미지 생성용 Highlight Card가 아니다.

각 `Hxx`는 다음 정도를 기록한다.

- 우선순위: `high / medium / low`
- 유형
- 실제 장면: 하나 이상의 `Pxx`
- 선정 이유
- 하이라이트 순간
- 중심 인물
- 핵심 시각 요소
- 이미지화 준비 상태

`Hxx`에서 `scene_uuid`, `map_uuid`를 다시 복제하지 않는다. 세션 설계가 있으면 필요한 설계 정보는 `Hxx → Pxx → scene_uuid → map_uuid` 참조를 따른다. 세션 설계가 없으면 `Hxx → Pxx`에서 참조를 종료하고 원본 로그의 실제 장면 정보만 사용한다.

### 세션 설계 프론트매터 참조

세션 설계가 있으면 다음과 같이 기록한다.

```yaml
session_design:
  status: found
  package:
  scenario:
  scene_index:
  flow_record:
  map_index:
```

세션 설계가 없으면 다음 두 줄만 기록하고 설계 경로 필드를 추가하지 않는다.

```yaml
session_design:
  status: not_found
```

이 메타데이터는 설계 패키지 대조 여부를 빠르게 확인하기 위한 것이며 `Pxx`나 `Hxx` 전체를 프론트매터에 복제하지 않는다.
