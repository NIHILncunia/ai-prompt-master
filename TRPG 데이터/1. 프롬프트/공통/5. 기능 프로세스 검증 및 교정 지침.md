# 기능 프로세스 검증 및 교정 지침

## 1. 목적

이 문서는 기능 프롬프트가 `4. 기능 프로세스 유저스토리 및 유스케이스.md`의 기대 흐름대로 작동하는지 점검하고, 어긋난 지침·라우팅·저장 규칙을 바로잡는 운영 절차다.

검증 대상은 실제 채팅 응답, 기능 폴더의 AGENTS·마스터·하위 지침, Drive 저장 결과, SESSION PROGRESS다.

## 2. 예약어와 발동 조건

### `프로세스 점검` 예약어

- `프로세스 점검.`은 점검의 **안내 단계**를 시작한다. 첫 응답에서 아래 전체 점검 흐름을 나열한 뒤 `전체 P0 점검을 시작할까요?`를 묻는다. 이 단계에서는 재현·판정·교정을 수행하지 않는다.
  1. 전역 라우팅·최신 정본·Drive 저장·ZIP 대체·`다음`
  2. 이미지 생성 모듈 내부 8개 기능
  3. 로그 분석
  4. 룰북
  5. 설정
  6. FVTT
  7. 창작 지원 데이터
  8. 세션 제작
  9. 집필 데이터 체크
  10. 복합 파이프라인
- `프로세스 점검 <기능명·흐름명·UC ID>`는 지정 대상과 필요한 선행·후속 흐름만 나열하고, 그 범위의 점검 시작 여부를 묻는다.
- 위 안내 뒤의 `다음`, `시작`, `진행`은 제시된 전체 P0 또는 선택 범위의 점검을 개시하는 승인이다. 같은 시작 질문을 반복하지 않는다.

다음 요청에서는 이 지침을 적용한다.

- 기능의 프롬프트 흐름 점검
- 유저스토리·유스케이스 검증
- 라우팅 오류·잘못된 `다음` 처리·승인 상태 오류 점검
- Drive 저장·ZIP 대체 흐름 점검
- 기능 추가·통합·이동·재번호 뒤의 회귀 점검
- 특정 생성·분석·세션 제작 과정이 문서 규칙과 다르게 동작한 사례의 교정
- 전역 정책을 수정한 뒤 영향 기능 확인

일반적인 자료 조회·이미지 생성·세션 제작에는 자동 적용하지 않는다. 다만 해당 작업에서 흐름 오류가 발견되면 이 지침으로 전환한다.

## 3. 필수 입력

검증을 시작할 때 다음을 확보한다.

1. 검증할 기능 또는 복합 파이프라인
2. 재현할 사용자 입력
3. 직전 대화 상태와 이미 확정된 결과
4. 관련 Drive 정본의 최신 경로와 파일 ID
5. 기대 결과를 판정할 유스케이스 ID
6. 실제 응답·실제 Drive 저장 결과·오류 메시지

입력이 불완전하면 범위를 가장 작은 재현 단위로 줄인다. 근거 없는 가상의 실패를 실제 오류처럼 기록하지 않는다.

## 4. 표준 검증 절차

### 단계 0 — 점검 흐름 안내와 시작 승인

- 대상 없는 `프로세스 점검.`이면 전체 10개 흐름을 빠짐없이 나열하고 전체 P0 점검 시작 여부를 묻는다.
- 대상이 있으면 해당 흐름·UC·의존 흐름을 안내하고 범위의 시작 여부를 묻는다.
- `다음`, `시작`, `진행`으로 승인되기 전에는 실제 입력 재현, 통과·실패 판정, 정본 교정을 시작하지 않는다.

### 단계 1 — 범위와 기준 유스케이스 선택

- 요청의 중심 기능을 1개 선택한다.
- 복합 흐름이면 선행 기능과 최종 기능을 순서대로 나눈다.
- `4. 기능 프로세스 유저스토리 및 유스케이스.md`에서 P0를 먼저 선택하고, 필요할 때 P1·P2를 추가한다.
- 같은 오류를 여러 유스케이스로 중복 기록하지 않는다.

### 단계 2 — 최신 Drive 정본 확인

다음 순서로 읽는다.

1. `TRPG 데이터` 루트에서 `PROJECT AGENTS YYYY MMDD.md` 형식과 정확히 일치하는 후보를 확인하고, 파일명 날짜가 유효한 문서 중 가장 최신 파일을 선택하여 처음부터 끝까지 읽는다.
2. 선택한 프로젝트 에이전트의 기준일을 `프로젝트 에이전트 기준일: YYYY-MM-DD (PROJECT AGENTS YYYY MMDD.md)` 형식으로 검증 기록에 남긴다.
3. `TRPG 데이터/AGENTS.md`
4. `TRPG 데이터/1. 프롬프트/AGENTS.md`
5. `00. TRPG 세션 매니저 프로젝트 기본 지침.md`
6. `0. TRPG 데이터 프롬프트 통합 마스터 프롬프트.md`
7. 선택 기능의 AGENTS와 마스터 프롬프트
8. 요청에 필요한 공통·하위 지침·템플릿·라이브러리

날짜 없는 `PROJECT AGENTS.md`, 프로젝트 소스 사본, 오래된 로컬 사본과 캐시된 ID가 최신 날짜형 Drive 정본과 다르면 최신 날짜형 프로젝트 에이전트와 실제 Drive 조회 결과를 기준으로 한다.

### 단계 3 — 상태 전이 재현

사용자 입력 하나를 넣고 아래 항목을 순서대로 기록한다.

1. 요청 분류
2. 기능·점검 흐름 안내와 시작 승인 여부
3. 선택된 기능과 근거
4. 읽은 정본 문서
5. 부족 자료와 처리 방식
6. 확인서·초안·장면 목록 등 현재 확정 단위
7. `다음` 입력 전후의 상태 변화
8. 생성·검수·Drive 저장 또는 ZIP 대체 결과
9. SESSION PROGRESS 변화

이미지 기능은 기능 안내 → 시작 승인 → 자료 확인 → 15개 섹션 렌더링 Markdown 요구사항 확인서 → 최종 영어 프롬프트 → P00~P10 점검·자동 교정 → 통과본 → `다음` → 생성 → 검수 → Drive 저장 순서를 재현한다.

### 단계 4 — 기대 결과 대조

각 항목을 아래 상태 중 하나로 판정한다.

| 판정 | 의미 |
| --- | --- |
| 통과 | 유스케이스의 기대 처리와 실제 동작이 일치 |
| 부분 통과 | 핵심 결과는 맞지만 설명·상태 기록·보조 절차가 누락 |
| 실패 | 라우팅·정본성·승인·저장·다음 전이 중 핵심 규칙 위반 |
| 차단 | 필수 자료 또는 도구 권한이 없어 정상 처리 여부를 판정할 수 없음 |
| 정책 미결 | 최신 지침끼리도 단일 기대 결과를 만들 수 없음 |

### 단계 5 — 원인 분류

실패는 가장 직접적인 원인 하나를 먼저 선택한다.

| 코드 | 원인 |
| --- | --- |
| ROU | 잘못된 기능 라우팅 또는 인접 기능 혼동 |
| STA | 시작 전 기능·점검 안내 또는 시작 승인 처리 오류 |
| SRC | 정본·출처·원본 로그·자산 탐색 누락 |
| PRI | 충돌 우선순위 또는 공개 수준 판정 오류 |

| IMG | 이미지 승인·재승인·검수 계약 오류 |
| STY | 정식 스타일 선택·앵커 호출·마감 정책·기능성 예외·`dev_` 격리·승격 계약 오류 |
| OUT | 산출물 형식·수량·비율·레이아웃 계약 오류 |

| REC | SESSION PROGRESS 또는 검증 기록 오류 |

### 단계 6 — 교정 위치 결정

교정은 가장 높은 공통 진입점에서 시작하되, 기능 고유 계약은 해당 기능 문서에서 고친다.

| 오류 범위 | 우선 교정 문서 |
| --- | --- |
| Drive 저장, ZIP 대체, 최신 정본, `다음` 전역 의미 | 프로젝트 AGENTS → TRPG 데이터 AGENTS → 프롬프트 AGENTS → 기본 지침 → 통합 마스터 |
| 시작 전 기능·점검 안내, `프로세스 점검` 예약어 | 프로젝트 AGENTS → TRPG 데이터 AGENTS → 프롬프트 AGENTS → 기본 지침 → 통합 마스터 → 공통 AGENTS·마스터 |
| 이미지 승인·재승인·검수·저장 | 이미지 생성 공통 운영 지침 → 이미지 승인 절차 → 영향 이미지 기능 AGENTS·마스터 |
| 정식 스타일·앵커·마감·기능성 예외 | 이미지 모듈 AGENTS·마스터 → `라이브러리/스타일/정식 스타일 호출 규칙.md` → 선택 스타일 계약 → `공통 붓터치 마감 규칙.md` → 영향 이미지 기능 AGENTS·마스터 |
| 신규 스타일 개발·격리·승격 | `라이브러리/스타일/스타일 개발 및 승격 규칙.md` → `TRPG 데이터/20. 그림 스타일 분석/<스타일명>/` 패키지 → 중앙 정식 스타일 호출 규칙 → 이미지 모듈 AGENTS·마스터 |
| 룰북 출처·Legacy·공식/커스텀 | 4번 룰북 마스터와 세부 지침 |
| 설정 공개 수준·정본·템플릿 | 5번 설정 마스터와 점검·템플릿 수칙 |
| 세션 설계 순서·장면·맵·UUID | 8번 세션 마스터와 해당 세부 지침 |
| 집필 과제·원문·문체 프로필 | 9번 집필 데이터 체크 AGENTS·마스터 → 과제·원문 기록 지침 → 문체 분석 지침 → `TRPG 데이터/19. 집필 데이터` 정본 |
| 특정 제작기 경계 | 7번 창작 지원 공통과 해당 제작기 마스터 |
| FVTT 버전·자동화 | 6번 FVTT 마스터와 전용 가이드 |

상위 문서와 하위 문서가 같은 전역 규칙을 다룰 때에는 한쪽만 수정하지 않는다. 변경 후 영향을 받는 모든 진입 문서를 다시 읽어 같은 의미인지 확인한다.

### 단계 7 — 재검증과 Drive 반영

- 교정 문서를 수정·검수한 뒤 해당 정본 Drive 파일을 직접 갱신한다.
- 기존 문서의 교정은 원래 파일명과 Drive ID를 유지한다.
- 신규 검증 기록과 신규 지침은 기능 또는 공통의 명확한 기본 경로에 Drive 생성한다.
- Drive 갱신 실패 시에만 같은 경로·파일명을 보존한 ZIP을 제공한다.
- 같은 유스케이스를 처음부터 다시 재현해 통과 여부를 확인한다.
- 실패가 남으면 완화 표현으로 통과 처리하지 않고 차단·정책 미결·실패 중 하나로 유지한다.

### 이미지 스타일·앵커·개발 스타일 회귀 검증

`UC-I16`부터 `UC-I29`까지를 검증할 때에는 아래를 추가로 확인한다.

1. `라인 웹툰 포트 준비`가 포트레이트 내부 1번으로 라우팅되고 준비 단계에서 요구사항 확인서·생성을 시작하지 않는가.
2. 제공 이미지가 있고 스타일 변경 지시가 없을 때 `제공 이미지 그림체 보존`을 선택해 정식 앵커·고정 영어 스타일 블록·공통 붓터치 마감을 자동 삽입하지 않는가.
3. 제공 이미지를 정식 스타일로 변환할 때 디자인 기준 이미지가 스타일 앵커보다 우선 배정되는가.
4. 라인 웹툰 인물·풍경·세션 하이라이트가 중앙 호출 규칙의 최소 조합만 사용하고, 모든 실제 사용 앵커의 픽셀을 확인하는가.
5. 라인 웹툰 풍경·세션 하이라이트에 기존 회화 풍경 앵커 05~09가 자동 혼합되지 않는가.
6. 라인 웹툰풍 배틀맵·게임 아이콘·월드 지도는 `사용자 지정 스타일·기능성 예외`를 유지하며 라인 웹툰 01~17과 고정 영어 그림체 블록을 자동 호출하지 않는가.
7. 공통 붓터치 마감은 선택 스타일 계약이 명시적으로 opt-in한 경우에만 적용되고 라인 웹툰에는 삽입되지 않는가.
8. 신규 스타일 패키지가 `TRPG 데이터/20. 그림 스타일 분석/<스타일명>/`에만 존재하고 최상위 스타일 폴더에는 `dev_`가 없으며, 내부 `dev_` 자산은 정식 런타임에서 자동 호출되지 않고 실패 시안과 승격 후보 앵커가 분리되는가.
9. 정식 승격은 마스터 확정과 승격 체크리스트 통과 뒤 개발 정본을 `20. 그림 스타일 분석`에 보존한 채 `dev_스타일 계약`·`dev_앵커`를 정식 경로로 복사·정규화하고 중앙 호출 규칙에 최소 조합을 등록하는가.
10. 활성 지침·마스터·유저스토리/유스케이스에서 `TRPG 데이터/20. 그림 스타일 분석` 이외의 개발 루트 또는 최상위 `dev_<스타일명>` 지시가 남아 있지 않은가.
10. 개발 단계의 공통 붓터치 마감 opt-in 여부를 정식 승격 시 다시 판정하는가.

위 항목의 실패는 기본적으로 `STY`를 원인 코드로 사용한다. 승인 상태 자체가 잘못되면 `IMG`, 출력 규격이 잘못되면 `OUT`, 저장이 잘못되면 `SAV`를 별도 직접 원인으로 우선할 수 있다.

## 5. 집필 데이터 체크 전용 검증

다음 유스케이스는 `UC-WR01`부터 `UC-WR08`까지를 기준으로 점검한다.

1. 새 요청에서는 소설 과제와 장면 묘사 과제의 차이, 제출·원문 보관·문체 프로필 갱신 절차를 먼저 안내하고 시작 여부를 묻는가.
2. 소설 과제는 장르와 주제만 제시하며 최소 5,000자 조건을 과제 이력에 기록하는가.
3. 장면 묘사 과제는 간결한 장면만 제시하고 룩스테라 여부를 50:50 무작위로 선택해 이력에 남기는가.
4. 제출 원문을 교정·요약·재작성하지 않고 과제별 원문 정본에 그대로 기록하는가.
5. 매 제출마다 분석 근거를 남기고 공통·소설·장면 묘사 프로필을 갱신하는가.
6. 원문·이력·프로필을 생성·수정 직후 Drive에 직접 저장하고, 실패했을 때만 ZIP을 제공하는가.
7. 기존 과제의 교정 요구가 아니라 새 과제를 발급하는가.

실패가 있으면 `WRT`를 우선 원인 코드로 기록하고, 저장 실패는 함께 `SAV`를 기록할 수 있다.

## 6. `다음` 전용 검증

`다음`은 반드시 다음 중 하나의 상태 전이를 만들어야 한다.

| 직전 공개 결과 | `다음` 후 상태 |
| --- | --- |
| 이미지 확인서·최종 프롬프트 | 생성 실행 |
| 이미지 생성·검수 결과 | 결과 채택, 다음 산출물 또는 후속 처리 |
| 세션 한 줄 이야기 | 핵심 이야기 골격 |
| 핵심 사건 흐름 | 장면 목록 |
| 장면 목록 | 장면별 문서 확장 |
| 데이터 초안 | 정식 데이터 작성·검수·Drive 저장 |
| 검토 의견·선택지 | 채택안 반영 또는 다음 분석 단위 |
| 기능·점검 시작 안내 | 안내된 기본 또는 선택 범위를 확정하고 절차 개시 |
| 아직 공개 결과 없음 | 현재 절차의 다음 필수 단계 |

다음 행동은 실패로 판정한다.

- `다음` 뒤에 같은 내용을 다시 확인하라고 묻는 행동
- 시작 안내를 생략하고 새 기능·점검 흐름을 바로 실행하는 행동
- `다음`을 무시하고 대기하는 행동
- `다음`을 이유로 필수 이미지 확인 절차를 생략하는 행동
- `다음`으로 근거 없는 이름·경로·설정 사실을 발명하는 행동
- `다음` 뒤 생성·검수 완료 데이터를 Drive에 저장하지 않는 행동

## 7. Drive 저장 전용 검증

지속 보관 데이터가 생성·수정되면 다음을 확인한다.

1. 저장 대상이 데이터인지 비데이터인지 판정했는가.
2. 대상 정본 경로를 기능 규칙과 현재 구조로 확인했는가.
3. 기존 파일이면 원래 Drive ID와 파일명을 유지했는가.
4. 신규 파일이면 기능별 정본 경로에 생성했는가.
5. Drive 직접 저장을 먼저 시도했는가.
6. 실제 저장 결과를 다시 읽거나 메타데이터로 확인했는가.
7. 실패했을 때만 동일 경로·파일명을 보존한 ZIP을 제공했는가.
8. 반영 실패를 성공처럼 보고하지 않았는가.

## 9. 완료 기준

프로세스 교정 작업은 아래를 모두 만족해야 완료다.

1. 선택 유스케이스의 재현 결과가 통과다.
2. 같은 문제를 일으키는 상위·하위 지침 충돌이 남아 있지 않다.
3. 교정한 문서가 Drive 최신 정본에 실제 반영됐다.
4. 데이터 생성 결과의 Drive 직접 저장·실패 시 ZIP 대체 원칙이 유지된다.
5. `다음`이 현재 결과 확정과 다음 프로세스 진행으로 일관되게 처리된다.
6. 검증 기록과 SESSION PROGRESS가 실제 상태를 과장하지 않는다.
7. 정식 스타일·앵커·마감·기능성 예외 검증은 중앙 호출 규칙과 실제 스타일 계약을 기준으로 통과했다.
8. 신규 스타일 개발 정본은 `TRPG 데이터/20. 그림 스타일 분석/<스타일명>/` 한 곳으로 단일화되어 있고 최상위 폴더에는 `dev_`가 없으며, 정식 승격 전 일반 런타임과 격리되고 승격 절차가 복사·정규화 계약과 일치한다.
