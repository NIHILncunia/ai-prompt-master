# 5. 연속 세션 및 연속성 관리 지침

## 역할

이 문서는 이전 세션에 이어지는 회차와 여러 회차로 구성된 아크를 설계하는 규칙을 정의한다.

## 적용 조건

- 사용자가 이전 세션 이름이나 파일을 지정한다.
- 기존 사건, 인물, 관계, 미해결 문제에 이어지는 회차를 요청한다.
- 여러 세션으로 구성된 연속 이야기를 요청한다.
- 세션 아크 개요를 바탕으로 특정 회차를 상세 제작한다.
- 실제 플레이 결과를 반영해 다음 회차를 수정한다.

## 이전 자료 참조 순서

1. 사용자가 지정한 분석본
2. 같은 스토리명의 직전 분석본
3. 필요한 경우 원본 로그
4. 장기 스토리 정리 문서
5. 기존 세션 아크 개요
6. 사용자가 직접 설명한 최신 플레이 결과

사용자가 제공한 최신 플레이 결과가 기존 기획보다 우선한다.

## 분석본에서 추출할 정보

- 세션 이름
- 최종 위치와 현재 목표
- 밝혀진 진실과 미확정 사실
- PC가 알고 있거나 오해하는 정보
- NPC 및 세력 관계 변화
- 획득하거나 잃은 물건
- 부상과 상태 변화
- 미해결 사건
- 다음 행동으로 약속된 내용

분석본에 필요한 정보가 충분하면 원본 로그 전체를 다시 읽지 않는다.

## 원본 로그를 추가로 확인할 조건

- 분석본에 말투나 감정 맥락이 부족하다.
- 중요한 선택의 정확한 이유가 필요하다.
- NPC 태도 변화를 판단해야 한다.
- 특정 대사나 장면을 직접 이어야 한다.

원본 로그에 없는 내용을 과거 사실로 만들지 않는다.

## 이전 이야기 낭독문 작성

연속 세션의 `장면/00. 세션 프롤로그.md`에는 현재 도입부보다 먼저 `## 이전 이야기`를 둔다. 별도 요약 문서를 만들지 않으며, 실제 플레이용 파생본인 `04. [세션 이름] 진행 시트.md`에도 같은 내용을 도입부보다 앞에 복제한다.

이전 이야기는 플레이어가 다음 세션에 필요한 기억을 되찾는 데 목적이 있다. 직전 세션 전체를 사건 목록처럼 나열하지 않고, 이번 회차와 직접 연결되는 핵심 사건·선택·결과·관계 변화·획득 또는 상실·현재 남아 있는 단서를 인과 순서로 압축한다. 가능하면 직전 회차 하나를 중심으로 하되, 현재 회차 이해에 반드시 필요한 경우에만 더 이전 사건을 짧게 회수한다.

사실 내용은 분석본을 기준으로 하며, 원본 로그는 감정 맥락과 GM 묘사 문체를 보완하는 근거로 사용한다. 문체는 정보흐름분석 문서의 목록체를 사용하지 않고 같은 캠페인·같은 아크의 직전 원본 로그에서 확인한 GM 서술의 문장 길이, 호명 방식, 구어적 종결, 장면 전환 호흡을 따른다. 각 서술 문단은 다른 실제 플레이용 묘사와 동일하게 3~4개의 완결된 문장으로 구성한다.

이전 이야기는 직전 상태와 미해결 목표를 상기시키는 지점에서 끝낸다. 이어지는 `## 세션 도입부 묘사`는 현재 시점과 현재 장소를 새로 보여 주어야 하며, 이전 이야기의 마지막 문장을 단순히 되풀이하지 않는다.

## 사실 구분

- 확정 사실
- 플레이어가 알고 있는 사실
- 플레이어의 추측
- NPC의 주장
- 미확정 사실
- GM만 아는 기획 정보

플레이어의 추측이나 NPC의 거짓말을 세계의 사실로 확정하지 않는다.

## 관계 변화 반영

이전 세션의 신뢰, 경계, 빚, 배신감, 존경, 두려움, 의존, 경쟁, 오해, 죄책감을 다음 회차의 행동에 반영한다.

관계 변화는 수치보다 행동으로 보여준다.

- 정보를 먼저 공유한다.
- 중요한 순간에 주저한다.
- 공개적으로 협력하지만 단둘이 있기를 피한다.
- 부탁을 받아들이되 대가를 요구한다.

## 미해결 사건 관리

미해결 요소를 다음처럼 구분한다.

- 이번 회차의 중심
- 보조 요소
- 배경에서 진행
- 잠시 보류
- 장기 떡밥

모든 미해결 사건을 한 회차에 동시에 해결하지 않는다.

## 연속 세션 아크 설계

아크 개요에는 다음을 포함한다.

- 아크명과 핵심 갈등
- 현재 상황
- 주요 세력과 NPC
- 각자의 목적
- 최종적으로 드러날 진실
- 플레이어가 바꿀 수 있는 지점
- 회차별 사건·발견·선택
- 예상 절정
- 가능한 결말 방향
- 확정하지 않을 요소

## 회차별 설계

각 회차에는 독립적인 목표와 변화가 있어야 한다.

- 아크에서 담당하는 기능
- 시작 상황
- 핵심 사건
- 반드시 드러날 정보
- 플레이어가 바꿀 수 있는 것
- 회차 내 절정
- 종료 시 남는 변화
- 다음 회차로 이어질 가능성

한 회차가 단순 이동이나 설명만 담당하지 않게 한다.

## 실제 플레이 결과 반영

다음 회차를 만들 때 기존 아크 개요보다 실제 플레이 결과를 우선한다.

- 예상과 다른 동맹
- NPC의 사망 또는 생존
- 장소의 파괴
- 획득하지 못한 정보
- 플레이어가 만든 새로운 계획
- 적대 세력의 예상 밖 손실
- 약속과 빚
- 새롭게 생긴 관심사

기획을 지키기 위해 플레이 결과를 되돌리지 않는다.

## 유연하게 둘 요소

- 주요 NPC의 최종 선택
- 최종 적대 세력
- 절정 장소
- 일부 회차 순서
- 진실이 공개되는 방식
- 아크 종료 후 관계

## 유지할 요소

- 핵심 갈등의 원인
- 설정 정본
- 이미 확정된 과거
- 플레이어가 확인한 사실
- 사용자가 고정한 테마와 금지 요소

## 독립 사건과 장기 스토리

연속 캠페인 안에서도 독립 사건을 만들 수 있다.

현재 지역, 기존 관계, 평판, 최근 사건의 여파, 장기 떡밥의 작은 징후, 이전에 얻은 물건이나 정보를 자연스럽게 반영할 수 있다.

모든 독립 사건을 장기 스토리의 핵심 음모와 연결하지 않는다.

## 연속성 인수인계

세션 문서의 `이후에 남는 변화`에는 다음을 정리한다.

- 확정된 결과
- 달라진 관계
- 확보한 정보
- 잃은 자원
- 남은 위협
- 다음에 가능한 행동
- 아직 미확정인 요소

실제 플레이 후에는 3번 로그 분석 기능의 분석본이 다음 회차 제작의 우선 자료가 된다.

## 로그 분석 연동용 장면·맵 식별 규칙

### 영구 장면·맵 식별자

- 모든 신규 세션 설계 장면에는 `scene_uuid`를 부여한다.
- 값은 소문자 표준 UUID 형식으로 작성한다. 예: `5e02c452-01a3-4d9e-8737-8f2b1a0c9d64`.
- 프롤로그와 에필로그도 정식 장면이므로 `scene_uuid`를 가진다.
- `scene_uuid`는 장면 번호·장면명·파일명이 바뀌어도 유지한다. 장면을 다른 장면과 통합하여 정체성이 사라질 때에만 폐기하고, 새 장면에는 새 UUID를 부여한다.
- 모든 신규 맵에는 `map_uuid`를 부여한다.
- 값은 소문자 표준 UUID 형식으로 작성한다. 예: `86a41b2c-761e-4f83-9b06-cd5e2a719840`.
- `map_uuid`는 맵 번호·맵명·파일명이 바뀌어도 유지한다.
- 같은 장소의 단순 상태·조명·배치 변화는 동일 `map_uuid`를 유지할 수 있다. 공간 구조를 다시 설계해 별도 배틀맵 자산으로 취급할 수준이면 새 `map_uuid`를 만들고 필요하면 `derived_from_map_uuid`로 원본 맵 UUID를 기록한다.

### 장면 식별 정보

각 장면 파일은 로그 분석에서 실제 플레이 장면과 의미적으로 대응할 수 있도록 다음 최소 지문을 둔다.

- 주요 장소
- 핵심 사건
- 주요 참여자
- 고유 앵커

장면 식별 정보는 장면 기능 전체를 복제하지 않는다. 장면 역할·시작/종료 조건·공개/숨겨진 정보·이전/다음 연결은 기존 정본 섹션과 `02. 장면 목록`을 사용한다.

### 사용 맵 직접 참조

- 맵이 필요 없는 장면은 `## 사용 맵` 아래에 반드시 `- 없음`을 기록한다. 빈 섹션으로 두지 않는다.
- 맵 하나를 사용하면 `map_uuid`, `공용 맵명`, `사용 범위`를 기록한다.
- 한 장면에서 복수 맵을 사용하면 각 맵을 하위 항목으로 나누고 `사용 범위`를 반드시 기록한다.
- 기존 맵을 재사용하면 같은 물리적 맵 자산은 기존 `map_uuid`를 유지한다.
- 로그 분석은 장면이 매칭된 뒤 이 직접 참조를 따라 맵을 확정하며, 장소명만 보고 설계 맵을 새로 추정하지 않는다.

### 플레이 완료 설계의 역사 보존

- 세션 설계 문서의 `status`는 기본적으로 `draft / confirmed / played`를 사용한다.
- `played`는 해당 장면이 실제 진행되었다는 뜻이 아니라, 해당 세션이 이미 플레이되어 그 설계 문서가 역사적 의도 기록으로 동결되었다는 뜻이다.
- 실제 진행 여부는 3번 로그 분석의 `matched / merged / split / skipped / unplanned / uncertain` 대응으로만 판정한다.
- `played` 상태에서는 오탈자, 깨진 링크, 잘못된 파일 참조 같은 정정은 허용하지만 장면 목적·핵심 사건·맵 구조를 당시와 다르게 소급 재작성하지 않는다.
- 플레이 후 실제 결과와 설계의 차이는 설계 문서를 고쳐 없애지 않고 3번 로그 분석에 기록한다.
- 기존 자료는 일괄 마이그레이션하지 않는다. 신규 세션부터 적용하고, 기존 세션은 수정·재분석이 필요한 패키지만 새 구조로 점진 승격한다.
