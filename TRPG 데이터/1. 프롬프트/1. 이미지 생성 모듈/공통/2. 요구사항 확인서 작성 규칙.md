# 요구사항 확인서 작성 규칙

## 정본 선언

이 문서는 TRPG 프로젝트의 모든 이미지 생성·수정·재생성·변형·확장 작업에서 사용하는 **요구사항 확인서 고정 양식의 정본**이다.

모든 이미지 생성 계열 기능은 아래 양식을 그대로 사용한다. 작업마다 달라지는 것은 각 항목에 기입되는 내용뿐이며, **번호·섹션 제목·필드명·순서·Markdown 계층 구조를 추가·삭제·재정렬하지 않는다.** 작업에 해당하지 않는 항목도 제거하지 않고 `해당 없음` 또는 `없음`으로 유지한다.

기능별 `AGENTS.md`, 마스터 프롬프트, 하위 지침이 별도 요구사항 확인 양식을 정의하거나 추가 필드를 요구하더라도, 사용자에게 공개하는 요구사항 확인서는 이 문서의 고정 양식을 우선한다. 기능별 세부 정보는 가장 가까운 기존 필드의 값 안에 서술하며 새 섹션이나 새 필드를 만들지 않는다.

## 사용자 공개 형식 하드 게이트

요구사항 확인서는 **플레인 텍스트나 코드 블록으로 출력하지 않는다.** 사용자에게는 실제 Markdown이 렌더링되는 형태로 공개한다.

- 문서 제목은 `## 이미지 생성 요구사항 확인서`를 사용한다.
- 15개 대분류는 `### 1. ...` 형식의 3단계 제목으로 표시한다.
- 각 필드명은 반드시 `**굵게**` 표시한다.
- 단일 값은 `- **필드명:** 값` 한 줄로 작성한다.
- 한 필드에 값이 둘 이상이면 필드명 아래에 **중첩 번호 목록**을 사용한다.
- 이미지별 역할처럼 하위 속성이 있는 경우 상위 항목 아래에 **중첩 불릿 목록**을 사용하고, 하위 필드명도 굵게 표시한다.
- `8. 반드시 유지할 요소`, `9. 변경 가능한 요소`, `10. 반드시 제외할 요소`처럼 본질적으로 복수 항목을 담는 섹션은 번호 목록을 사용한다.
- `15. 최종 해석 > 우선순위`가 복수이면 중첩 번호 목록으로 작성한다.
- 값이 없는 경우에도 필드를 삭제하지 않고 `해당 없음`, `없음`, `미지정` 중 의미에 맞는 값을 적는다.

### 다중값 표기 예시

```md
- **참고 이미지:**
  1. 오리진 비공정 1층 배틀맵
  2. 오리진 비공정 외관 컨셉 이미지
```

### 계층형 표기 예시

```md
- **이미지 1:**
  - **역할:** 공간 구조 참고
  - **유지할 요소:** 중앙 식당의 위치와 공간 성격
  - **참고만 할 요소:** 탑뷰 도식 표현과 정확한 치수
```

문서 내부에서 양식을 설명하기 위해 Markdown 코드 블록을 사용할 수는 있지만, **실제 사용자 응답에서는 코드 블록 바깥의 렌더링된 Markdown으로 출력한다.**

## 고정 양식 운영 규칙

1. 사용자에게 공개하는 요구사항 확인서는 항상 위 15개 섹션과 필드를 같은 순서로 사용한다.
2. 사용자 공개 시 위 예시의 코드 펜스를 그대로 출력하지 않고, 실제 Markdown 제목·굵기·중첩 목록이 렌더링되도록 작성한다.
3. 필드명은 모두 굵게 표시한다. `작업명:`처럼 굵기 없는 평문 필드명을 사용하지 않는다.
4. 단일 값은 한 줄에 기록한다.
5. 한 필드에 값이 둘 이상이면 쉼표로 길게 연결하지 않고 해당 필드 아래 중첩 번호 목록으로 분리한다.
6. 하위 속성이 있는 항목은 상위 항목 아래 중첩 불릿 목록을 사용한다.
7. 사용하지 않는 필드도 생략하지 않는다. `해당 없음`, `없음`, `미지정` 중 의미에 맞는 값을 적는다.
8. 기능별 전용 요구는 새 섹션을 추가하지 않고 기존 필드에 배치한다.
9. 참고 이미지가 없더라도 `11. 참고 이미지 역할`을 삭제하지 않고 `해당 없음`으로 작성한다.
10. 신규 생성이면 `13. 수정 작업 전용`을 삭제하지 않고 전 항목을 `해당 없음`으로 작성한다.
11. 미확정 요소를 사용자 확정 사항처럼 표현하지 않는다. 모델 재량으로 둘 수 있는 내용은 `14. 미확정 사항`에 구분한다.
12. 요구사항 확인서 다음에는 별도 `## 최종 영어 프롬프트` 블록을 공개한다. 최종 영어 프롬프트는 요구사항 확인서의 필드가 아니므로 15개 섹션 안에 끼워 넣지 않는다.
13. 요구사항 확인서와 최종 영어 프롬프트가 모두 공개되고 공통 점검을 통과하기 전에는 생성 승인을 요청하거나 이미지 생성 도구를 호출하지 않는다.

## 프로젝트 전용 정보 매핑 규칙

프로젝트 내부의 스타일·앵커·기능 계약 정보도 고정 양식을 깨지 않고 다음과 같이 기록한다.

- 그림체 적용 방식, 선택 정식 스타일, 고정 영어 그림체 블록·공통 마감 블록 적용 여부는 `6. 시각 스타일 > 렌더링/그림체`의 값에 요약한다.
- 스타일 앵커·디자인 기준 이미지·프로젝트 공식 이미지는 `2. 입력 자료`에 기록하고, 각 이미지가 무엇을 결정하는지는 `11. 참고 이미지 역할`에 기록한다.
- 산출물 구도 분류는 별도 필드를 만들지 않고 `5. 화면 구성`의 구도·카메라 거리·프레이밍 값으로 표현한다.
- 출력 계약, 생성 수량, 투명 배경, 파일 성격 등은 `7. 출력 규격`과 필요 시 `15. 최종 해석`에 반영한다.
- 완성형 토큰의 대상 유형·등급·자동 프레임·기준 이미지 정보는 `2. 입력 자료`, `4. 피사체`, `7. 출력 규격`, `12. 연속성 조건`의 기존 필드에 배치한다.
- P01~P10 점검 결과와 자동 교정 내역은 새 필드를 만들지 않는다. `15. 최종 해석 > 작업 가능 여부`에 `가능 — P01~P10 통과 / 자동 교정: 없음` 또는 실제 교정 요약을 함께 기록한다.
- 점검이 실패했거나 사용자 확인이 필요한 필수 항목이 남아 있으면 `작업 가능 여부`를 `확인 필요`로 기록하고 승인 요청을 붙이지 않는다.

## 금지 사항

- 요구사항 확인서를 플레인 텍스트 또는 `text` 코드 블록으로 사용자에게 출력하지 않는다.
- 필드명의 굵기 표현을 제거하지 않는다.
- 복수 값을 한 줄의 쉼표 나열로 평탄화하지 않는다.
- 중첩되어야 할 정보를 동일 깊이의 평면 목록으로 출력하지 않는다.
- 기능마다 다른 요구사항 확인서 레이아웃을 사용하지 않는다.
- 기존 필드를 삭제하거나 필드명을 바꾸지 않는다.
- 기능별 편의를 위해 새 번호·새 섹션·독립적인 `스타일 통제`, `산출물`, `대상 해석`, `추정한 요소` 섹션을 추가하지 않는다.
- 최종 영어 프롬프트를 요구사항 확인서 내부 필드처럼 섞지 않는다.
- `프롬프트 점검 결과`, `자동 교정 내역`을 별도 공개 필드로 추가하지 않는다. 고정 양식의 `15. 최종 해석 > 작업 가능 여부`에 통합한다.
