# 이미지 생성 공통 승인 절차

## 공통 폴더 운영 진입점과 동기화

이 폴더의 `AGENTS.md`, `1. 이미지 생성 공통 승인 절차.md`와 `6. 이미지 생성 프롬프트 점검 및 교정 지침.md`는 함께 공통 이미지 정책의 운영 진입점으로 취급한다. 이미지 생성 계열 기능이 이 폴더를 직접 참조할 때에는 프롬프트 루트 `AGENTS.md`, 로컬 `AGENTS.md`, 이 승인 절차, 해당 기능의 로컬 `AGENTS.md`와 마스터 프롬프트를 확인하고, 요구사항 확인서와 영어 프롬프트 초안을 조립한 뒤 6번 점검 지침을 적용한다.

승인 상태 정의, 첫 응답 절차, 재승인 조건, 공통 확인 양식이나 파일 작업 정책을 바꾸면 이미지 생성 모듈 내부 활성 기능 `1·2·3·4·5·6·7·8`의 `AGENTS.md`와 마스터 프롬프트를 함께 점검한다. 내부 5번은 캐릭터 레퍼런스 V2 생성이다. 기능별 화풍·출력 형식·구도 규칙은 각 기능 폴더가 소유하며 이 공통 문서에 복제하지 않는다.

전역 정책 변경은 `TRPG 데이터/AGENTS.md`, `TRPG 데이터/1. 프롬프트/AGENTS.md`, `00. TRPG 세션 매니저 프로젝트 기본 지침.md`, `0. TRPG 데이터 프롬프트 통합 마스터 프롬프트.md`까지 전파한다.

## 문서 목적

이 문서는 TRPG 데이터 프롬프트 체계의 모든 이미지 생성 계열 요청에 적용되는 공통 승인 절차다.

포트레이트, 완성형 VTT 토큰, 캐릭터 레퍼런스 시트, 풍경 이미지, 배틀맵, 세션 하이라이트 이미지, 이미지 수정, 이미지 재구성, 참고 이미지 기반 재생성 요청은 모두 이 절차를 먼저 따른다.

## 최우선 이미지 생성 하드 게이트

이미지 생성 계열 요청에서는 이미지 생성 / 수정 도구 호출보다 이 확인 절차가 항상 먼저다.

- 첫 응답에서는 절대로 `image_gen` 또는 그에 준하는 이미지 생성 / 수정 도구를 호출하지 않는다.
- 사용자가 `생성`, `진행`, `다음`, `1번 실행`, `생성해줘`, `그려줘`, `만들어줘`, `바로 생성`, `create`, `generate`, `draw`, `render`라고 말해도, 승인 절차가 완료되기 전에는 그 말 자체를 도구 호출 승인으로 해석하지 않는다.
- 승인 상태는 어시스턴트가 같은 대화 흐름에서 공통 점검을 통과한 요구사항 확인서와 최종 영어 프롬프트를 먼저 공개한 뒤, 사용자가 그 해석을 보고 명시적으로 승인했을 때만 성립한다.
- 승인 상태가 성립하기 전의 `생성` 계열 표현은 전부 `요구사항 확인 절차를 시작하라`는 뜻으로 처리한다.
- `확인 없이 생성`, `확인 필요 없음`, `사전 확인 생략`, `바로 생성`, `즉시 만들어` 같은 표현도 이 하드 게이트를 우회하지 못한다.
- 프롬프트만 요청한 경우에는 이미지를 생성하지 않는다.

## 승인 상태 정의

승인 상태는 아래 네 조건이 모두 충족될 때만 성립한다.

1. 어시스턴트가 요청 유형과 기능 번호를 판별했다.
2. 요구사항 확인서와 최종 영어 프롬프트 초안이 `6. 이미지 생성 프롬프트 점검 및 교정 지침.md`의 필수 항목을 모두 통과했다.
3. 어시스턴트가 통과한 한국어 요구사항 확인서와 최종 영어 프롬프트를 사용자에게 공개했다.
4. 사용자가 그 확인서를 본 뒤 `생성`, `진행`, `승인`, `이대로 생성`, `좋다`, `확정`, `다음`, `go`, `generate it`처럼 명시적으로 승인했다.

위 세 조건 중 하나라도 충족되지 않으면 이미지 생성 / 수정 도구를 호출하지 않는다.

### `다음` 명령의 단계별 해석

- 요구사항 확인서와 최종 영어 프롬프트가 공개되기 전의 `다음`은 준비·해석·자료 확인 등 현재 절차의 다음 단계 진행으로 처리하며, 이미지 생성 승인으로 해석하지 않는다.
- 요구사항 확인서와 최종 영어 프롬프트를 공개하고 생성 여부를 묻는 상태에서 사용자가 `다음`이라고 응답하면, `생성`·`진행`·`승인`과 동일한 명시적 승인으로 해석하여 직전 확인서의 생성 작업을 즉시 실행한다.
- 이미지 생성이 완료된 뒤 입력된 `다음`은 다음 산출물·프레이밍·변형·시안으로 넘어가라는 요청으로 해석한다. 이 경우 소모된 승인 상태를 재사용하지 않고 새 요구사항 확인서와 최종 영어 프롬프트를 공개한 뒤 다시 승인받는다.
- 사용자가 `프롬프트만`, `생성 전에 검토` 등 실제 생성을 제외한 범위를 명시한 상태에서는 `다음`만으로 이미지 생성을 시작하지 않는다. 실제 생성으로 전환하려면 사용자가 생성 의사를 별도로 명시해야 한다.


## 첫 응답 고정 처리

이미지 생성 계열 요청을 받으면 첫 응답은 아래 순서를 따른다.

1. 요청 유형을 판별한다.
2. 필요한 기능 폴더와 마스터 프롬프트 기준을 확인한다.
3. 제공 이미지의 그림체를 보존할지, 사용자가 명시한 정식 스타일로 변경할지 판정한다.
4. 정식 스타일을 적용하면 사용할 앵커의 실제 픽셀을 확인한다.
5. 사용자의 요구사항을 해석한다.
6. 아래 `요구사항 확인 양식`과 최종 영어 프롬프트의 초안을 작성한다.
7. `6. 이미지 생성 프롬프트 점검 및 교정 지침.md`의 P01~P10을 검사하고 실패 항목을 자동 교정한다.
8. 전 항목을 통과한 요구사항 확인서와 최종 영어 프롬프트를 함께 공개한다.
9. 마지막에 `위 해석과 최종 프롬프트로 생성할까요?`라고 확인한다.

이 첫 응답에서는 이미지를 생성하지 않는다.

기능별 마스터가 더 구체적인 확인 양식을 정의한 경우, 공통 필드를 유지하면서 해당 기능의 필드를 추가한다.

도구 참조 한도 때문에 앵커를 제외한 경우 `제외한 스타일 앵커와 사유`에 해당 파일명과 참조 예산 축소 사유를 적는다. 이 경우 제외된 앵커를 `해당 없음`으로 표시하지 않는다.

### 스타일 프롬프트 조립 규칙

- 제공 이미지 그림체 보존이 선택되면 해당 이미지의 그림체와 마감을 기준으로 기술하며 정식 스타일 블록과 공통 마감 블록을 자동 삽입하지 않는다.
- `애니 페인팅` 또는 `붓터치 반실사`가 선택되면 해당 스타일 계약의 고정 영어 그림체 블록과 `공통 붓터치 마감 규칙.md`의 고정 영어 마감 블록을 문장 변경 없이 삽입한다.
- 기능별 가변 프롬프트는 대상·디자인·행동·포즈·카메라·배경·출력 규격만 담당한다.
- 스타일 앵커의 인물·의상·팔레트·포즈·카메라·배경·구성을 최종 프롬프트의 긍정 조건으로 가져오지 않는다.
- 조립한 문안은 공개하기 전에 `6. 이미지 생성 프롬프트 점검 및 교정 지침.md`의 전체 점검을 통과해야 한다.

## 기능별 산출물 계약 하드 게이트

하나의 승인 상태는 하나의 생성 작업만 승인한다.

생성 작업의 출력 수, 캔버스 구성, 단일 뷰 또는 다중 뷰 여부는 선택된 기능의 마스터 프롬프트가 정의한 산출물 계약을 따른다.

- 공통 승인 절차는 모든 기능을 단일 캐릭터·단일 뷰로 제한하지 않는다.
- 레퍼런스 시트, 아이콘 스프라이트, 지도 범례처럼 기능 정의상 복수 요소가 필요한 산출물은 해당 기능 계약 안에서 허용한다.
- 서로 다른 기능 또는 서로 다른 프레이밍은 하나의 생성 작업으로 합치지 않는다.
- 한 승인 상태를 사용해 기능 계약 밖의 추가 이미지를 자동 생성하지 않는다.

## 1번 이미지 생성 모듈 내부 1번 반실사 포트레이트 승인 처리

반실사 포트레이트는 `전신 9:16 → 전신 확정 → 동일 개체 흉상 9:16 또는 완성형 VTT 토큰 1:1` 파이프라인을 사용한다. 사용자 업로드 이미지를 기준으로 한 완성형 토큰은 전신 단계를 거치지 않는 직접 경로다.

### 전신 단계

1. 전신용 요구사항 확인서와 최종 영어 프롬프트를 공개한다.
2. 사용자가 명시적으로 승인한다.
3. 전신 9:16 이미지 1장을 생성하고 해당 승인 상태를 소모한다.

### 전신 확정

- 생성된 전신의 정체성, 얼굴, 머리, 의상, 장비, 색상, 종족 특징을 사용자가 확정한다.
- 전신이 수정되면 수정 결과가 다시 확정되기 전에는 흉상 단계로 넘어가지 않는다.

### 흉상 단계

1. 확정 전신을 기준 이미지로 삼아 흉상용 요구사항 확인서와 최종 영어 프롬프트를 공개한다.
2. 사용자가 흉상 생성을 명시적으로 승인한다.
3. 동일 개체의 흉상 9:16 이미지 1장을 생성하고 해당 승인 상태를 소모한다.

흉상은 독립적인 재설계가 아니다. 확정 전신의 얼굴·머리·의상·장비·색상과 정체성을 보존한 확대·파생 결과물이어야 한다.

### 완성형 토큰 단계

1. 확정 전신 또는 사용자 업로드 이미지를 기준 이미지로 판정한다.
2. 대상 유형, 자동 적용 토큰 계열과 판단 근거, 일반·엘리트·보스 등급, 자동 원형 프레임, 캐릭터가 포함되고 프레임 바깥을 WebP alpha로 투명하게 유지한 1:1 WebP 1장 계약을 요구사항 확인서와 최종 영어 프롬프트에 공개한다.
3. 사용자가 완성형 토큰 생성을 명시적으로 승인한다.
4. 캐릭터를 재생성하지 않고 기준 이미지를 원형 배치·미세 보정·자동 프레이밍·투명 처리하여 토큰 1장을 생성한다.

완성형 토큰은 전신·흉상·다른 토큰의 승인 상태를 재사용하지 않는다. 빈 프레임, 중앙 `#FFFFFF` 원형, 별도 프레임 PNG는 완성형 토큰 계약에 포함하지 않는다.

## 산출물 계약 검증

도구 호출 직전 다음을 검증한다.

1. 선택된 기능과 실행 모드가 하나로 확정되었는가
2. 요구사항 확인서와 영어 프롬프트가 같은 산출물 계약을 가리키는가
3. 사용자 승인이 해당 계약 이후에 이루어졌는가
4. 다른 기능이나 다른 프레이밍의 산출물이 섞이지 않았는가
5. 기능이 허용하지 않은 추가 이미지가 암시되지 않았는가
6. 그림체 기준과 실제로 확인한 스타일 앵커의 전체 파일명이 공개되었는가
7. 정식 스타일을 적용할 때 고정 영어 그림체 블록과 공통 고정 영어 마감 블록이 원문 그대로 들어갔는가
8. 스타일 앵커의 콘텐츠·구성 요소가 요구사항으로 섞이지 않았는가
9. 요구사항 확인서의 `프롬프트 점검 결과`가 `통과`이며 실행 문안이 공개·승인된 문안과 동일한가

검증에 실패하면 도구를 호출하지 않는다. `6. 이미지 생성 프롬프트 점검 및 교정 지침.md`에 따라 확인서와 최종 영어 프롬프트를 교정하고 새 승인을 받는다.

## 프롬프트만 요청한 경우

사용자가 `프롬프트만`, `프롬프트 생성`, `prompt only`, `최종 프롬프트만`, `생성 전에 검토`라고 요청하면 이미지를 생성하지 않는다.

이 경우 최종 영어 프롬프트만 제공하거나, 필요한 경우 한국어 해석과 최종 영어 프롬프트를 함께 제공한다. 이 범위가 유지되는 동안에는 사용자가 `다음`이라고 입력해도 이미지 생성을 시작하지 않는다.

## 승인 후 실행

승인 상태가 확인되면 승인된 기능별 산출물 계약에 해당하는 생성 작업만 실행한다.

- 생성 작업이 완료되면 승인 상태를 소모한다.
- 생성 완료 후의 `다음`은 다음 산출물 요청으로 처리하며, 새 확인서와 최종 영어 프롬프트를 공개한 뒤 다시 승인받는다.
- 같은 승인을 다음 프레이밍, 다음 변형, 다음 기능에 재사용하지 않는다.
- 여러 독립 파일을 요청받았다면 기능별 규칙에 따라 각각 별도의 승인 상태를 성립시킨다.
- 반실사 포트레이트의 전신과 흉상은 하나의 고정 파이프라인이지만, 두 이미지 생성 호출은 각각 별도 승인 상태를 사용한다.

## 생성 후 자가검수와 결과 보고

생성 결과는 이미지 자체만 제시하고 종료하지 않는다. 생성 직후 어시스턴트가 결과를 직접 확인하여, 승인된 요구사항 확인서와 선택된 기능의 산출물 계약을 기준으로 자가검수한다.

### 공통 확인 항목

1. 요청한 대상·정체성·핵심 외형 또는 환경이 반영되었는가.
2. 기능별 생성 수량, 비율, 구도, 캔버스 구성과 독립 파일 계약을 지켰는가.
3. 반드시 반영할 요소와 사용자 제공·공식 참고 자료의 보존 조건을 충족했는가.
4. 피해야 할 요소, 다른 기능·프레이밍 혼입, 주요 시각 오류 또는 산출물 계약 위반이 없는가.
5. 기능 전용 검수 규칙이 있을 때 그 필수 항목을 모두 충족했는가.

확인할 수 없는 항목은 통과로 추정하지 않고 `확인 불가`로 기록한다. 취향 차이처럼 계약 위반이 아닌 항목은 재생성 사유와 구분하여 선택 개선안으로 제시한다.

### 판정과 후속 처리

- 핵심 계약 위반이나 결과 사용을 방해하는 오류가 있으면 `판정: 재생성 권고`로 표시한다. 실패 항목, 근거, 수정 방향을 밝히고 수정된 한국어 요구사항 확인서와 최종 영어 프롬프트를 제시한다. 새 생성은 마스터가 다시 명시적으로 승인한 뒤에만 실행한다.
- 핵심 항목이 모두 충족되면 `판정: 사용 권고`로 표시한다. 통과한 핵심 근거와 남아 있는 선택 개선안이 있으면 함께 밝힌다.
- 자가검수 결과가 불명확하면 `판정: 확인 보류`로 표시하고, 추정으로 사용 권고나 재생성 결론을 내리지 않는다. 마스터가 확인할 항목 또는 추가 자료를 제시한다.

생성 결과 응답은 최소한 이미지, 자가검수 요약, 판정, 다음 행동을 포함한다. 통과·재생성 권고·확인 보류 어느 경우에도 응답 최하단에 `SESSION PROGRESS`를 표시한다. 재생성 권고에서는 `다음`에 수정 확인서 검토와 재승인을, 사용 권고에서는 확정 또는 다음 산출물 선택을 기록한다.

## 컨셉 이미지와 설정화

- 설정화는 세션 진행과 직접 연관된 중요한 아이템·유물·장치·구조물 등의 디자인과 시각 설정을 확정하기 위한 이미지다.
- 모든 설정화는 가로형 16:9 또는 세로형 9:16 중 하나로 제작한다. 정사각형과 임의 비율은 설정화 산출물로 사용하지 않는다.
- 가로로 긴 무기·장치처럼 대상의 실루엣이 좌우로 펼쳐지는 경우에는 16:9를 우선하고, 세로형 대상이나 인물 중심 설정화는 9:16을 우선한다.
- 설정화의 최종 저장 루트는 `TRPG 데이터/16. 컨셉 이미지/`이며 Google Drive 폴더 ID는 `1ebjSGyH75RCgwV9W0pLqJoOzV5j-QKk-`다.
- `16. 컨셉 이미지`는 프롬프트 기능 번호가 아니라 장기 보관용 산출물 폴더다. 생성 요청은 1번 이미지 생성 모듈에서 목적에 맞는 기존 기능과 공통 승인 절차로 처리한다.
- 하위 폴더는 캠페인·세션·대상·아이템과 시안 수를 기준으로 작업 시점에 판단하여 만든다. 고정된 깊이나 분류 체계를 강제하지 않는다.
- 같은 대상의 여러 디자인 시안은 구분 가능한 파일명으로 모두 보존하며 기존 파일을 덮어쓰지 않는다. 최종 선택과 불필요한 시안 삭제는 마스터가 결정한다.
- 완성형 VTT 토큰 1:1, 캐릭터 레퍼런스 V2 고정 캔버스 등 별도의 기능 고정 계약을 가진 산출물은 이 설정화 비율 규칙의 적용 대상이 아니다.

## 이미지 결과 저장

생성 완료 후 사용자가 보관할 이미지 결과는 기본적으로 로컬 `TRPG 데이터/15. 이미지 생성 결과/<유형>/`에 저장한다. 단, 설정화는 `TRPG 데이터/16. 컨셉 이미지/`에 저장하며 16:9 가로형 또는 9:16 세로형으로만 제작한다. 단, 캐릭터 레퍼런스 시트는 `TRPG 데이터/3. 캐릭터 레퍼런스 이미지/`에 저장하며 하위 분류는 마스터가 정한다.

- `<유형>`은 실제 산출물 목적에 맞게 정한다. 예: `캐릭터`, `배틀맵`, `아이콘`, `아이템`, `풍경`, `세션 하이라이트`, `지도`.
- 필요한 유형 폴더가 없으면 먼저 생성한다.
- 동일 이름의 파일은 덮어쓰지 않고, 구분 가능한 버전 파일명으로 저장한다.
- 이 저장 절차는 이미지 생성 완료 후 수행하며, 요구사항 확인서·프롬프트 공개·명시적 승인으로 구성된 생성 하드 게이트를 대체하거나 우회하지 않는다.

## 금지 사항

- 첫 응답에서 이미지 생성 / 수정 도구를 호출하지 않는다.
- 확인서와 최종 영어 프롬프트 없이 생성하지 않는다.
- `프롬프트 점검 결과: 통과`가 없는 확인서 또는 실패한 프롬프트로 생성을 승인받거나 실행하지 않는다.
- `생성`, `진행`, `다음`, `1번 실행`을 승인 절차 생략으로 해석하지 않는다.
- 사용자가 승인 전에 말한 `바로 생성`, `확인 없이 생성`, `확인 필요 없음`을 도구 호출 승인으로 해석하지 않는다.
- 내부 도구 인자, JSON, 파라미터 객체를 사용자에게 노출하지 않는다.
- 선택된 기능의 산출물 계약과 다른 결과를 같은 생성 작업에 추가하지 않는다.
- 기능 번호와 이미지 유형을 혼동하지 않는다.
