# TRPG 세션 매니저 프롬프트 폴더 표준화 설계안

## 1. 개편 목적

현재 1번부터 19번 기능 폴더는 작성 시기와 기능 성격에 따라 서로 다른 구조를 사용한다.

일부 기능은 `AGENTS.md`와 숫자 문서만 존재하고, 일부 기능은 `README.md`, `템플릿`, `인덱스`, 데이터 폴더 등을 별도로 가진다.

이 차이로 인해 신규 기능을 추가하거나 기존 기능을 수정할 때마다 해당 기능의 구조를 다시 파악해야 한다.

또한 마스터 프롬프트, 세부 지침, 라이브러리, 템플릿, 예시 문서의 역할이 기능마다 다르게 해석될 가능성이 있다.

이번 개편의 목적은 모든 기능 폴더가 동일한 외형과 탐색 규칙을 가지도록 만드는 것이다.

이를 통해 사람과 에이전트 모두 기능 번호만 확인하면 같은 방식으로 문서를 탐색하고 수정할 수 있게 한다.

---

## 2. 개편 대상

이번 개편은 다음 범위를 대상으로 한다.

```text
TRPG 데이터/1. 프롬프트/
├─ 00. TRPG 세션 매니저 프로젝트 기본 지침.md
├─ 0. TRPG 데이터 프롬프트 통합 마스터 프롬프트.md
├─ AGENTS.md
├─ 공통/
└─ 1~19번 기능 폴더/
```

기능 폴더만 정비하지 않는다.

기능 구조와 참조 경로를 관리하는 상위 문서도 모두 함께 점검한다.

---

## 3. 기능 폴더 표준 구조

모든 번호 기능 폴더는 다음 구조를 반드시 가진다.

```text
N. 기능명 프롬프트/
├─ AGENTS.md
├─ README.md
├─ 0. 기능명 마스터 프롬프트.md
├─ 1. 기능 문서.md
├─ 2. 기능 문서.md
├─ ...
├─ 라이브러리/
└─ 템플릿/
```

`라이브러리/`와 `템플릿/`은 사용하지 않는 기능에도 생성한다.

빈 폴더는 누락이 아니라 현재 해당 자료가 존재하지 않음을 의미한다.

---

## 4. 표준 구조를 강제하는 이유

### 4.1 탐색 방식 통일

현재는 기능마다 진입 파일의 번호와 이름이 다르다.

개편 후에는 모든 기능에서 다음 파일을 첫 진입점으로 사용한다.

```text
0. 기능명 마스터 프롬프트.md
```

에이전트는 기능 번호와 관계없이 동일한 순서로 자료를 읽을 수 있다.

### 4.2 신규 기능 확장성

향후 20번 이상의 기능을 만들 때 기존 기능 중 하나를 임의로 복제하지 않아도 된다.

표준 빈 구조를 복사한 뒤 숫자 문서, 라이브러리, 템플릿만 기능에 맞게 채우면 된다.

### 4.3 누락 탐지

모든 기능에 `AGENTS.md`, `README.md`, `라이브러리/`, `템플릿/`이 존재하면 구조 점검이 단순해진다.

하나라도 없다면 의도적 예외인지 판단할 필요 없이 구조 누락으로 처리할 수 있다.

### 4.4 유지보수 자동화

동일한 파일 구조는 향후 스크립트나 에이전트를 통한 검증에 유리하다.

다음 항목을 일괄 검사할 수 있다.

```text
AGENTS.md 존재 여부
README.md 존재 여부
0번 마스터 프롬프트 존재 여부
숫자 문서 번호 연속성
라이브러리 폴더 존재 여부
템플릿 폴더 존재 여부
```

---

## 5. `AGENTS.md` 역할

`AGENTS.md`는 에이전트가 해당 기능을 실행하거나 수정할 때 따르는 운영 지침이다.

사람에게 기능을 소개하는 문서가 아니다.

각 기능의 `AGENTS.md`는 얇은 운영 라우터다. 실행 규칙과 품질 기준을 숫자 문서에 복제하지 않는다.

각 기능의 `AGENTS.md`에는 최소한 다음 내용이 들어가야 한다.

```text
기능의 적용 범위
요청 라우팅 조건
선행 참조 문서
숫자 문서 읽기 순서
공통 라이브러리 의존성
기능 전용 라이브러리 의존성
템플릿 선택 규칙
결과 검수 순서
금지 작업
상위 문서 동기화 조건
```

실제 제작 절차, 출력 세부 규칙, 검수 체크리스트는 0번과 이후 숫자 문서가 담당한다.

에이전트는 README를 탐색 규칙의 정본으로 사용하지 않는다.

실행에 필요한 모든 의존성은 `AGENTS.md`에 명시한다.

---

## 6. `README.md` 역할

`README.md`는 사람이 기능 폴더를 열었을 때 구조와 사용 방식을 이해하기 위한 안내 문서다.

모든 기능의 README는 동일한 목차를 사용한다.

```text
# 기능명

## 기능 개요
## 적용 대상
## 주요 사용 사례
## 파일 구성
## 숫자 문서 적용 순서
## 기능 전용 라이브러리
## 공통 라이브러리 의존성
## 템플릿
## 입력 자료
## 출력 결과
## 관련 기능
## 유지보수 주의사항
```

기능 전용 라이브러리나 템플릿이 없다면 해당 섹션을 삭제하지 않는다.

다음처럼 현재 사용하지 않음을 명시한다.

```text
현재 기능 전용 라이브러리는 없습니다.
현재 기능 전용 템플릿은 없습니다.
```

---

## 7. 숫자 문서 규칙

모든 기능의 숫자 문서는 반드시 `0`부터 시작한다.

`0번`은 항상 해당 기능의 마스터 프롬프트다.

```text
0. 기능명 마스터 프롬프트.md
1. 기능 기본 지침.md
2. 세부 처리 규칙.md
3. 출력 규칙.md
4. 품질 검수 체크리스트.md
5. 기능 예시.md
```

1번 이후 문서의 이름과 개수는 기능별로 자유롭게 구성한다.

모든 기능에 동일한 번호 의미를 강제하지 않는다.

### 번호 연속성

숫자 문서는 중간 번호가 비지 않도록 한다.

```text
허용:
0, 1, 2, 3, 4

금지:
0, 1, 3, 4
```

파일 삭제나 통합으로 번호가 비면 이후 문서를 재번호화한다.

번호 변경 시 해당 파일을 참조하는 모든 문서를 함께 수정한다.

### 색인 예외

`9999.`로 시작하는 문서는 실행 순서에 포함되지 않는 색인·레지스트리다. 예를 들어 `9999. D&D 룰북 소유 리스트.md`는 0번 이후 실행 문서의 연속 번호 규칙에서 제외한다. 이 문서는 요청 유형에 따라 조건부로 읽는다.

---

## 8. 숫자 문서와 폴더 자료의 구분

숫자 문서는 해당 기능의 필수 실행 절차다.

라이브러리와 템플릿은 실행 과정에서 선택적으로 불러오는 자료다.

### 숫자 문서에 둘 자료

```text
마스터 프롬프트
기본 지침
입력 해석 규칙
제작 절차
출력 규칙
검수 체크리스트
예시 문서
```

### 라이브러리에 둘 자료

```text
반복적으로 재사용되는 데이터
선택 가능한 프리셋
표현 사전
명명 사전
아키타입
공용 효과나 특성
기능 전용 참조 데이터
```

### 템플릿에 둘 자료

```text
최종 결과물의 문서 구조
복사해 사용할 수 있는 빈 양식
출력 항목과 섹션 순서
프런트매터 기본 구조
```

---

## 9. 예시 문서 처리

현재 일부 기능은 `예시 라이브러리`라는 이름을 사용한다.

개편 후 예시는 라이브러리 폴더로 옮기지 않고 숫자 문서로 유지한다.

```text
N. 기능 제작 예시.md
```

예시는 선택 데이터보다 품질 기준과 실행 절차의 마지막 단계에 가깝기 때문이다.

예시 문서는 마스터 프롬프트나 검수 문서에서 필요할 때 참조한다.

---

## 10. 체크리스트 처리

품질 검수 체크리스트도 라이브러리로 이동하지 않는다.

체크리스트는 선택 사항이 아니라 필수 검수 절차이므로 숫자 문서로 유지한다.

```text
N. 기능 품질 검수 체크리스트.md
```

마스터 프롬프트는 결과 생성 후 해당 체크리스트를 반드시 적용하도록 지시한다.

---

## 11. 라이브러리 이중 구조

라이브러리는 다음 두 계층으로 분리한다.

```text
공통/라이브러리/
기능 폴더/라이브러리/
```

### 공통 라이브러리

둘 이상의 기능이 동일한 원본을 참조해야 하는 자료를 둔다.

### 기능 전용 라이브러리

특정 기능의 출력 방식이나 처리 절차에 종속되는 자료를 둔다.

---

## 12. 공통 라이브러리를 두는 이유

현재 일부 자료는 여러 기능에서 유사한 내용을 별도로 관리한다.

이 구조에서는 동일한 설정을 수정해도 다른 기능의 문서에는 이전 내용이 남을 수 있다.

공통 라이브러리를 사용하면 하나의 정본을 여러 기능이 참조할 수 있다.

단, 프로젝트 위그드라실의 설정 정본은 공통 라이브러리에 복제하지 않는다. 공통 라이브러리에는 프롬프트 기능이 공유하는 운영 정의와 검증된 재사용 자료만 둔다.

다음 자료가 대표적인 공통 후보다.

```text
종족의 고정 신체 특징
문화권 기본 정의
용종 명명 규칙
정치 체제 분류
공용 태그 사전
공통 문장 지양 표현
여러 기능이 공유하는 세계관 정의
```

---

## 13. 모든 라이브러리를 공통으로 이동하지 않는 이유

모든 라이브러리를 공통 폴더에 넣으면 공통 폴더가 다시 거대한 기능 혼합 폴더가 된다.

반실사 렌더링 규칙, 애니 작화 스타일, 토큰 프레임 장식 규칙은 서로 공유할 필요가 없다.

기능 전용 자료까지 중앙에 모으면 어떤 기능이 어떤 자료를 사용하는지 파악하기 어려워진다.

따라서 공통 라이브러리는 실제 공유가 확인된 자료만 받는다.

---

## 14. 공통 라이브러리 등록 기준

다음 조건 중 하나 이상을 만족하는 자료만 공통 라이브러리 후보로 본다.

```text
둘 이상의 기능이 실제로 사용한다.
하나의 원본만 유지해야 한다.
특정 출력 스타일에 종속되지 않는다.
변경 시 여러 기능에 같은 내용이 반영되어야 한다.
세계관 또는 시스템 전체에서 동일한 정의를 사용한다.
```

단순히 여러 기능에서 비슷한 내용이 보인다는 이유만으로 합치지 않는다.

공통 요소와 기능별 표현 요소를 분리할 수 있는지도 먼저 검토한다.

---

## 15. 기능 전용 라이브러리 등록 기준

다음 조건에 해당하면 기능 폴더의 `라이브러리/`에 둔다.

```text
하나의 기능에서만 사용한다.
특정 이미지 스타일이나 렌더링 방식에 종속된다.
해당 기능의 마스터 프롬프트와 강하게 결합된다.
다른 기능에서 그대로 재사용할 수 없다.
기능 고유 프리셋이나 아키타입이다.
```

예시는 다음과 같다.

```text
1번:
반실사 테마
반실사 클래스 아키타입
반실사 캐릭터 프리셋

11번:
애니 작화 스타일 모드
애니 조명 및 분위기
애니 캐릭터 프리셋

14번:
게임 아이콘 시각 언어

16번:
기본 피해 관련 특성
```

---

## 16. 공통 정의와 기능별 표현 분리

종족 자료처럼 공통성과 기능 종속성이 동시에 있는 자료는 두 층으로 나눈다.

```text
공통/라이브러리/종족/
└─ 종족 공통 시각 정의.md

1번/라이브러리/
└─ 반실사 종족 렌더링 규칙.md

11번/라이브러리/
└─ 애니 종족 렌더링 규칙.md
```

공통 자료는 종족이 반드시 가져야 하는 특징을 정의한다.

기능 전용 자료는 해당 특징을 특정 스타일에서 표현하는 방식을 정의한다.

---

## 17. 공통 폴더 표준 구조

`공통`도 관리 대상이므로 독립적인 표준 구조를 가진다.

```text
공통/
├─ AGENTS.md
├─ README.md
├─ 0. 공통 자료 관리 마스터 프롬프트.md
├─ 1. 공통 자료 등록 및 관리 지침.md
├─ 2. 공통 자료 충돌 처리 지침.md
├─ 라이브러리/
└─ 템플릿/
```

공통 폴더 역시 숫자 문서를 `0`부터 시작한다.

공통 라이브러리 등록·수정·삭제 방법을 명시적으로 관리한다.

---

## 18. 공통 라이브러리 초기 하위 구조

초기에는 다음 분류를 사용한다.

```text
공통/라이브러리/
├─ 세계관 정의/
├─ 종족/
├─ 문화권/
├─ 명명/
├─ 분류 체계/
├─ 문장 규칙/
└─ 공용 데이터/
```

처음부터 지나치게 많은 하위 폴더를 만들지 않는다.

새로운 자료가 기존 분류에 들어가지 않을 때만 새 분류를 추가한다.

---

## 19. 빈 폴더 정책

모든 기능에 빈 `라이브러리/`와 `템플릿/`을 만든다.

빈 폴더는 구조 오류가 아니다.

```text
빈 라이브러리/
→ 현재 기능 전용 재사용 자료가 없음

빈 템플릿/
→ 현재 별도 출력 템플릿이 없음
```

Google Drive에서는 빈 폴더가 유지되므로 `.gitkeep`이나 임시 README를 넣지 않는다.

ZIP 산출물에서는 빈 폴더가 누락되지 않도록 별도 처리가 필요하다.

---

## 20. ZIP의 빈 폴더 유지 방식

일반 ZIP은 빈 폴더 항목을 포함할 수 있다.

최종 ZIP 생성 시 모든 기능의 다음 경로를 명시적으로 추가한다.

```text
라이브러리/
템플릿/
```

빈 폴더 보존을 위해 의미 없는 파일을 생성하지 않는다.

압축 해제 후 실제 디렉터리 구조가 유지되는지 검증한다.

---

## 21. 템플릿 관리 원칙

템플릿에는 최종 출력물의 구조를 정의하는 파일만 둔다.

설명, 예시, 작업 메모는 템플릿 폴더에 넣지 않는다.

템플릿은 다음 특성을 가져야 한다.

```text
빈 양식으로 사용할 수 있다.
고정 섹션 순서가 있다.
출력 구조를 직접 통제한다.
마스터 프롬프트가 선택 기준을 설명한다.
```

템플릿이 여러 개라면 기능 `AGENTS.md`와 0번 마스터 프롬프트에 선택 기준을 적는다.

---

## 22. 라이브러리 참조 방식

각 기능은 공통 라이브러리 전체를 무조건 탐색하지 않는다.

해당 기능에서 사용하는 자료만 `AGENTS.md`에 등록한다.

```text
## 공통 라이브러리 의존성

- `공통/라이브러리/종족/종족 공통 시각 정의.md`
- `공통/라이브러리/문화권/문화권 기본 정의.md`
```

이 방식은 불필요한 자료 탐색과 잘못된 교차 적용을 막는다.

README에도 같은 의존성을 사람용 설명으로 기록한다.

---

## 23. 표준 문서 참조 순서

에이전트의 기본 참조 순서는 다음과 같다.

```text
1. 프로젝트 기본 지침
2. 프롬프트 루트 AGENTS.md
3. 통합 마스터 프롬프트
4. 기능 AGENTS.md
5. 기능 0번 마스터 프롬프트
6. 필요한 기능 숫자 문서
7. 지정된 공통 라이브러리
8. 지정된 기능 전용 라이브러리
9. 선택된 템플릿
10. 품질 검수 문서
```

README는 일반 실행 때 매번 필수로 읽지 않는다.

구조 이해, 유지보수, 파일 추가·삭제 작업에서 우선 확인한다.

## 24. 자료 충돌 우선순위

자료 충돌 시 다음 순서를 기본으로 한다.

```text
1. 현재 대화의 사용자 최신 지시
2. 프로젝트 기본 지침
3. 세계관 및 시스템 공통 정의
4. 기능 AGENTS.md
5. 기능 0번 마스터 프롬프트
6. 기능 숫자 문서
7. 기능 전용 라이브러리
8. 템플릿
```

공통 자료가 모두 기능 자료보다 우선하는 것은 아니다.

세계관의 고정 사실은 공통 정의가 우선하고, 표현 방식은 기능 전용 규칙이 우선한다.

## 25. 통합 마스터 프롬프트 개편

`0. TRPG 데이터 프롬프트 통합 마스터 프롬프트.md`는 이번 개편의 핵심 대상이다.

공통 라이브러리와 기능 전용 라이브러리를 구분한다.

공통 참조 순서를 정의한다.
구조 변경 시 동기화 대상을 정의한다.

기존의 개별 파일명 직접 참조는 모두 새 경로에 맞게 점검한다.

## 31. 정규 구조에서 제외할 파일

다음 자료는 기능 폴더의 정규 구조에 두지 않는다.

```text
검증 보고서
설치 완료 기록
일회성 수정 지침
ZIP 작성 메모
임시 분석 문서
이전 버전 백업
```

계속 보존해야 한다면 별도의 `개발 자료/` 또는 개편 산출물 문서에 포함한다.

비정규 파일은 분류가 끝날 때까지 삭제하지 않는다. 실행에 필요하지 않은 파일은 `개발 자료/`로 이동하고, 이동 전후 경로를 이관 목록에 기록한다.

19번의 `개발 자료/검증 보고서.md`와 `개발 자료/상위 문서 등록 및 동기화 수정 지침.md`는 대표적인 점검 대상이다.

## 32. 1번과 11번의 마스터 번호 정규화

현재 1번과 11번은 마스터 프롬프트가 1번으로 시작한다.

개편 시 다음처럼 변경한다.

```text
1번:
0. 포트레이트 생성 마스터 프롬프트.md

11번:
0. 애니 포트레이트 생성 마스터 프롬프트.md
```

기존 2번 이후 파일은 역할을 다시 분류한 뒤 연속 번호로 재배치한다.

마스터 번호 변경에 따라 모든 직접 참조 경로를 수정한다.

## 33. 라이브러리 파일명 정리

기능 폴더의 `라이브러리/` 안에 들어가는 파일은 이름에 다시 `라이브러리`를 붙이지 않는 방향을 권장한다.

```text
기존:
라이브러리/반실사 테마 라이브러리.md

권장:
라이브러리/반실사 테마.md
```

상위 폴더가 이미 자료의 성격을 나타내므로 파일명이 간결해진다.

다만 기존 링크가 많다면 1차 개편에서는 이동만 수행하고 파일명 정리는 2차 작업으로 분리할 수 있다.

## 34. 템플릿 파일명 정리

템플릿 폴더 내부 파일은 명확성을 위해 `템플릿` 접미사를 유지할 수 있다.

```text
단일 세션 템플릿.md
연속 세션 회차 템플릿.md
클래스 문서 템플릿.md
```

템플릿이라는 성격이 파일명에도 드러나므로 검색 시 유리하다.

## 35. 이관 작업의 단계

### 1단계: 현황 목록 확정

1~19번과 공통 폴더의 모든 파일·폴더 목록을 수집한다.

각 항목을 숫자 문서, 라이브러리, 템플릿, 비정규 파일로 분류한다.

### 2단계: 표준 빈 구조 생성

모든 기능에 다음 항목을 준비한다.

```text
AGENTS.md
README.md
라이브러리/
템플릿/
```

### 3단계: 숫자 문서 정규화

마스터 프롬프트를 0번으로 통일한다.

모든 숫자 문서를 기능별로 연속 번호로 재정렬한다.

### 4단계: 기능 전용 자료 이동

기존 최상위 라이브러리 성격 파일을 해당 기능의 `라이브러리/`로 이동한다.

### 5단계: 공통 자료 분리

실제로 둘 이상의 기능이 공유하는 자료만 `공통/라이브러리/`로 이동한다.

각 기능 AGENTS에 의존성을 등록한다.

### 6단계: 템플릿 이동

문서 양식과 출력 구조 파일을 각 기능의 `템플릿/`에 배치한다.

### 7단계: AGENTS 작성

각 기능의 새 경로, 참조 순서, 공통 의존성, 검수 절차를 반영한다.

### 8단계: README 작성

모든 기능에 공통 목차를 적용한다.

빈 라이브러리와 빈 템플릿 상태도 명시한다.

### 9단계: 기능 마스터 갱신

0번 마스터 프롬프트의 참조 경로와 실행 순서를 새 구조에 맞춘다.

### 10단계: 상위 문서 갱신

통합 마스터 프롬프트, 루트 AGENTS, 프로젝트 기본 지침을 함께 수정한다.

### 11단계: 비정규 파일 정리

임시 보고서와 일회성 지침을 정규 기능 구조에서 제거한다.

### 12단계: 전체 검증

경로, 번호, 중복, 누락, 빈 폴더, 상위 문서 참조를 점검한다.

## 36. 검증 기준

최종 ZIP은 다음 조건을 모두 만족해야 한다.

```text
1~19번 모든 기능 폴더가 존재한다.
모든 기능에 AGENTS.md가 존재한다.
모든 기능에 README.md가 존재한다.
모든 기능에 0번 마스터 프롬프트가 존재한다.
모든 숫자 문서 번호가 연속된다.
모든 기능에 라이브러리 폴더가 존재한다.
모든 기능에 템플릿 폴더가 존재한다.
공통 폴더도 표준 구조를 가진다.
기존 경로를 가리키는 링크가 남아 있지 않다.
비정규 파일이 정규 기능 폴더에 남아 있지 않다.
ZIP 해제 후 빈 폴더가 유지된다.
```

## 37. 링크 검증 방식

파일을 이동하거나 이름을 변경한 뒤 다음 패턴을 전체 검색한다.

```text
기존 마스터 프롬프트 이름
기존 숫자 문서 이름
기존 라이브러리 파일 경로

1번과 11번의 이전 마스터 경로
19번의 비정규 파일 참조
```

검색 결과가 0건이거나 의도적으로 남긴 설명문인지 확인한다.

## 38. 중복 검증 방식

공통 라이브러리로 이동한 자료가 기능 폴더에 복제되어 남지 않았는지 확인한다.

단, 공통 정의와 기능별 표현 규칙처럼 역할을 분리한 경우는 중복으로 보지 않는다.

파일명뿐 아니라 내용도 비교해야 한다.

---

## 39. 개편 시 보수적으로 처리할 항목

공통 라이브러리 이동은 구조 표준화보다 위험도가 높다.

자료를 잘못 합치면 기능별 고유 규칙이 사라질 수 있다.

따라서 1차 ZIP에서는 다음 원칙이 안전하다.

```text
명백한 기능 전용 자료는 기능 라이브러리로 이동한다.
명백한 공통 자료만 공통 라이브러리로 이동한다.
판단이 애매한 자료는 기능 폴더에 유지한다.
```

공통화는 중복 제거보다 정본 안정성을 우선한다.

## 40. 권장 적용 범위

이번 ZIP에서는 다음 작업까지 한 번에 수행하는 것이 적절하다.

```text
전체 기능 폴더 구조 표준화
AGENTS와 README 보강
0번 마스터 프롬프트 통일
숫자 문서 연속 번호화
기능별 라이브러리 폴더 이동
템플릿 폴더 정리
공통 폴더 표준화
상위 세 문서 갱신
비정규 파일 제거 또는 분리
전체 경로 검증
```

다만 공통 라이브러리의 대규모 내용 병합은 별도 점검 결과에 따라 보수적으로 적용한다.

## 42. 최종 설계 원칙

모든 기능은 동일한 기본 구조를 가진다.

모든 기능은 `AGENTS.md`, `README.md`, `라이브러리/`, `템플릿/`을 반드시 가진다.

모든 숫자 문서는 0번부터 시작하며, 0번은 항상 기능 마스터 프롬프트다.

필수 실행 규칙은 숫자 문서로 관리하고, 재사용 자료는 라이브러리로 관리한다.

결과물 구조는 템플릿으로 관리한다.

공통 자료는 검증된 공유 자료만 중앙화한다.

기능 전용 자료는 각 기능의 라이브러리에 유지한다.

구조가 변경되면 통합 마스터 프롬프트, 루트 AGENTS, 프로젝트 기본 지침을 반드시 함께 점검한다.

최종 산출물은 전체 표준 구조를 포함한 ZIP으로 제공하며, 사용자가 기존 프롬프트 폴더를 교체할 수 있는 완전한 형태로 구성한다.
