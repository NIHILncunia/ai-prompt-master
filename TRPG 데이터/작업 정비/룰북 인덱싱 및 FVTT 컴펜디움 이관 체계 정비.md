# 룰북 인덱싱 및 FVTT 컴펜디움 이관 체계 정비

## 상태

- 상태: 룰북별 원본 검증 진행 중
- 시작일: 2026-09-01
- 작업 유형: 룰북 장기 인덱싱·데이터 검증·FVTT 컴펜디움 이관 추적 체계 운영
- 현재 위치: 주분류별 독립 진행 — 데이터북 `Monstrous Compendium Vol. 1: Spelljammer Creatures`, 시나리오북 `Tomb of Annihilation`, 설정북 `Guildmasters’ Guide to Ravnica`
- 후속 실행 주체: Codex

## 시발점

초기 룰북 수집 단계에서는 90권이 넘는 룰북을 하나씩 확보할 때마다 수집 여부를 체크하기 위해 Google Sheets 기반 체크리스트를 사용했다.

그러나 현재는 대부분의 룰북 수집이 끝났고, 새 룰북이 추가될 때마다 체크리스트 자체를 갱신하는 방식으로 업무 성격이 변했다. 이 때문에 별도의 시트는 더 이상 필요하지 않다고 판단했고, 기존 `9999. D&D 룰북 소유 리스트.md`를 룰북 소유·관리의 단일 정본으로 유지하도록 정비했다. 수집 룰북은 같은 파일 안에서 데이터북·시나리오북·설정북의 독립 표로 관리한다.

현재 정본은 실제 수집 룰북 94개와 D&D Beyond 비교 전용 항목 14개를 구분하며, 전체 관리 범위는 108개다. 과거 Google Sheets `룰북 수집 현황`은 역할을 종료하여 제거했다.

이 정비 과정에서 다음 문제가 새로 명확해졌다.

룰북 수가 많아질수록 특정 주문, 클래스, 서브클래스, 몬스터, 아이템 등의 위치를 찾기 위해 다수의 룰북을 반복해서 검색해야 한다. 한 번 찾은 정보의 위치를 다시 찾는 비용도 계속 발생한다.

따라서 앞으로는 룰북을 단순 보유 목록으로만 관리하지 않고, 데이터의 존재 위치를 미리 조사하여 인덱싱하고, 해당 데이터의 추출·검증·FVTT 이관 상태까지 장기적으로 추적하는 체계가 필요하다.

## 마스터의 취지

이 작업의 핵심 목적은 다음과 같다.

1. **검색 비용 선지불**
   - 주문이나 몬스터 등을 요청할 때마다 90권 이상의 룰북을 다시 뒤지지 않는다.
   - 한 번 확인한 데이터의 룰북·파일·페이지 또는 섹션 위치를 인덱스에 남긴다.
   - 이후 질의는 `인덱스 → 대상 룰북 → 원본 검증` 순서로 처리한다.

2. **룰북 추가 이력 추적**
   - 앞으로 새 룰북이 추가되면 언제 관리 대상으로 등록되었는지 추적한다.
   - 기존 자료의 획득일을 Drive 업로드일로 소급 추정하지 않는다.
   - 추적 시작 이전 자료와 추적 시작 이후 자료를 구분할 수 있어야 한다.

3. **룰북별 데이터 제공 범위 재검증**
   - 현재 `9999. D&D 룰북 소유 리스트.md`의 `룰북 유형` 설명은 과거 개략 분류가 포함될 수 있다.
   - 실제 룰북을 다시 확인하면서 클래스, 서브클래스, 종족, 배경, 재주, 주문, 몬스터, 아이템 등 어떤 데이터를 제공하는지 검증한다.
   - 기존 설명과 실제 내용이 다르면 정본의 유형 설명도 갱신한다.

4. **단계적 데이터 추출**
   - 모든 룰북을 한 번에 완전히 처리하는 방식으로 제한하지 않는다.
   - 예: 전체 룰북 클래스 추출 → 서브클래스 추출 → 주문 추출 → 몬스터 추출처럼 데이터 유형 단위로 장기간 진행할 수 있어야 한다.
   - 중단·재개 시 어느 룰북의 어느 유형까지 완료했는지 바로 확인할 수 있어야 한다.

5. **원본 검증과 추출 완료의 분리**
   - 이름이나 위치를 추출했다고 정확성이 보장되는 것은 아니다.
   - `추출 완료`와 `원본 검증 완료`를 별도 상태로 관리한다.
   - 인덱스는 상세 원문 자체의 대체물이 아니라 원문으로 빠르게 이동하기 위한 탐색 장치다.

6. **FVTT 컴펜디움 이관 추적**
   - 룰북에서 확인한 데이터를 Foundry VTT용 컴펜디움 데이터로 옮겼는지 추적한다.
   - 단순 `이관 완료` 표시가 아니라 실제 모듈 저장소에 해당 Document가 존재하는지 크로스체킹한다.
   - 최종적으로는 원본 룰북과 FVTT 데이터의 내용 일치 여부도 검증한다.

7. **장기 진행률의 양방향 검증**
   - Google Drive의 룰북 인덱스가 기대 상태를 관리한다.
   - GitHub의 FVTT 모듈 저장소가 실제 구현 상태를 가진다.
   - 두 상태를 대조해 누락·중복·불일치를 발견할 수 있어야 한다.

## 실제 저장소 분석 결과

### 모듈 기준

현재 `module.json` 기준:

- Foundry VTT minimum: 13
- Foundry VTT verified: 13.351
- D&D5e minimum/verified: 5.2.4
- 현재 실제 등록 Pack:
  - `common-monsters` / Actor
  - `common-feats` / Item
  - `common-items` / Item

현재 `module.json`에 등록된 Pack은 실제 존재 Pack의 정본으로 취급한다.

### Pack 계획

`packs/README.md`와 초기 모듈 설계에는 다음과 같은 추가 Pack 후보가 기록되어 있다.

공통 데이터 후보:

- `common-monsters`
- `common-items`
- `common-spells`
- `common-species`
- `common-rolltables`

룩스테라 후보:

- `luxterra-monsters`
- `luxterra-npcs`
- `luxterra-items`
- `luxterra-spells`
- `luxterra-species`
- `luxterra-journals`
- `luxterra-scenes`
- `luxterra-rolltables`

다만 계획 문서는 현재 실제 Pack의 정본이 아니다. 현재 실제 등록 여부는 항상 `module.json`을 우선한다.

### 현재 구조상 확인된 불일치

- `common-feats`는 현재 `module.json`에 실제 등록되어 있고 LevelDB 디렉터리도 존재한다.
- 반면 기존 `packs/README.md`와 초기 Pack 설계 목록에는 `common-feats`가 빠져 있다.

따라서 향후 인덱싱 설계는 예정 Pack 목록을 하드코딩해서 따라가면 안 된다.

### LevelDB와 검증 기반

현재 `packs/common-monsters`는 실제 LevelDB 데이터가 생성되어 있다.

저장소에는 다음 도구가 존재한다.

- `scripts/seed-common-monsters.js`
  - `common-monsters`가 비어 있을 때 최초 시드 생성
  - `일반`, `엘리트`, `보스` 폴더 생성
  - CR 1~30 × 3등급 = 총 90개 Actor 템플릿 생성
- `data/common-monster-templates.json`
  - 위 90개 템플릿의 원천 작업 데이터
- `scripts/verify-compendium-packs.mjs`
  - `module.json`을 읽고 실제 Pack LevelDB를 연다.
  - Pack별 Document 개수와 폴더 이름을 요약한다.

현재 검증 스크립트는 개수·폴더 중심이며, 장기적인 인덱스 크로스체크를 위해 향후 Document ID·이름·유형 등까지 읽는 방향의 확장이 필요하다.

## 핵심 설계 방향

### 1. 룰북 소유 정본

`9999. D&D 룰북 소유 리스트.md`는 계속 룰북 자체의 정본으로 유지한다.

역할:

- 실제 보유 룰북 판정
- D&D Beyond 존재 여부
- 비교 전용 항목 구분
- 향후 룰북 관리 등록일 추적
- 룰북 유형 설명 검증 상태 추적 후보

관리 등록일 및 유형 검증 필드의 구체적인 반영 방법은 후속 설계에서 확정한다.

### 룰북 유형 재검증 진행 기록

- 검증 우선순위: D&D Beyond의 출처 페이지·마켓플레이스 설명에서 데이터 유형을 먼저 확인하고, 전체 구성을 판단할 수 없는 경우에만 로컬 실제 파일을 열람한다.
- 2026-09-01 완료 범위: 소유 룰북 92권과 D&D Beyond 비교 전용 항목 14개, 총 106개 항목의 유형·실제 파일명·D&D Beyond 존재 여부를 대조했다. D&D Beyond의 공개 출처 페이지·마켓플레이스·지원 문서에서 유형을 우선 확인했고, 전체 구성이 공개되지 않은 `Boo's Astral Menagerie`, `The Astral Adventurer's Guide`, `One Grung Above`는 로컬 원본을 열람했다.
- 현재 정본 수정:
  - `Princes of the Apocalypse`: 부록의 Genasi를 반영하여 데이터 유형에 `종족`을 추가했다.
  - `One Grung Above`: D&D Beyond 검색 결과가 종족 항목만 제시하여 로컬 PDF 7쪽을 열람했다. 기존 `시나리오, 몬스터` 분류를 `데이터(종족/장비), 사전 생성 캐릭터`로 정정했다.
  - `Guildmasters’ Guide to Ravnica`: 데이터 유형에 `배경`, `주문`을 추가했다.
  - `Rrakkma`: 제공되는 9레벨 사전 생성 캐릭터를 반영했다.
  - `Acquisitions Incorporated`: 차량 데이터를 추가했다.
  - `Baldur’s Gate Gazetteer`: 마법 아이템 표기를 제거하고 `다크 시크릿`을 반영했다.
  - `Baldur’s Gate: Descent into Avernus`: Baldur’s Gate Gazetteer, 차량, 지옥 전쟁 기계 규칙을 반영했다.

  - `Explorer's Guide to Wildemount`: 영웅 연대기를 추가했다.
  - `Frozen Sick`: 질병 데이터를 추가했다.
  - `Tasha’s Cauldron of Everything`: 마법 문신, 그룹 후원자, 사이드킥, 출신 맞춤 규칙을 추가했다.
  - `Fizban's Treasury of Dragons`, `Strixhaven: A Curriculum of Chaos`, `Boo's Astral Menagerie`, `The Astral Adventurer's Guide`: 드라코닉 기프트, 학교 생활·관계, 아스트랄 변형·조우, 스펠재밍·아스트랄 항행 범위를 보강했다.

### 2. 룰북 인덱싱 레지스트리

룰북 단위 진행 상황을 요약하는 진행표를 둔다.

초기 관리 축 후보:

- 룰북 유형 검증
- 클래스
- 서브클래스
- 종족
- 배경
- 재주
- 주문
- 몬스터
- 마법 아이템

위 목록은 최초 설계에서 먼저 식별한 관리 축이며, 전체 독립 인덱스의 최종 목록으로 고정하지 않는다.

독립 인덱스 채택 기준:

1. 독립적인 이름과 정체성을 가지며 개별 검색할 필요가 있는가
2. 항목별 원본 룰북·파일·페이지 또는 섹션 위치를 별도로 기록할 필요가 있는가
3. 추출·원본 검증·FVTT 이관 대상 여부 등 진행 상태를 항목별로 추적할 필요가 있는가

각 데이터 유형은 위 기준으로 판정한다. 시나리오·설정·규칙·장비·차량·질병·저주·오염·변이·변형 등도 명칭만으로 보조 정보에 고정하지 않는다. 자체 정체성과 항목별 추적 필요성이 있으면 독립 인덱스로 채택하고, 독립 추적 단위가 아니면 룰북 또는 다른 독립 항목의 보조 필드·연결 정보로 둔다.

권장 상태 후보:

- 미확인
- 해당 없음
- 추출 대상
- 추출 중
- 추출 완료
- 검증 필요
- 검증 완료

이 구분은 인덱스의 검색 단위와 장기 진행률 단위만 정한다. 보조 정보는 독립 항목으로 중복 추출하지 않고, 원본 룰북·독립 데이터 항목의 검색 필드 또는 연결 데이터로 기록한다.

검색을 빠르게 하기 위해 데이터 유형별 독립 인덱스를 둔다.

예:

- 클래스 인덱스

#### 공통 추적 상태 초안

각 독립 인덱스 항목은 다음 상태를 분리해 기록한다. 하나의 상태값으로 합치지 않는다.

| 추적 축 | 값 | 의미 |
| --- | --- | --- |
| 원본 적용성 | `미확인` / `해당 없음` / `추출 대상` | 해당 룰북이 이 유형의 데이터를 제공하는지와 추출 필요 여부 |
| 추출 | `미착수` / `추출 중` / `추출 완료` | 이름·원본 위치를 인덱스에 옮긴 정도 |
| 원본 검증 | `미검증` / `검증 중` / `검증 완료` / `불일치` | 실제 원문과 인덱스의 이름·위치·핵심 분류 일치 여부 |
| FVTT 이관 대상 | `false` / `true` | 기본값은 `false`. `true`이면 FVTT 이관 대상으로 설정 |
| Pack | `미정` / `예정` / `실존` | 이관 목적 Pack의 현재 저장소 상태. 실존은 `module.json` 등록으로만 판정 |
| FVTT 이관 | `미착수` / `이관 중` / `이관 완료` | 대상 Document의 작성·반영 정도 |
| 저장소 검증 | `미확인` / `존재 확인` / `누락` / `중복` / `불일치` | 인덱스가 가리키는 Document의 저장소 실재 및 중복 여부 |
| FVTT 원본 대조 | `미검증` / `검증 중` / `검증 완료` / `불일치` | 저장소 Document와 원본의 내용 일치 여부 |

이 상태는 룰북별 진행표와 개별 데이터 인덱스에서 공통으로 사용한다. 룰북별 진행표는 유형별 집계 상태를, 개별 인덱스는 항목별 실제 상태를 보관한다.

#### FVTT 이관 대상 Boolean 계약

- 모든 독립 인덱스 항목에 FVTT 이관 대상 여부를 둔다.
- 기본값은 `false`다.
- `false`는 현재 이관 대상으로 선택되지 않았다는 뜻이며, 영구 제외나 검토 완료를 의미하지 않는다.
- `true`는 해당 항목을 FVTT 이관 대상으로 설정했다는 뜻이다.
- 실제 이관 착수·완료 및 저장소 검증 상태는 이 Boolean과 별도 축으로 추적한다.
- 전체 인덱스 축이 마련되기 전에는 모든 항목을 `false`로 시작하고, 이후 유형별 판단에 따라 `true`로 전환한다.

예:

- 주문: 레벨, 학파, 클래스
- 몬스터: CR, 크리처 유형
- 서브클래스: 기본 클래스
- 아이템: 아이템 유형, 희귀도, 조율 여부 등

### 4. 인덱스 유형과 FVTT Pack 분리

중요 원칙:

**룰북 데이터 유형과 Foundry Compendium Pack은 동일 개념이 아니다.**

예를 들어 클래스·서브클래스·재주·주문·종족 등은 Foundry에서 모두 Item 계열일 수 있지만, 실제 Pack 구분은 모듈 설계에 따라 달라질 수 있다.

따라서:

- `주문 인덱스 = common-spells`처럼 고정하지 않는다.
- 유형별 인덱스에서 FVTT 목적지 Pack을 별도 매핑한다.
- Pack 상태는 최소 `미정 / 예정 / 실존`을 구분할 수 있어야 한다.
- 실제 Pack 실존 여부는 `module.json`을 기준으로 한다.

#### 독립 인덱스와 FVTT 목적지 매핑 초안

현재 `module.json`에 등록된 Pack은 `common-monsters`, `common-feats`, `common-items`뿐이다. 아래 `예정` Pack은 설계상 목적지일 뿐, Module Maker로 생성되어 `module.json`에 등록되기 전까지 실존 Pack으로 취급하지 않는다.

| 독립 인덱스 | FVTT Document | 목적 Pack | Pack 상태 | 매핑 기준 |
| --- | --- | --- | --- | --- |
| 몬스터 | Actor | `common-monsters` | 실존 | 룰북 몬스터는 기존 CR 템플릿과 별도 폴더로 보관 |
| 재주 | Item | `common-feats` | 실존 | 재주만 수록 |
| 마법 아이템 | Item | `common-items` | 실존 | 무기·장비·소모품·전리품과 함께 Item 하위 유형으로 구분 |
| 주문 | Item | `common-spells` | 예정 | 주문만 수록 |
| 종족 | Item | `common-species` | 예정 | 종족 및 종족 특성 수록 |
| 클래스 | Item | `common-character-options` | 예정 | 클래스·서브클래스·배경과 같은 플레이어 선택지를 한 Pack에 보관 |
| 서브클래스 | Item | `common-character-options` | 예정 | 기본 클래스 연결을 인덱스 필드로 보관 |
| 배경 | Item | `common-character-options` | 예정 | 배경 고유 보상·특성을 Item 하위 유형으로 구분 |

`common-character-options`는 아직 모듈 문서나 `module.json`에 없는 새 예정 Pack이다. Pack 생성 전에는 각 D&D5e Item 하위 유형과 실제 컴펜디움 입력·로드 동작을 Foundry VTT 13.351 / D&D5e 5.2.4 환경에서 검증한다. 검증 전에는 이 표를 이관 실행 지시로 해석하지 않는다.

### 5. common / luxterra Scope 분리

현재 모듈 설계 기준:

- `common`: 세계관 비종속 D&D5e 공통 데이터
- `luxterra`: 룩스테라 고유 데이터

룰북에서 추출한 데이터의 기본 FVTT Scope는 원칙적으로 `common`이다.

룩스테라 커스텀 몬스터·NPC·아이템·주문·설정·씬 등은 `luxterra` Scope에 속한다.

### 6. 출처 유형 분리

현재 `common-monsters`에 존재하는 90개 CR 템플릿은 룰북에서 추출한 몬스터가 아니다.

따라서 개별 인덱스/FVTT 데이터에는 출처 유형 구분이 필요하다.

후보:

- `rulebook`
- `custom`
- `template`

이 구분이 없으면 90개 템플릿을 룰북 이관 데이터로 잘못 집계할 수 있다.

### 7. FVTT 상태 다축 추적

FVTT 관련 상태를 하나의 `완료/미완료`로 관리하지 않는다.

최소 다음 개념을 분리한다.

- FVTT 이관 대상 여부 Boolean
- 대상 Pack 매핑
- Pack 실존 여부
- 실제 이관 상태
- 실제 저장소 Document 존재 확인
- Document ID / UUID
- FVTT 데이터 검증 상태

예상 실제 이관 상태 후보:

- 미착수
- 이관 중
- 이관 완료

예상 저장소 확인 상태 후보:

- 미확인
- 존재 확인
- 누락
- 중복
- 불일치

예상 FVTT 검증 상태 후보:

- 미검증
- 검증 중
- 검증 완료
- 수정 필요

정확한 상태 계약은 후속 설계에서 확정한다.

## 데이터 유형 정규화 진행 기록

- 전체 유형 목록은 `9999. D&D 룰북 소유 리스트.md`의 개략적인 룰북 유형 설명만으로 확정하지 않는다.
- 목록 정본은 보유 룰북과 실제 파일 관계의 정본이지만, 모든 세부 데이터 유형을 빠짐없이 발견하는 유일한 정본으로 사용하지 않는다.
- 현재는 넓게 묶인 분류를 독립 인덱스 채택 기준에 따라 정규화하는 단계다.
- `효과·변형`은 질병·저주·상태·상처·오염·타락·광기·변이·변형 등의 특수 체계를 임시로 모아 검토하기 위한 상위 분류이며, 그 자체를 단일 독립 인덱스로 확정한 것은 아니다.
- 드라켄하임 계열에서는 오염 체계와 그 결과로 발생하는 변이를 구분하여 검토한다. 기존 유형 설명에는 오염이 반영되어 있으나 변이가 누락되어 있다.
- 그림 할로우 계열에서는 고유한 변형(Transformations) 체계를 별도 유형 후보로 검토한다. 기존 두 룰북의 유형 설명에는 이 체계가 누락되어 있다.
- 각 특수 체계는 원본에서 항목별 이름·위치·진행 상태를 독립적으로 추적해야 하는지 확인한 뒤 독립 인덱스 또는 보조 정보로 판정한다.

## 크로스체크 구조

최종적으로 세 종류의 정합성 검증이 필요하다.

### A. 룰북 ↔ 룰북 인덱스

검증 대상:

- 원본에 실제 데이터가 존재하는가
- 인덱스에서 누락되지 않았는가
- 이름·분류·위치가 정확한가

### B. 룰북 인덱스 ↔ `nihil-compendium-module`

검증 대상:

- 이관 완료로 표시된 데이터가 실제 Pack에 존재하는가
- 대상 Pack이 맞는가
- Document ID/UUID가 유효한가
- 중복 Document가 없는가
- 저장소에는 있으나 인덱스에 등록되지 않은 데이터가 없는가

### C. 원본 룰북 ↔ FVTT Document

검증 대상:

- 이름
- 데이터 유형
- 핵심 수치
- 설명
- 효과
- 조건
- 주문 레벨
- CR
- 아이템 등급
- 클래스·서브클래스 연결
- 기타 유형별 핵심 필드

인덱스는 원본과 FVTT 사이의 연결점이며, 최종 데이터 정합성은 원본과 FVTT를 직접 대조해 검증한다.

## 현재 확정된 원칙

- `9999. D&D 룰북 소유 리스트.md`를 룰북 정본으로 유지한다.
- 과거 Google Sheets 체크리스트는 더 이상 사용하지 않는다.
- 룰북 인덱스는 원문 대체물이 아니라 위치 탐색·작업 상태 추적 수단이다.
- 추출 완료와 원본 검증 완료를 구분한다.
- 룰북 데이터 유형과 FVTT Pack 구조를 분리한다.

- 모든 독립 인덱스 항목의 FVTT 이관 대상 여부는 Boolean으로 관리하며 기본값은 `false`, `true`는 이관 대상으로 설정했음을 의미한다.
- 실제 FVTT Pack의 현재 정본은 `nihil-compendium-module/module.json`이다.
- 계획 Pack 문서는 예정 구조로만 취급한다.
- 룰북 데이터는 기본적으로 `common` Scope를 사용한다.
- 룩스테라 고유 데이터는 `luxterra` Scope로 분리한다.
- 룰북/커스텀/템플릿 등 데이터 출처 유형을 구분한다.
- FVTT 이관 기록과 실제 모듈 저장소 상태를 양방향 크로스체크한다.
- 저장소의 기존 검증 스크립트를 향후 자동 크로스체크 기반으로 활용할 수 있다.

### 데이터북 상세 인덱스 작성 규칙

- 데이터북 논리 룰북 하나당 Markdown 인덱스 파일 하나를 작성한다.
- 파일명 앞 번호는 데이터북 표 순서이며, 다음 번호는 9번이다.
- 원본이 여러 PDF로 분할되어도 논리 룰북 인덱스는 하나로 유지한다.
- 분할 PDF의 위치는 `2번 PDF p.15`처럼 파일 번호와 PDF 페이지를 함께 적는다.
- 페이지는 PDF 뷰어의 전체 페이지 번호만 사용하며, 인쇄 페이지나 이미지 속 페이지 번호는 기록하지 않는다.
- 맵, 삽화, 이미지 참조, 이미지 개수는 추적하지 않는다.
- 기본 상세 분류는 아이템, 몬스터, NPC, 피트, 주문, 클래스, 서브클래스다.
- 종족·배경 등 독립된 플레이어 옵션이 있으면 별도 플레이어 옵션 절에 추가한다.
- 단순 언급은 제외하고, 실제 설명·획득 위치·스탯블록·구체적 변형 규칙이 있는 항목만 기록한다.
- 고유명이 있는 생물은 NPC 절에 넣는다.
- 이름 없는 몬스터는 이 PDF에 실제 스탯블록이나 구체적 변형 규칙이 있을 때만 몬스터 절에 넣는다.
- 주문 두루마리나 NPC 스탯블록에 주문명이 나온 것만으로는 독립 주문으로 기록하지 않는다.
- 외부 핵심 룰북의 일반 스탯블록을 단순 참조하는 항목은 해당 PDF의 독립 몬스터 데이터로 취급하지 않는다.
- 시나리오북과 설정북은 이 상세 인덱스 규칙을 적용하지 않는다. 전 페이지를 검증한 뒤 장르·핵심 주제·확인된 데이터 유형만 목록과 현황에 기록한다.

현재 진행:

이후 순서:

1. 선택한 주분류의 현재 원본을 전체 대조한다.
2. 데이터북이면 상세 위치 인덱스를 작성하고, 시나리오북·설정북이면 장르·주제·데이터 유형만 갱신한다.
3. 소유 목록과 진행 현황의 해당 행을 갱신한다.
4. 반영본을 다시 읽어 분류별 집계와 다음 대상을 검증한다.

## 작업 제한

- Google Drive 및 GitHub에 대한 실제 생성·수정·삭제·푸시는 마스터의 명시적인 요청이 있을 때만 수행한다.
- OCR 필요 여부는 작업 공간에서 원본 PDF의 텍스트 레이어를 직접 추출해 확인한다. Google Drive가 반환한 읽기 텍스트·검색 색인·미리보기는 보조 자료일 뿐, 이 판정의 근거로 사용하지 않는다.
- OCR이 필요한 원본은 OCR 처리·수동 전사·부분 인덱싱을 하지 않고 건너뛴다. 해당 파일은 `OCR 필요 — 인덱싱 건너뜀`으로 미검증 상태를 보존하며, 분할본 중 하나라도 해당하면 논리 룰북 전체를 완료 처리하지 않는다.
- 기존 파일을 수정할 때에는 별도 지시가 없으면 원본 파일명을 유지한다.
- 실제 Pack 구조는 현재 `module.json`을 우선하고 계획 문서만으로 존재를 추정하지 않는다.
- 룰북 원본 데이터와 FVTT 데이터의 내용 검증 전에는 최종 완료로 처리하지 않는다.
