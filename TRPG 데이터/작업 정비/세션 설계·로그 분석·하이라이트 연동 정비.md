# 세션 설계·로그 분석·하이라이트 연동 정비

## 1. 작업 목적

세션 제작 단계의 장면·맵 설계와 실제 플레이 로그 분석, 세션 하이라이트 추출, 세션 하이라이트 이미지 생성 사이를 하나의 추적 가능한 데이터 흐름으로 연결한다.

이 작업은 다음 두 범위를 함께 관리한다.

1. 프로젝트 공통 구조 개편
   - 세션 설계 장면·맵에 영구 식별자와 로그 매칭용 구조를 부여한다.
   - 로그 분석이 실제 플레이 장면과 세션 설계를 비교하고 기본 하이라이트를 산출하도록 개편한다.
   - 로그 하이라이트 추출과 이미지 생성이 분석 결과를 중복 없이 후속 사용하도록 연결한다.
2. 현행 세션 설계 정비
   - `남아있는 이야기 2 / 섬에서 전해진 바람 상편 2` 세션 패키지를 새 구조로 승격한다.
   - 현재 제작된 맵 4개 중 실질적으로 핵심 사용되는 맵이 2개뿐인 문제를 재검토한다.

## 2. 현재 상태

- 상태: 현행 세션 패키지 정비 완료, 전역 자산 이관은 미착수
- 완료한 현행 세션 범위:
  1. `섬에서 전해진 바람 상편 2`의 네 맵을 `03 → 01 → 04 → 02` 필수 흐름으로 재배정했다.
  2. 장면 00~08에 `scene_uuid`와 구조화된 `사용 맵` 참조를 부여했다.
  3. 맵 01~04에 `map_uuid`를 부여하고, 맵 03의 도시 진입 1차 전투와 맵 04의 격리·돌 회수·추적 국면을 고유 플레이로 확정했다.
  4. 맵 02의 논리 그리드를 이미지 확인 뒤 `30 × 30`으로 정정했고, 이미지 파일 4개의 SHA-256 불변을 확인했다.
- 미착수 범위: 전역 자산 분류 이관, `16. 컨셉 이미지`의 미분류 전환, 공용 단일 맵 카탈로그의 물리 이관.
- 재개 지점: 전역 자산 폴더 구조와 공용 맵 카탈로그의 대상 목록을 별도 설계로 확정한다.

## 3. 이번 작업에서 확정한 전체 데이터 모델

### 3.1 설계 장면 식별

모든 신규 세션 설계 장면은 영구 `scene_uuid`를 가진다.

- 기본 형식: 소문자 표준 UUID
- 예: `5e02c452-01a3-4d9e-8737-8f2b1a0c9d64`
- `scene_number`: 장면 정렬·표시 순서
- `scene_title`: 사람이 읽는 장면 이름
- `scene_uuid`: 장면의 영구 정체성
- 장면 번호·제목·파일명이 바뀌어도 같은 장면이면 `scene_uuid`를 유지한다.
- 프롤로그와 에필로그도 정식 장면으로 동일 규칙을 적용한다.

### 3.2 장면 식별 정보

각 장면 파일에는 영구 식별 정보와 로그 매칭용 최소 장면 지문을 둔다.

```markdown
## 장면 식별 정보
- scene_uuid:
- 설계 장면 번호:
- 설계 장면명:
- 주요 장소:
- 핵심 사건:
- 주요 참여자:
- 고유 앵커:
```

필드 목적:

- `주요 장소`: 로그의 공간 단서와 대응한다.
- `핵심 사건`: “실제로 이 사건이 발생하면 이 설계 장면이다”를 판정하는 핵심 기준이다.
- `주요 참여자`: 모든 인물을 나열하지 않고 장면 식별에 유효한 PC·NPC·몬스터만 기록한다.
- `고유 앵커`: 고유 물건·현상·구조·명칭 등 다른 장면과 구별되는 시각·사건 단서를 기록한다.

장면 역할, 시작/종료 조건, 공개·숨겨진 정보, 예상 대응 등 기존 `장면 기능` 정보는 중복하여 장면 식별 블록에 복제하지 않는다.

### 3.3 설계 맵 식별

모든 신규 세션 설계 맵은 영구 `map_uuid`를 가진다.

- 기본 형식: 소문자 표준 UUID
- `map_number`: 세션 패키지 내 정렬 번호
- `map_title`: 사람이 읽는 맵 이름
- `map_uuid`: 맵의 영구 정체성
- 같은 맵을 재사용하는 경우 기존 `map_uuid`를 유지한다.
- 공간 구조를 다시 설계하여 별도 배틀맵 이미지가 필요한 수준으로 달라지면 새 `map_uuid`를 발급하고 필요 시 `derived_from_map_uuid`로 원본 맵을 참조한다.

### 3.4 장면의 사용 맵 참조

장면에서 맵을 찾을 때는 의미 추론보다 직접 참조를 우선한다.

맵이 없으면 빈 섹션으로 두지 않고 반드시 다음처럼 명시한다.

```markdown
## 사용 맵
- 사용 맵 없음
  - 사유:
```

단일 맵 사용 예시:

```markdown
## 사용 맵
- map_uuid: `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`
  - 맵명:
  - 사용 방식: 필수
  - 공간적 목적:
```

복수 맵 사용 시에도 맵별 하위 항목을 나누고 `map_uuid`, 맵명, 사용 방식, 공간적 목적을 각각 기록한다.

맵 상태는 로그 분석에서 다음처럼 구분한다.

- `confirmed`: 장면 참조를 통해 확정된 설계 맵
- `none`: 의도적으로 맵 없음
- `unavailable`: 세션 설계 자체가 없음
- `unmapped`: 세션 설계는 있으나 맵 할당이 완료되지 않음
- `uncertain`: 설계 장면 매칭 자체가 불확실하여 맵도 확정할 수 없음

### 3.5 플레이 완료 설계의 역사 기록 보존

세션 패키지 상태에 `played`를 사용할 수 있다.

`played`의 의미는 “이 설계 장면이 실제로 실행되었다”가 아니라 “이 세션이 실제 플레이까지 완료되어 세션 설계 패키지를 당시의 의도 기록으로 동결한다”이다.

- 오탈자, 깨진 링크, 잘못된 참조 등 정정은 가능하다.
- 플레이 당시의 장면 목적·핵심 사건·맵 구조·장면 순서를 후대 결과에 맞춰 소급 변경하지 않는다.
- 실제 실행·생략 여부는 로그 분석의 `Pxx ↔ scene_uuid` 대응 결과에서 기록한다.

## 4. 실제 플레이 장면 Pxx 구조

3번 로그 분석은 설계 문서에 맞춰 로그를 자르지 않는다.

먼저 원본 로그만 보고 실제 플레이의 목적·갈등·상태 변화를 기준으로 `P01`, `P02` … 실제 플레이 장면을 분할한 뒤 세션 설계와 대응한다.

### 4.1 장면 분할 우선순위

강한 장면 경계:

1. 중심 목적 변화
2. 핵심 갈등·문제 변화
3. 비가역적 사건 상태 변화
4. 의미 있는 장소·시간 변화
5. 독립적인 플레이 모드 변화(전투·추격·도주·의식·잠입 등)
6. 주요 참여자 구성 변화로 장면 중심이 바뀌는 경우

약한 변화만으로는 새 Pxx를 만들지 않는다.

- 단순 위치 이동
- 같은 대화 안의 화제 변화
- 단일 판정 발생
- 보스 전투 중 단순 페이즈 변화
- 같은 목적·갈등 안에서 접근 방식만 달라지는 경우

하이라이트를 만들기 위해 Pxx를 잘게 분할하지 않는다. 한 Pxx 안에서 여러 Hxx가 나올 수 있다.

### 4.2 Pxx 권장 필드

```markdown
### Pxx. 실제 플레이 장면명
- 실제 전개:
- 장면 시작:
- 장면 종료:
- 주요 장소:
- 주요 참여자:
- 핵심 사건:
- 세션 설계 대응:
- 설계 맵:
- 설계 대비 실제 변화:
```

`설계 대비 실제 변화`는 세션 설계가 없거나 유의미한 차이가 없으면 생략할 수 있다.

### 4.3 설계 장면 대응 상태

- `matched`: Pxx와 하나의 설계 장면이 정상 대응
- `merged`: 여러 설계 장면이 실제 플레이에서 하나의 Pxx로 합쳐짐
- `split`: 하나의 설계 장면이 실제 플레이에서 여러 Pxx로 분리됨
- `skipped`: 설계에는 있었으나 실제로 진행되지 않음
- `unplanned`: 실제 플레이에서 발생했으나 설계에 대응 장면이 없음
- `uncertain`: 대응을 확정할 근거가 부족함

진행되지 않은 설계 장면은 실제 Pxx가 존재하지 않으므로 `## 실제 플레이 장면 및 세션 설계 대응` 섹션 말미의 별도 `진행되지 않은 설계 장면` 목록에서 `skipped`로 관리한다.

## 5. 3번 로그 분석의 신규 기본 산출 구조

기존 `정보 흐름 지도`는 정보 의미의 전환점을 기록하는 역할을 유지한다. 모든 플레이 장면을 담는 Pxx와 합치지 않는다.

정보흐름분석 문서의 권장 흐름은 다음이다.

```text
YAML 프론트매터
↓
기승전결 스토리 요약
↓
정보 흐름 지도
↓
실제 플레이 장면 및 세션 설계 대응 (Pxx)
↓
기존 서사 심층 분석·정보 흐름 요약·떡밥·관계 분석
↓
PC 관계 변화
↓
세션 하이라이트 (Hxx)
↓
세션 단위 핵심 결과 데이터
```

프론트매터에는 세션 설계 존재 여부와 참조 위치를 기록할 수 있다.

```yaml
session_design:
  status: found
  package: ...
  scene_index: 02. ... 장면 목록.md
  map_index: 맵/00. 맵 목록.md
```

세션 설계가 없으면 `status: not_found`로 기록한다.

## 6. 기본 세션 하이라이트 Hxx

3번 로그 분석은 정보흐름분석의 기본 산출물로 세션 하이라이트 `H01`, `H02` … 를 선정한다.

Hxx는 Pxx에서 이미지화 가치가 높은 순간을 선별하는 계층이다.

- Pxx = 실제 플레이 진행 단위
- Hxx = 실제 플레이 안의 기억할 만한 순간

Hxx는 `scene_uuid`, `map_uuid`를 반복 복제하지 않고 Pxx를 참조한다.

```text
Hxx
↓
Pxx
↓
scene_uuid
↓
map_uuid
```

권장 Hxx 필드:

- 우선순위: `high / medium / low`
- 유형
- 실제 장면: `Pxx`
- 선정 이유
- 하이라이트 순간
- 중심 인물
- 핵심 시각 요소
- 이미지화 준비 상태

세션 설계에 하이라이트 후보 여부나 우선순위를 미리 저장하지 않는다. 실제 플레이가 끝난 뒤 로그를 기준으로 선정한다.

## 7. 2번 로그 하이라이트 추출 기능의 역할

2번 기능은 두 모드로 운용한다.

### 7.1 독립 추출 모드

사용자가 로그 분석 없이 하이라이트만 요청한 경우 기존처럼 원본 로그에서 직접 Highlight Card를 만든다.

```text
원본 로그 → 2번 → Highlight Card
```

### 7.2 분석 연계 정밀화 모드

3번 정보흐름분석이 존재하면 Hxx/Pxx를 기준으로 정밀화한다.

```text
3번 Hxx
→ Pxx
→ Pxx 원본 로그 범위 재확인
→ scene_uuid / map_uuid 대응 확인
→ 캐릭터 레퍼런스·시각 맥락 확인
→ 완전한 Highlight Card
```

2번은 설계 장면 ID, 설계 맵 ID, FVTT Scene ID를 구분한다.

- `design_scene_refs[].scene_uuid` = 설계 장면 UUID
- `design_map_refs[].map_uuid` = 설계 맵 UUID
- `fvtt_scene_id` = 실제 Foundry Scene 식별자

설계 맵이 확정되어 있어도 FVTT Scene은 없을 수 있으며, 이 경우 설계 맵은 그대로 배경 근거로 사용할 수 있다.

## 8. 1번 이미지 모듈 내부 4번 세션 하이라이트 이미지 연계

이미지 생성 단계는 다음 연결을 이해한다.

```text
Hxx → Pxx → scene_uuid → map_uuid
```

근거 우선순위:

- 실제 사건: 원본 로그 / Pxx
- 이미지화 순간 선정: Hxx / Highlight Card
- 설계 공간: `map_uuid` 정본
- 인물 외형: 캐릭터 레퍼런스
- 실제 FVTT Scene: 별도 `fvtt_scene_id`

설계 맵이 없거나 `unavailable / unmapped / uncertain`이면 원본 로그의 환경 단서와 별도 풍경·Scene Manifest를 사용하고 임의로 배경을 확정하지 않는다.

## 9. 묘사 문단 규칙 선행 정비

이 작업과 병행하여 세션 제작의 실제 플레이용 묘사 규칙도 갱신 완료했다.

적용 대상:

- 세션 프롤로그 묘사
- 세션 에필로그 묘사
- 장면 묘사
- 진행 묘사
- NPC 등장 묘사
- 몬스터 등장 묘사
- NPC·몬스터 정본의 마스터용 묘사

확정 규칙:

- 모든 서술 문단은 반드시 3~4개의 완결된 문장으로 작성한다.
- 한 문장짜리 서술 문단을 허용하지 않는다.
- 강조·긴장감·장면 전환을 위해 한 문장을 독립 문단으로 분리하지 않는다.
- 5문장 이상이면 의미와 장면 호흡을 기준으로 각각 3~4문장인 복수 문단으로 나눈다.
- 고정 대사·인용문·목록·GM 메모는 직접 대상에서 제외할 수 있지만 앞뒤 상황 묘사는 다시 3~4문장 문단 기준을 따른다.

별도 “마스터 고유 묘사 문체 템플릿”을 만들어 문체 자체를 스타일화하는 안은 아이디어만 남겼고 이번 작업 범위에서는 보류했다.

## 13. 현행 세션의 확정 맵 운용 구조

마스터는 제작 완료된 맵 4종을 모두 필수 플레이 흐름에 편입하는 방향을 확정했다.

```text
03. 아그니르 도시 외곽 진입로
= 도시 진입 국면
↓
01. 아그니르 도시 전투 구역
= 도시 방어 국면
↓
04. 성소 외곽 회랑 및 격리 구역
= 조사·격리·조종망 추적 국면
↓
02. 검은 사수의 왼팔 성소
= 유해·최종 갈등 국면
```

공간 이동 자체가 `03 → 01 → 04 → 02` 네 단계의 세션 진행 구조가 된다.

### 맵 03 — 도시 진입과 1차 전투

- 비공정에서 하선한 일행은 맵 03에서 도시로 진입하기 위한 1차 전투를 치른다.
- 이 전투는 베르카스 전투와 분리된 자코 처리이며, 종료 뒤 일행은 맵 01의 핵심 도시 방어전으로 이동한다.

### 맵 01 — 도시 방어와 베르카스 전투

- 맵 01은 베르카스가 지휘하는 2차 전투의 주 전장이다.
- 베르카스 격파 뒤, 워락들이 붙잡아 온 수상한 마법사가 등장한다.
- 일행은 수상한 마법사를 인계받은 뒤 맵 04로 이동한다.

### 맵 04 — 성소 외곽 조사와 회수

- 맵 04에서 `혼탁함을 먹는 돌`을 찾고 회수한다.
- 수상한 마법사는 베르카스 격파 뒤, 일행이 맵 04로 들어가기 전에 워락들이 인계한다.
- 돌은 혼탁하고 사특한 기운을 먹어 감추는 `악마의 씨앗`이며, 실타래는 수상한 마법사를 매개체로 삼아 자신의 기운을 숨기는 데 이용했다.
- 마법사의 잔류 조종 실과 은폐 술식을 끊는 조사 플레이는 유지하며, 돌 회수와 결합해 실타래의 은폐를 무너뜨리고 추적 근거를 만든다.
- 이번 세션에서 돌이 품은 악마는 태어나지 않는다. 돌은 회수 뒤에도 장기 위험 자산으로 남는다.
- 회수와 조사가 끝난 뒤 일행은 맵 02의 핵심 성소로 이어진다.

### 맵 02 — 왼팔 공개와 최종 갈등

- 맵 02는 검은 사수의 왼팔 공개와 실타래의 최종 갈등을 담당하는 핵심 성소 공간으로 유지한다.

### 장면 조정 기준

- 장면 01은 맵 03의 자코 처리 1차 전투가 된다.
- 장면 02는 맵 01의 베르카스 2차 전투가 된다.
- 장면 04·05는 맵 04의 격리 조사·돌 회수·실타래 폭로를 담당한다.
- 장면 06은 맵 02의 왼팔 공개와 최종 갈등만 담당하며, 맵 04를 선택 보조 전장으로 사용하지 않는다.
