## 저장소별 실행 흐름

각 저장소에서 다음 순서로 실행한다.

1. 대상 경로와 Git 저장소 여부를 확인한다.
2. 진행 중인 Git 작업, 잠금 파일, 현재 브랜치와 upstream을 확인한다.
3. 기존 staged 변경과 최근 15분 안에 수정된 파일을 확인한다.
4. 원격 상태를 fetch하고 현재 브랜치와 upstream의 앞섬·뒤처짐·분기를 판정한다.
5. 추적 변경, 삭제, 이름 변경, untracked 파일과 diff를 모두 분석한다.
6. 비밀정보와 비정상 삭제 위험을 검사한다.
7. 변경을 성격과 직접 의존 관계에 따라 논리적인 커밋 단위로 분류한다.
8. 각 단위를 stage한 뒤 staged diff를 다시 확인하고 검증한다.
9. 검증을 통과한 단위만 커밋한다.
10. 저장소의 모든 안전한 커밋 처리가 끝나면 현재 upstream으로 한 번 push한다.

한 저장소가 중단되거나 일부 변경 단위가 실패해도 다른 저장소의 처리는 계속한다.

## 작업 중 변경 보호

다음 조건 중 하나라도 해당하면 해당 저장소 전체를 이번 실행에서 건너뛴다.

- 실행 전에 staged 변경이 존재한다.
- merge, rebase, cherry-pick 등 진행 중인 Git 작업이나 해결되지 않은 충돌이 있다.
- Git 잠금 파일이 존재한다.
- Git 상태에서 확인된 변경 후보 가운데 최근 15분 이내 수정된 파일이 있다.
- HEAD가 분리되어 있거나 현재 브랜치를 확정할 수 없다.
- 현재 브랜치의 upstream을 해석할 수 없다.

예약 작업은 브랜치를 전환하거나 새 브랜치를 만들지 않는다. staged 변경을 해제하거나 사용자의 작업 상태를 재구성하지 않는다.

## 원격 상태 처리

원격 상태 확인에는 fetch만 사용한다. pull, rebase, `reset --hard`, force push는 금지한다.

- upstream보다 뒤처졌거나 양쪽에 서로 다른 커밋이 있어 분기된 경우 해당 저장소를 중단한다.
- 로컬에만 존재하는 기존 커밋은 실행 당시 Codex가 저장소 상태, 변경 연속성, push 안전성을 분석하여 함께 push할지 판단한다.
- 판단 근거가 불충분하면 기존 로컬 커밋을 변경하지 않고 해당 저장소를 중단한다.

## 비밀정보와 삭제 안전 검사

새로 추적되려는 `.env`, 인증서, 개인 키, 토큰, 자격 증명, 그 밖의 비밀정보 후보를 발견하면 해당 저장소 전체를 중단한다. 보고에는 파일과 차단 사유만 남기고 비밀값은 노출하지 않는다.

삭제 안전성은 고정된 파일 수 하나로 판정하지 않는다. 전체 변경 대비 삭제 비율, 디렉터리 단위 소실, 이동·이름 변경·형식 변환에 따른 대체 파일 존재 여부, 저장소 문맥을 함께 분석한다.

- 정상적인 대량 이동·이름 변경·형식 변환임을 검증할 수 있으면 처리할 수 있다.
- 삭제 의도나 대체 관계가 불분명하면 해당 저장소 전체를 중단한다.

## 커밋 분류

하루 변경을 하나의 커밋으로 고정하지 않는다. 기능, 데이터, 문서, 수정, 리팩터링, 운영 지침처럼 변경 성격이 다르면 분리한다. 직접 의존하는 파일은 같은 단위에 둔다.

파일 하나에 서로 독립적인 변경이 함께 있으면 다음 기준을 적용한다.

- 서로 독립적임이 명확하고 부분 stage 뒤 staged diff를 재검증할 수 있을 때만 hunk 단위로 나눈다.
- 독립성을 확정하기 어렵거나 분할로 문맥이 깨질 수 있으면 파일 전체를 하나의 관련 단위로 묶는다.

자동 분류의 목표는 커밋 수를 늘리는 것이 아니라 각 커밋이 하나의 설명 가능한 변경 목적을 갖게 하는 것이다.

## 검증과 커밋 형식

각 논리 단위는 커밋 전에 `git diff --check`를 통과해야 한다. 저장소 지침이나 변경 유형에 맞는 검사 명령이 있으면 해당 단위에 필요한 추가 검사를 실행한다.

- 검증에 실패한 단위는 커밋하지 않는다.
- 실패 단위와 독립적인 다른 단위는 검증을 통과하면 계속 처리할 수 있다.
- 커밋 직전 staged diff를 다시 읽어 의도한 파일과 변경만 포함됐는지 확인한다.

커밋 제목은 다음 형식을 사용한다.

```text
yyyy MMdd <type>(<scope>): <한글 설명>
```

변경 내용이 많으면 커밋 본문에 한글 불릿으로 주요 내용을 기록한다. 타입과 scope는 실제 변경 성격과 저장소 문맥을 분석하여 정한다.

## 푸시와 실패 보존

저장소별 커밋이 끝난 뒤 현재 브랜치의 upstream으로 한 번 push한다. push 실패 시 이미 만든 로컬 커밋과 아직 커밋하지 않은 작업 트리 변경을 그대로 보존한다.

일반적인 커밋이 생성된 뒤 후속 단위나 push가 실패해도 앞선 커밋을 자동으로 되돌리지 않는다. amend, reset, 강제 푸시로 이력을 재작성하지 않는다.

## 알림 규칙

- 두 저장소 모두 변경이 없으면 알리지 않는다.
- 커밋과 push가 성공하면 저장소, 브랜치, 생성한 커밋 목록을 알린다.
- 저장소를 건너뛰면 저장소와 구체적인 사유를 알린다.
- 검증이나 push가 실패하면 실패 단계와 보존된 로컬 상태를 알린다.
- 비밀정보 관련 알림에는 파일 경로와 차단 사유만 포함하고 내용은 노출하지 않는다.

## 현재 확인된 실행 전제

2026-09-08 확인 시점에 작업 저장소 `master`는 `origin/master`를 upstream으로 사용한다. 설정 저장소 `master`에는 upstream이 설정되어 있지 않다. 이 상태가 유지되면 예약 작업은 확정된 안전 규칙에 따라 설정 저장소를 건너뛰고 사유를 알린다.

예약 작업 자체는 upstream을 임의로 생성하거나 변경하지 않는다. 설정 저장소까지 자동 push하려면 실제 실행 전에 별도 Git 설정으로 현재 `master`의 upstream을 확정해야 한다.
